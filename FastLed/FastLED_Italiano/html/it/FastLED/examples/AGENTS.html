Linee Guida per gli Agenti di Esempio FastLED¶

🚨 CRITICO: REGOLE PER LA CREAZIONE DI FILE .INO¶

⚠️ PENSARE PRIMA DI CREARE FILE .INO ⚠️¶

I file .ino dovrebbero essere creati CON PAZIENZA e SOLO quando veramente giustificato.

🚫 QUANDO NON CREARE FILE .INO:¶

  • Testare piccole modifiche al codice - Utilizzare file di test o “unit test” esistenti

  • Convalida rapida delle API - Utilizzare “unit test” o modificare esempi esistenti

  • Debug di funzioni specifiche - Utilizzare file di test, non nuovi sketch

  • Esperimenti una tantum - Creare invece file di test temporanei

  • Piccoli test di funzionalità - Estendere esempi rilevanti esistenti

✅ QUANDO CREARE FILE .INO:¶

1. Temporary Testing (.ino)¶

Utilizzare il Pattern: temp_<feature>.ino o test_<api>.ino

// temp_json_api.ino - Testing new JSON fetch functionality
// test_networking.ino - Validating network stack changes

  • ✅ PER: Testare nuove API durante lo sviluppo

  • ✅ PER: Prototipazione rapida e convalida

  • ✅ ELIMINARE DOPO L’USO - Sono temporanei per definizione

2. Significant New Feature Examples¶

Usare il Pattern: examples/<FeatureName>/<FeatureName>.ino

// examples/JsonFetchApi/JsonFetchApi.ino - Comprehensive JSON API example
// examples/NetworkStack/NetworkStack.ino - Major networking features

  • ✅ PER: Nuove funzionalità ampie e complete

  • ✅ PER: API che richiedono esempi dedicati

  • ✅ PER: Funzionalità che gli utenti implementeranno comunemente

  • ✅ PERMANENTI - Queste diventano parte della libreria di esempi

📋 CHECKLIST DI CREAZIONE:¶

Prima di creare QUALSIASI file .ino, chiedersi:

  1. 🤔 Si tratta di una nuova API in fase di test?

    • SÌ → Creare temp_<nome>.ino, eliminarlo dopo il test

    • NO → Considerare alternative

  2. 🤔 Si tratta di una nuova funzionalità significativa che gli utenti utilizzeranno comunemente?

    • SÌ → Creare examples/<FeatureName>/<FeatureName>.ino

    • NO → Utilizzare esempi o file di test esistenti

  3. 🤔 Si può modificare un esempio esistente invece?

    • SÌ → Estendere l’esempio esistente anziché crearne uno nuovo

    • NO → Procedere con la creazione

  4. 🤔 Serve solo per debug/validazione?

    • SÌ → Utilizzare test unitari o file di test temporanei

    • NO → Valutare se soddisfa i criteri di “funzionalità significativa”

🔍 CRITERI DI REVISIONE:¶

Per Esempi di Funzionalità (file .ino che rimangono):

  • ✅ Dimostra modelli di utilizzo completi e reali

  • ✅ Copre in modo completo diversi aspetti della funzionalità

  • ✅ Offre valore formativo per gli utenti

  • ✅ Mostra best practice e casi d’uso comuni

  • ✅ È probabile che più utenti vi facciano riferimento

Per Test Temporanei (file .ino che vengono eliminati):

  • ✅ Chiaramente denominato temporaneo (temp_, test_)

  • ✅ Incentrato su un’API specifica convalida

  • ✅ Verrà eliminato dopo il ciclo di sviluppo

  • ✅ Troppo complesso per il framework di unit test

❌ ESEMPI DI COSA NON CREARE:¶

  • test_basic_led.ino - Utilizzare l’esempio Blink esistente

  • debug_colors.ino - Utilizzare l’esempio ColorPalette esistente

  • quick_brightness.ino - Utilizzare unit test o modificare l’esempio esistente

  • validate_pins.ino - Utilizzare l’esempio PinTest o unit test

✅ ESEMPI DI CREAZIONI GIUSTIFICATE:¶

  • temp_new_wifi_api.ino - Test delle principali nuove funzionalità WiFi (temporaneo)

  • examples/MachineLearning/MachineLearning.ino - Nuova funzionalità di integrazione ML (permanente)

  • temp_performance_test.ino - Validazione delle modifiche di ottimizzazione (temporaneo)

🧹 RESPONSABILITÀ DI PULIZIA:¶

  • File temporanei: Il creatore deve eliminarli al termine del test

  • Esempi di funzionalità: Devono essere mantenuti e aggiornati con l’evoluzione dell’API

  • File abbandonati: Pulizia regolare recensioni per rimuovere gli esempi non utilizzati

Ricordare: La directory degli esempi è la documentazione rivolta all’utente. Ogni file .ino dovrebbe fornire un valore chiaro agli utenti di FastLED.

Standard del Codice per gli Esempi¶

Usare fl:: Namespace (Non std::)¶

NON usare funzioni o intestazioni con prefisso std:: negli esempi. Questo progetto fornisce le proprie implementazioni equivalenti a STL nello spazio dei nomi fl::.

Esempi di cosa evitare e cosa usare al suo posto:

Header:

  • ❌ #include <vector> → ✅ #include "fl/vector.h"

  • ❌ #include <string> → ✅ #include "fl/string.h"

  • ❌ #include <optional> → ✅ #include "fl/optional.h"

  • ❌ #include <memory> → ✅ #include "fl/stl/scoped_ptr.h" o #include "fl/stl/shared_ptr.h"

Funzioni e Classi:

  • ❌ std::move() → ✅ fl::move()

  • ❌ std::vector → ✅ fl::vector

  • ❌ std::string → ✅ fl::string

Perché: Il progetto mantiene le proprie implementazioni per garantire la compatibilità su tutte le piattaforme supportate ed evitare di appesantire la libreria con dipendenze STL non necessarie.

Gestione della Memoria¶

🚨 CRITICO: utilizzare sempre i pattern RAII appropriati: puntatori intelligenti, oggetti mobili o classi wrapper invece di “raw pointer” [puntatori grezzi] per la gestione delle risorse.

Opzioni di Gestione delle Risorse:

  • ✅ PREFERITO: fl::shared_ptr<T> per la “shared ownership” [proprietà condivisa] (riferimenti multipli allo stesso oggetto)

  • ✅ PREFERITO: fl::unique_ptr<T> per la proprietà esclusiva (proprietario unico, pulizia automatica)

  • ✅ PREFERITO: oggetti wrapper mobili (come fl::promise<T>) per la copia e il trasferimento sicuri di risorse univoche

  • ✅ ACCETTABILE: fl::vector<T> che memorizza gli oggetti per valore quando gli oggetti supportano la semantica di spostamento/copia

  • ❌ EVITARE: fl::vector<T*> che memorizza i puntatori grezzi - utilizzare fl::vector<fl::shared_ptr<T>> o fl::vector<fl::unique_ptr<T>>

  • ❌ EVITARE: new/delete manuale - usare fl::make_shared<T>() o fl::make_unique<T>()

Esempi:

// ✅ GOOD - Using smart pointers
fl::vector<fl::shared_ptr<HttpClient>> mActiveClients;
auto client = fl::make_shared<HttpClient>();
mActiveClients.push_back(client);

// ✅ GOOD - Using unique_ptr for exclusive ownership
fl::unique_ptr<HttpClient> client = fl::make_unique<HttpClient>();

// ✅ GOOD - Moveable wrapper objects (fl::promise example)
fl::vector<fl::promise<Response>> mActivePromises;  // Copyable wrapper around unique future
fl::promise<Response> promise = fetch.get(url).execute();
mActivePromises.push_back(promise);  // Safe copy, shared internal state

// ❌ BAD - Raw pointers require manual memory management
fl::vector<Promise*> mActivePromises;  // Memory leaks possible
Promise* promise = new Promise();      // Who calls delete?

Stampa di Debug¶

Usare FL_WARN per la stampa di debug negli esempi. Questo garantisce un output di debug coerente che funziona sia nei test unitari che in quelli delle applicazioni live.

Utilizzo:

  • ✅ FL_WARN("Debug message: " << message);

  • ❌ FL_WARN("Value: %d", value);

Nessuna Emoticon o Emoji¶

NESSUN carattere emoticon o emoji è consentito nei file sorgente C++. Questo garantisce un codice professionale e manutenibile che funziona correttamente su tutte le piattaforme e gli ambienti di sviluppo.

Esempi di cosa NON fare nei file .ino:

// ❌ BAD - Emoticons in comments
// 🎯 This function handles user input

// ❌ BAD - Emoticons in log messages  
FL_WARN("✅ Operation successful!");
FL_WARN("❌ Error occurred: " << error_msg);

// ❌ BAD - Emoticons in string literals
const char* status = "🔄 Processing...";

Esempi di alternative corrette:

// ✅ GOOD - Clear text in comments
// TUTORIAL: This function handles user input

// ✅ GOOD - Text prefixes in log messages
FL_WARN("SUCCESS: Operation completed successfully!");
FL_WARN("ERROR: Failed to process request: " << error_msg);

// ✅ GOOD - Descriptive text in string literals  
const char* status = "PROCESSING: Request in progress...";

Utilizzo di JSON - Pattern API Ideali¶

🎯 PREFERITO: utilizzare la moderna classe fl::Json per tutte le operazioni JSON. FastLED fornisce un’API JSON ideale che privilegia la sicurezza dei tipi, l’ergonomia e il funzionamento a prova di crash.

✅ UTILIZZO DI JSON IDIOMATICO:

// NEW: Clean, safe, idiomatic API
fl::Json json = fl::Json::parse(jsonStr);
int brightness = json["config"]["brightness"] | 128;  // Gets value or 128 default
string name = json["device"]["name"] | string("default");  // Type-safe with default
bool enabled = json["features"]["networking"] | false;  // Never crashes

// Array operations
if (json["effects"].contains("rainbow")) {
    // Safe array checking
}

❌ SCONSIGLIATO: API legacy prolissa:

// OLD: Verbose, error-prone API (still works, but not recommended)
fl::JsonDocument doc;
fl::string error;
fl::parseJson(jsonStr, &doc, &error);
int brightness = doc["config"]["brightness"].as<int>();  // Can crash if missing

📚 Esempio di Riferimento: Consultare examples/Json/Json.ino per pattern di utilizzo completi e un confronto tra API.

Compilazione WASM¶

🎯 COME COMPILARE QUALSIASI SKETCH ARDUINO IN WASM:

Comandi di Compilazione di Base:

# Compile any sketch directory to WASM
uv run ci/wasm_compile.py path/to/your/sketch

# Quick compile test (compile only, no browser)
uv run ci/wasm_compile.py path/to/your/sketch --just-compile

# Compile examples/Blink to WASM
uv run ci/wasm_compile.py examples/Blink --just-compile

# Compile examples/NetTest to WASM (test fetch API)
uv run ci/wasm_compile.py examples/NetTest --just-compile

# Compile examples/DemoReel100 to WASM  
uv run ci/wasm_compile.py examples/DemoReel100 --just-compile

Output: Crea la cartella fastled_js/ folder con:

  • fastled.js - Loader JavaScript

  • fastled.wasm - Binario WebAssembly

  • index.html - Pagina HTML per eseguire lo sketch

Eseguire nel Browser:

# Simple HTTP server to test
cd fastled_js
python -m http.server 8000
# Open http://localhost:8000

🚨 REQUISITI:

  • Docker deve essere installato e funzionante

  • Connessione Internet (per il download dell’immagine Docker al primo avvio)

  • ~1 GB di RAM per il container Docker durante la compilazione

Prestare Attenzione a Questi Pattern di Errore:

  • error: conflicting types for 'function_name'

  • error: redefinition of 'function_name'

  • warning: attribute declaration must precede definition

  • RuntimeError: unreachable (often async-related)

REGOLE OBBLIGATORIE:

  • Testare SEMPRE la compilazione WASM dopo aver modificato qualsiasi file della piattaforma WASM

  • UTILIZZARE uv run ci/wasm_compile.py per la convalida

  • ATTENZIONE alla presenza di conflitti di build unificate nell’output di compilazione

  • VERIFICARE il funzionamento delle operazioni asincrone correttamente nell’ambiente browser

Soppressione dei Warning del Compilatore¶

Utilizzare SEMPRE le macro di controllo del compilatore FastLED da fl/compiler_control.h per la soppressione dei warning. Questo garantisce un supporto coerente tra più compilatori e una corretta gestione delle differenze di piattaforma.

Pattern di Soppressione Corretto dei Warning:

#include "fl/compiler_control.h"

// Suppress specific warning around problematic code
FL_DISABLE_WARNING_PUSH
FL_DISABLE_FORMAT_TRUNCATION  // Use specific warning macros
// ... code that triggers warnings ...
FL_DISABLE_WARNING_POP

Macro di Soppressione dei Warning Disponibili:

  • ✅ FL_DISABLE_WARNING_PUSH / FL_DISABLE_WARNING_POP - Pattern push/pop standard

  • ✅ FL_DISABLE_WARNING(warning_name) - Soppressione generica dei warning (usare con parsimonia)

  • ✅ FL_DISABLE_WARNING_GLOBAL_CONSTRUCTORS - Warning del costruttore globale Clang

  • ✅ FL_DISABLE_WARNING_SELF_ASSIGN_OVERLOADED - Warning di autoassegnazione Clang

  • ✅ FL_DISABLE_FORMAT_TRUNCATION - Warning di troncamento del formato GCC

Cosa NON fare:

  • ❌ NON usare MAI direttive #pragma grezze - non gestiscono le differenze del compilatore

  • ❌ NON scrivere MAI Blocchi manuali #ifdef __clang__ / #ifdef __GNUC__ - utilizzare le macro

  • ❌ NON ignorare MAI i warning senza sopprimerli - risolvere il problema o sopprimerli in modo appropriato

Gestione delle Eccezioni¶

NON utilizzare blocchi try-catch o la gestione delle eccezioni C++ negli esempi. FastLED è progettato per funzionare su sistemi embedded come Arduino, dove la gestione delle eccezioni potrebbe non essere disponibile o desiderata a causa di vincoli di memoria e prestazioni.

Utilizzare Alternative per la Gestione degli Errori:

  • ✅ Codici di errore restituiti: bool function() { return false; } o enumerazioni di errore personalizzate

  • ✅ Tipi optionali: fl::optional<T> per funzioni che potrebbero non restituire un valore

  • ✅ Asserzioni: FL_ASSERT(condition) per la convalida in fase di debug

  • ✅ Return anticipati: if (!valid) return false; per condizioni di errore

  • ✅ Oggetti di stato: Tipi di risultato personalizzati che combinano successo/fallimento con dati

Esempi di corretta gestione degli errori:

// Good: Using return codes
bool initializeHardware() {
    if (!setupPins()) {
        FL_WARN("Failed to setup pins");
        return false;
    }
    return true;
}

// Good: Using fl::optional
fl::optional<float> calculateValue(int input) {
    if (input < 0) {
        return fl::nullopt;  // No value, indicates error
    }
    return fl::make_optional(sqrt(input));
}

// Good: Using early returns
void processData(const uint8_t* data, size_t len) {
    if (!data || len == 0) {
        FL_WARN("Invalid input data");
        return;  // Early return on error
    }
    // Process data...
}
