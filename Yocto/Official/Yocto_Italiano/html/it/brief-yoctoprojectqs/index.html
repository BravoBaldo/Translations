Build Rapida di un'Immagine con lo Yocto Project

Benvenuti!

Questo breve documento illustra la procedura per la creazione di un'immagine tipica utilizzando lo Yocto Project. Il documento spiega anche come configurare una build per un hardware specifico. Si userà lo Yocto Project per creare un sistema operativo embedded di riferimento chiamato Poky.

Nota

  • Gli esempi in questo documento presuppongono l'uso di un sistema Linux nativo con una versione supportata di una distribuzione Ubuntu Linux. Se la macchina su cui si desidera utilizzare Yocto Project per creare un'immagine (Build Host) non è un sistema Linux nativo, è comunque possibile eseguire questi passaggi utilizzando un container OCI (tramite Docker o Podman).

  • È possibile utilizzare la versione 2 di Windows Subsystem for Linux (WSL 2) per configurare un host di compilazione con Windows 10 o versioni successive, Windows Server 2019 o versioni successive. Per ulteriori informazioni, consultare la sezione Setting Up to Use Windows Subsystem For Linux (WSL 2) nel Manuale di Sviluppo dei Task di Yocto Project.

Per maggiori informazioni concettuali o di base sullo Yocto Project, consultare la sezione Manuale Introduttivo e Concetti di Yocto Project.

Distribuzione Linux Compatibile

Assicurarsi che il proprio Build Host soddisfi i seguenti requisiti:

  • Almeno 140 GB di spazio libero su disco, ma una quantità maggiore consentirà di eseguire più build e di migliorare le prestazioni riutilizzando gli artefatti della build.

  • Almeno 32 GB di RAM, sebbene per massimizzare le prestazioni di compilazione si raccomandi vivamente un host di compilazione moderno con la massima quantità di RAM e il maggior numero possibile di core CPU.

  • Deve eseguire una distribuzione Linux supportata (ad esempio, versioni recenti di Fedora, openSUSE, CentOS, Debian o Ubuntu). Per un elenco delle distribuzioni Linux che supportano lo Yocto Project, consultare la sezione Distribuzioni Linux Supportate nel Manuale di Riferimento di Yocto Project. Per informazioni dettagliate sulla preparazione dell'host di compilazione, consultare la sezione Preparing the Build Host nel Manuale di Sviluppo dei Task di Yocto Project.

  • Assicurarsi che le seguenti utility abbiano i seguenti numeri di versione minimi:

    • Git 2.22.0 o superiore

    • tar 1.28 o superiore

    • Python 3.9.0 o superiore

    • gcc 10.1 o superiore

    • GNU make 4.0 o superiore

Se l'host di compilazione non soddisfa tutti i requisiti di versione sopra indicati, si possono adottare delle misure per preparare il sistema in modo da poter comunque utilizzare lo Yocto Project. Consultare la sezione Versioni richieste di Git, tar, Python, make e gcc nel Manuale di Riferimento di Yocto Project per ulteriori informazioni.

Pacchetti dell'Host di Build

Ecco i pacchetti necessari per creare un'immagine su un sistema senza interfaccia grafica con una distribuzione Linux Ubuntu o Debian supportata:

sudo apt-get install build-essential chrpath cpio debianutils diffstat file gawk gcc git iputils-ping libacl1 libcrypt-dev locales python3 python3-git python3-jinja2 python3-pexpect python3-pip python3-subunit socat texinfo unzip wget xz-utils zstd

È inoltre necessario assicurarsi che sia abilitata la localizzazione en_US.UTF-8:

$ locale --all-locales | grep en_US.utf8

In caso contrario, è possibile riconfigurare il pacchetto locales per aggiungerla (richiede una shell interattiva):

$ sudo dpkg-reconfigure locales

Nota

  • Se non si utilizza una shell interattiva, dpkg-reconfigure non funzionerà come previsto. Per aggiungere la localizzazione, è necessario modificare il file /etc/locale.gen per aggiungere/decommentare la localizzazione en_US.UTF-8. Un modo semplice per farlo come root è il seguente:

    $ echo "en_US.UTF-8 UTF-8" >> /etc/locale.gen
$ locale-gen

  • Se il sistema di build ha installato il pacchetto oss4-dev, si potrebbero riscontrare errori di compilazione di QEMU a causa dell'installazione, da parte del pacchetto, di una propria versione personalizzata di /usr/include/linux/soundcard.h sul sistema Debian. Se ci si imbatte in questa situazione, provare una di queste soluzioni:

    $ sudo apt build-dep qemu
$ sudo apt remove oss4-dev

Nota

Per i requisiti dei pacchetti host su tutte le distribuzioni Linux supportate, consultare la sezione Pacchetti Richiesti per l'Host di Build nel Manuale di Riferimento di Yocto Project.

Installazione e utilizzo di bitbake-setup

Dopo aver completato le istruzioni di configurazione per la macchina, si deve ottenere una copia del tool bitbake-setup per configurare la distribuzione di riferimento di Poky sul proprio build host. Utilizzare i seguenti comandi per installare il tool in un ambiente virtuale Python:

$ python3 -m venv --clear ./bitbake-setup-venv
$ . ./bitbake-setup-venv/bin/activate
$ pip install bitbake-setup

Nota

Il tool bitbake-setup è sviluppato e gestito nel repository di BitBake, quindi può essere utilizzato direttamente da lì:

$ git clone https://git.openembedded.org/bitbake ./bitbake
$ ./bitbake/bin/bitbake-setup ...

Configurare un ambiente di build con il seguente comando:

$ bitbake-setup init

Per default, questo creerà una directory principale nella directory corrente.

Se si preferisce configurare le build in una directory principale diversa, ad esempio $HOME/bitbake-builds, la si può impostare col comando bitbake-setup settings:

$ bitbake-setup settings set --global default top-dir-prefix $HOME

Nota

Usare bitbake-setup settings list per ottenere una panoramica delle impostazioni.

bitbake-setup init è un programma interattivo per default e chiederà di prendere alcune decisioni. A seconda delle risposte, l'output potrebbe differire dagli esempi seguenti.

  1. Scegliere una configurazione (ad esempio, poky-master):

    Available Configuration Templates:
1. oe-nodistro-master   OpenEmbedded - 'nodistro' basic configuration
2. oe-nodistro-blacksail  OpenEmbedded - 'nodistro' basic configuration, release 6.1 'blacksail' (supported until ...)
3. poky-master          Poky - The Yocto Project testing distribution configurations and hardware test platforms
4. poky-blacksail         Poky - The Yocto Project testing distribution configurations and hardware test platforms, release 6.1 'blacksail' (supported until ...)

Please select one of the above configurations by its number: 3

    A seconda della scelta precedente, potrebbero essere richieste nuove opzioni per specificare ulteriormente quale configurazione utilizzare. Ad esempio:

    Available bitbake configurations:
1. poky              Poky - The Yocto Project testing distribution
2. poky-with-sstate  Poky - The Yocto Project testing distribution with internet sstate acceleration. Use with caution as it requires a completely robust local network with sufficient bandwidth.

Please select one of the above bitbake configurations by its number: 1

  2. Scegliere una MACHINE target (ad esempio, qemux86-64):

    Target machines:
1. machine/qemux86-64     x86-64 system on QEMU
2. machine/qemuarm64      ARMv8 system on QEMU
3. machine/qemuriscv64    RISC-V system on QEMU
4. machine/genericarm64   Arm64 SystemReady IR/ES platforms
5. machine/genericx86-64  x86_64 (64-bit) PCs and servers

Please select one of the above options by its number: 1

  3. Scegliere una DISTRO (per esempio, poky):

    Target distributions:
1. distro/poky         Yocto Project Reference Distro
2. distro/poky-altcfg  Poky alternative with systemd as init manager
3. distro/poky-tiny    Poky alternative optimized for size

Please select one of the above options by its number: 1

  4. Scegliere un nome per la directory setup:

    Enter setup directory name: [poky-master]

    Premere Invio per lasciare il valore di default mostrato tra parentesi, oppure digitare un nome di directory personalizzato.

Nota

Se si preferisce eseguire il programma in modalità non interattiva, si può eseguire un comando come il seguente:

$ bitbake-setup init --non-interactive poky-master poky distro/poky machine/qemux86-64

Il comando init crea un nuovo Setup nella top directory. Il nome di default deriva dalla configurazione selezionata in precedenza.

Per le opzioni selezionate nell'esempio precedente, il nome sarebbe:

poky-master

Questa sarà la configurazione di esempio nelle sezioni seguenti.

Questa directory contiene:

  • La directory BitBake Build, chiamata build. Successivamente, al termine della compilazione, questa directory conterrà tutti i file creati durante il processo.

    Questa directory contiene anche un file README, che descrive la configurazione corrente e fornisce alcune istruzioni.

  • I layer, nella directory layers servono per la build della distribuzione di riferimento di Poky.

  • È presente anche una directory config, che rappresenta la configurazione corrente utilizzata per questo setup.

Nota

È inoltre possibile configurare manualmente la distribuzione di riferimento Poky. Per maggiori informazioni, consultare la sezione Setting Up the Poky Reference Distro Manually del Manuale di Sviluppo dei Task di Yocto Project.

Building dell'Immagine

Seguire i passaggi seguenti per compilare l'immagine. Il processo di compilazione (build) crea un'intera distribuzione Linux, inclusa la toolchain, a partire dai sorgenti.

Nota

  • Se si lavora dietro un firewall e l'host di build non è configurato per i proxy, si potrebbero riscontrare problemi con il processo di build durante il recupero del codice sorgente (ad esempio, errori di fetcher o errori di Git).

  • Se non si conoscono le impostazioni del proxy, consulta le risorse della propria infrastruttura di rete locale per ottenere queste informazioni. Un buon punto di partenza potrebbe essere anche controllare le impostazioni del browser web. Infine, si possono trovare maggiori informazioni nella pagina "Working Behind a Network Proxy" nello Yocto Project Wiki.

  1. Inizializzare il Build Environment: Eseguire lo script di configurazione dell'ambiente init-build-env nella directory BitBake build per configurare l'ambiente di build BitBake sul proprio host:

    $ source poky-master/build/init-build-env
Poky reference distro build

  2. Esaminare la Configurazione Corrente: Quando si configura l'ambiente di compilazione [build], un file di configurazione denominato toolcfg.conf diventa disponibile in una sottocartella conf/ della directory BitBake build. Questo file viene modificato automaticamente dal tool da riga di comando bitbake-config-build. Con questo tool, si elencano i frammenti di configurazione attualmente abilitati:

    $ bitbake-config-build list-fragments

    Per questa configurazione, l'impostazione di default prevede l'utilizzo di due Frammenti Nativi:

    • distro/poky imposta DISTRO a Poky (frammento distro/).

    • machine/qemux86-64 imposta MACHINE a qemux86-64 (frammento machine/).

    Questi valori dei frammenti corrispondono alle scelte effettuate durante l'esecuzione di bitbake-setup init.

    Nota

    Queste impostazioni configurano l'ambiente in modo simile a quanto precedentemente presente nel file di configurazione locale local.conf, che ora è in gran parte vuoto. Per configurare la build come in precedenza, consultare la sezione Setting Up the Poky Reference Distro Manually del Manuale di Sviluppo dei Task di Yocto Project.

    La configurazione attuale non consente all'utente root di effettuare l'accesso. Poiché può essere utile per lo sviluppo, è possibile abilitare il frammento core/yocto/root-login-with-empty-password:

    $ bitbake-config-build enable-fragment core/yocto/root-login-with-empty-password

    Nota

    È possibile velocizzare significativamente la compilazione e proteggersi dagli errori del fetcher utilizzando i mirror Cache di Shared State e abilitando Equivalenza degli Hash. Ciò è rilevante solo se la rete e il server utilizzati possono scaricare questi artefatti più velocemente di quanto sarebbe possibile crearli.

    Per utilizzare tali mirror, abilitare il frammento core/yocto/sstate-mirror-cdn:

    $ bitbake-config-build enable-fragment core/yocto/sstate-mirror-cdn

    Il server di equivalenza hash richiede il modulo Python websockets versione 9.1 o successiva. Debian GNU/Linux 12 (Bookworm) e versioni successive, Fedora, CentOS Stream 9 e versioni successive e Ubuntu 22.04 (LTS) e versioni successive dispongono tutte di un pacchetto sufficientemente recente. Le altre distribuzioni supportate devono ottenere il modulo da una fonte diversa dal proprio feed di pacchetti, ad esempio tramite pip. In alternativa, è possibile installare un tarball di Buildtools seguendo le istruzioni nella sezione Versioni richieste di Git, tar, Python, make e gcc del Manuale di Riferimento di Yocto Project.

  3. Avvio della Build: Continuare col seguente comando per creare un'immagine del sistema operativo per il target, che in questo esempio è core-image-sato:

    $ bitbake core-image-sato

    Per informazioni sull'utilizzo del comando bitbake, consulta la sezione BitBake nel Manuale Introduttivo e Concetti di Yocto Project, oppure consultare The BitBake Command nel Manuale Utente di BitBake.

  4. Simulare l'Immagine con QEMU: Una volta creata questa immagine, si può avviare QEMU, un "Quick EMUlator" incluso nello Yocto Project:

    $ runqemu snapshot

    Per ulteriori informazioni sull'esecuzione di QEMU, consultare il capitolo Using the Quick EMUlator (QEMU) nel Manuale di Sviluppo dei Task di Yocto Project.

  5. Uscita da QEMU: Per uscire da QEMU, cliccare sull'icona di spegnimento oppure digitare Ctrl-C nella finestra di trascrizione di QEMU da cui è stato avviato il programma.

Personalizzazione della Build per un Hardware Specifico

Finora, tutto ciò che si è fatto è stato creare rapidamente un'immagine adatta solo all'emulazione. Questa sezione mostra come personalizzare la build per un hardware specifico aggiungendo un layer hardware all'ambiente di sviluppo di Yocto Project.

In generale, i layer sono repository che contengono set correlati di istruzioni e configurazioni che indicano allo Yocto Project cosa fare. Isolare i metadati correlati in layer specifici per funzionalità facilita lo sviluppo modulare e semplifica il riutilizzo dei metadati del layer.

Nota

Per convenzione, i nomi dei layer iniziano con la stringa "meta-".

Seguire questi passaggi per aggiungere un layer BSP:

  1. Trovare un Layer: Sono disponibili molti layer BSP. Il layer index può essere utilizzato per trovare tali layer. Questo esempio aggiunge il layer BSP meta-raspberrypi.

    Innanzitutto, clonare il layer accanto agli altri layer:

    git clone -b blacksail https://git.yoctoproject.org/meta-raspberrypi ../layers/meta-raspberrypi

  2. Aggiungere il Layer al File di Configurazione dei Layer: Prima di poterlo utilizzare, si deve aggiungere il layer e le sue dipendenze al file build/conf/bblayers.conf, che si trova nella directory Build Directory (conf/).

    A tale scopo, si può utilizzare il comando bitbake-layers add-layer:

    $ bitbake-layers add-layer ../layers/meta-raspberrypi

    Si possono trovare maggiori informazioni sull'aggiunta di layer nella sezione Aggiungere un Layer Utilizzando lo Script bitbake-layers.

  3. Modificare la Configurazione per la Build su una Macchina Specifica: La variabile MACHINE è definita dal frammento machine/. In questo esempio, il layer meta-raspberrypi fornisce la macchina raspberrypi5, quindi impostiamola come MACHINE utilizzata per la compilazione con bitbake-config-build:

    $ bitbake-config-build enable-fragment machine/raspberrypi5

    Nota

    Per ulteriori informazioni sulla configurazione della compilazione, consultare il passaggio "Esaminare la Configurazione Corrente" precedente.

    La build raspberrypi5 dipende da un firmware non libero (https://github.com/RPi-Distro/firmware-nonfree) che include la licenza Synaptics. Per ulteriori informazioni, consultare il documento ipcompliance.md. Aggiungere il valore synaptics-killswitch alla variabile LICENSE_FLAGS_ACCEPTED, nel file build/conf/local.conf della directory di build:

    LICENSE_FLAGS_ACCEPTED = "synaptics-killswitch"

  4. Avviare la Build: La configurazione è ora impostata per la build su Raspberry Pi 5. Avviare nuovamente la build:

    $ bitbake core-image-sato

Il completamento di questi passaggi ha aggiunto il layer meta-raspberrypi all'ambiente [environment] di sviluppo di Yocto Project e lo ha configurato per la build per la macchina raspberrypi5.

Nota

I passaggi precedenti sono solo a scopo dimostrativo. Per tentare di creare un'immagine per la macchina raspberrypi5, si deve leggere il file README.md in meta-raspberrypi.

Creazione di un Proprio Layer Generico

Magari si ha un'applicazione o un insieme specifico di comportamenti da isolare. Si può creare un layer generico personalizzato utilizzando il comando bitbake-layers create-layer. Il tool automatizza la creazione dei layer impostando una sottocartella con un file di configurazione layer.conf, una sottocartella recipes-example contenente una ricetta example.bb, un file di licenza e un file README.

I seguenti comandi eseguono il tool per creare un layer denominato meta-mylayer:

$ bitbake-layers create-layer ../layers/meta-mylayer
NOTE: Starting bitbake server...
Add your new layer with 'bitbake-layers add-layer ../layers/meta-mylayer'

Nota

Per convenzione, i layer vengono posizionati uno accanto all'altro.

Per ulteriori informazioni sui layer e su come crearli, consultare la sezione Creating Your Own Layer nel Manuale di Sviluppo dei Task di Yocto Project.

Cosa Fare Ora?

Ora che c'è familiarità con lo Yocto Project, ci si potrebbe chiedere "E adesso?". Lo Yocto Project offre numerose fonti di informazione, tra cui il sito web, le pagine wiki e i manuali utente:

  • Sito Web: Il Sito Web di Yocto Project fornisce informazioni di base, le build più recenti, le ultime notizie, la documentazione completa per lo sviluppo e l'accesso a una ricca Community di Sviluppatori di Yocto Project a cui è possibile partecipare.

  • Seminario Video: I video Introduction to the Yocto Project and BitBake, Part 1 e Introduction to the Yocto Project and BitBake, Part 2 offrono un seminario video che introduce gli aspetti più importanti dello sviluppo di una distribuzione Linux embedded personalizzata con lo Yocto Project.

  • Manuale Introduttivo e Concetti di Yocto Project: Il documento Manuale Introduttivo e Concetti di Yocto Project è un ottimo punto di partenza per conoscere lo Yocto Project. Questo manuale introduce lo Yocto Project e il suo ambiente di sviluppo. Il manuale fornisce anche informazioni concettuali su vari aspetti di Yocto Project.

  • Wiki di Yocto Project: Lo Yocto Project Wiki fornisce ulteriori informazioni su come iniziare con lo Yocto Project, informazioni sulle release, pianificazione del progetto e informazioni sul controllo qualità.

  • Mailing List di Yocto Project: Le mailing list correlate offrono un forum per discussioni, invio di patch e annunci. Sono presenti diverse mailing list, raggruppate per argomento. Consultare la sezione Mailing lists nel Manuale di Riferimento di Yocto Project per un elenco completo delle mailing list di Yocto Project.

  • Elenco Completo di Link e Altra Documentazione: La sezione Links and Related Documentation nel Manuale di Riferimento di Yocto Project fornisce un elenco completo di tutti i link correlati e altra documentazione per gli utenti.
