4 Apportare Modifiche a un Componente

I contributi a Yocto Project e a OpenEmbedded sono benvenuti. Dato che il sistema è estremamente configurabile e flessibile, sappiamo che gli sviluppatori vorranno estenderlo, configurarlo o ottimizzarlo per le loro esigenze specifiche.

4.1 Contribuire tramite mailing list: Perché non utilizzare flussi di lavoro basati sul web?

Sia Yocto Project che OpenEmbedded hanno molti componenti chiave che vengono mantenuti tramite patch inviate tramite mailing list. Sappiamo che questo approccio può sembrare un po' antiquato, considerando che sono disponibili altri flussi di lavoro basati su tecnologie web come GitHub, GitLab e altri. Poiché ci viene spesso posta questa domanda, abbiamo deciso di documentare i motivi per cui utilizziamo le mailing list.

Un fattore importante è che diamo valore alla revisione paritaria. Quando viene proposta una modifica a molti dei componenti principali del progetto, è utile che venga esaminata da più persone. Sebbene la decisione finale sull'accettazione o il rifiuto di una patch spetti a un singolo manutentore, la revisione viene effettuata da più persone e l'identità di chi la effettua è probabilmente sconosciuta al manutentore. Spesso è il revisore a sorpresa a individuare i problemi più interessanti!

Questo contrasta con il flusso di lavoro in stile "GitHub", dove la revisione viene effettuata solo dal manutentore o richiesta specificamente a persone designate. Crediamo che questo tipo di revisione tra pari apporti un valore significativo al codice sorgente e che abbandonare le mailing list sarebbe dannoso per il nostro codice.

Dobbiamo anche riconoscere che molti dei nostri sviluppatori sono abituati a questo flusso di lavoro tramite mailing list e lo utilizzano da anni, con strumenti e processi creati appositamente per questo scopo. Abbandonare questo sistema comporterebbe la perdita di persone chiave dal progetto, il che sarebbe a sua volta dannoso.

I progetti sono perfettamente consapevoli che i potenziali nuovi collaboratori trovano l'approccio tramite mailing list scoraggiante e preferirebbero un'interfaccia grafica basata sul web. Poiché non crediamo che questa soluzione possa funzionare per noi, il progetto si propone di rendere disponibile patchwork per aiutare a monitorare lo stato delle patch e sta anche valutando come gli strumenti possano fornire un feedback più completo agli utenti sullo stato delle patch. Stiamo cercando di migliorare strumenti come patchtest per testare i contributi degli utenti prima che vengano inviati alle mailing list e anche di documentare meglio come utilizzare tali flussi di lavoro, poiché riconosciamo che, mentre questo era di dominio pubblico dieci anni fa, potrebbe non esserlo più.

4.2 Preparazione delle Modifiche per l'Invio

4.2.1 Configurazione di Git

La prima cosa da fare è installare i pacchetti Git. Ecco un esempio su Debian e Ubuntu:

sudo apt install git-core git-email

Successivamente, è necessario impostare un nome e un indirizzo e-mail che Git utilizzerà per identificare i commit:

git config --global user.name "Ada Lovelace"
git config --global user.email "ada.lovelace@gmail.com"

Per default, Git aggiunge una riga di firma alla fine delle patch contenente la versione di Git. Si consiglia di rimuoverla in quanto non aggiunge informazioni utili.

Rimuoverla con il seguente comando:

git config --global format.signature ""

4.2.2 Clonare il repository Git del componente da modificare

Dopo aver identificato il componente da modificare come descritto nella sezione "Identificazione del Componente", clonare il repository Git corrispondente. Ecco un esempio per OpenEmbedded-Core:

git clone https://git.openembedded.org/openembedded-core
cd openembedded-core

4.2.3 Creare un nuovo branch

Poi, si crea un nuovo branch nel proprio repository Git locale per le modifiche, partendo dal branch di riferimento nel repository upstream (spesso chiamato master):

$ git checkout <ref-branch>
$ git checkout -b my-changes

Se si ha un set di modifiche completamente indipendenti da inviare, si dovrebbe addirittura creare un branch per ogni set.

4.2.4 Implementare e confermare le modifiche

In ogni branch, si deve raggruppare le proprie modifiche in piccole parti controllate e isolate. Mantenere le modifiche piccole e isolate facilita la revisione, semplificare le operazioni di merge/rebase e mantenere pulita la cronologia delle modifiche, qualora qualcuno dovesse farvi riferimento in futuro.

A questo scopo, si deve creare un commit Git per ogni modifica, corrispondente a ciascuna delle patch che si invierà. Consultare ulteriori indicazioni nella documentazione del kernel Linux, se necessario.

Ad esempio, quando si intende aggiungere più nuove ricette, ciascuna ricetta deve essere aggiunta in un commit separato. Per gli aggiornamenti di ricette esistenti, la versione precedente dovrebbe in genere essere eliminata come parte dello stesso commit per aggiungere la versione aggiornata.

  1. Staging delle Modifiche: Aggiungere le modifiche all'area di staging utilizzando il comando git add su ogni file modificato. Per aggiungere tutti i file modificati all'area di staging, si può anche utilizzare il comando git add -A.

  2. Commit delle Modifiche: In questa fase si possono creare commit separati. Per ogni commit da creare, si utilizza il comando git commit -s specificando i file o le directory da includere nel commit:

    $ git commit -s file1 file2 dir1 dir2 ...

    Per includere tutti i file aggiunti all'area di staging:

    $ git commit -sa

    1. L'opzione -s di git commit aggiunge la riga "Signed-off-by:" al messaggio di commit. Lo stesso requisito vale per chi contribuisce al kernel Linux. L'aggiunta di tale riga indica che l'utente che invia la patch ha accettato il Developer's Certificate of Origin 1.1 come segue:

      Developer's Certificate of Origin 1.1

By making a contribution to this project, I certify that:

(a) The contribution was created in whole or in part by me and I
    have the right to submit it under the open source license
    indicated in the file; or

(b) The contribution is based upon previous work that, to the best
    of my knowledge, is covered under an appropriate open source
    license and I have the right under that license to submit that
    work with modifications, whether created in whole or in part
    by me, under the same open source license (unless I am
    permitted to submit under a different license), as indicated
    in the file; or

(c) The contribution was provided directly to me by some other
    person who certified (a), (b) or (c) and I have not modified
    it.

(d) I understand and agree that this project and the contribution
    are public and that a record of the contribution (including all
    personal information I submit with it, including my sign-off) is
    maintained indefinitely and may be redistributed consistent with
    this project or the open source license(s) involved.

    2. Fornire un breve riepilogo della modifica su una sola riga e, se sono necessarie ulteriori spiegazioni, aggiungere maggiori dettagli nella descrizione del commit. Questo riepilogo è generalmente visibile nella "shortlist" delle modifiche. Pertanto, fornire una descrizione breve e concisa che riassuma la modifica è utile quando si visualizza un elenco di molti commit. Anteporre a questa breve descrizione il nome della ricetta (se si modifica una ricetta) o il path abbreviato del file modificato.

      Nota

      Per trovare un prefisso adatto per il riepilogo del commit, un buon consiglio è quello di cercare i prefissi utilizzati nei commit precedenti che hanno interessato gli stessi file o directory:

      git log --oneline <paths>

    3. Nella descrizione del commit, fornire informazioni dettagliate che descrivano cosa è stato modificato, perché è stato fatto e l'approccio che utilizzato. Potrebbe anche essere utile menzionare come è stata testato la modifica. Fornire il maggior numero possibile di dettagli nella descrizione del commit.

      Nota

      Se il riepilogo di una sola riga è sufficiente a descrivere una modifica semplice, la descrizione del commit può essere lasciata vuota.

    4. Se la modifica risolve un bug o un problema specifico associato a un ID di tracciamento dei bug, includere un riferimento a tale ID nel corpo del messaggio di commit. Ad esempio, Yocto Project utilizza una convenzione specifica per i riferimenti ai bug: qualsiasi commit che risolve un bug specifico dovrebbe utilizzare il seguente formato per il corpo del messaggio di commit. Assicurarsi di utilizzare l'ID di tracciamento del bug effettivo di Bugzilla per bug-id:

      single-line summary of change

Fixes [YOCTO #bug-id]

detailed description of change

    5. Se altre persone hanno partecipato a questa patch, aggiungere alcuni tag alla descrizione del commit per dare credito agli altri contributori alla modifica:

      • Reported-by: nome e indirizzo email della persona che ha segnalato un bug che il commit sta cercando di correggere. Questa è una buona pratica per incoraggiare gli utenti a continuare a segnalare bug e far loro sapere che le loro segnalazioni vengono prese in considerazione.

      • Suggested-by: nome e indirizzo email della persona a cui attribuire il merito dell'idea di apportare la modifica.

      • Tested-by, Reviewed-by: nome e indirizzo email delle persone che hanno testato le modifiche o revisionato il codice. Questi campi vengono solitamente aggiunti dal manutentore che accetta una patch, oppure in proprio se si è il mittente delle patch a dei revisori preliminari o se si sta inviando nuovamente una patch non modificata come parte di una nuova iterazione della propria serie di patch.

      • Cc: nome e indirizzo email delle persone a cui inviare una copia delle modifiche. Questo campo verrà utilizzato da git send-email.

      Per, ulteriori informazioni sull'utilizzo di questi tag consultare la documentazione del kernel Linux.

      Nota

      È possibile modificare un messaggio di commit Git esistente per aggiungere i tag mancanti per i collaboratori con il comando git commit --amend.

4.2.5 Verificare le modifiche

Per ogni contributo che apporti, si devono anche testare le modifiche. A tal fine, Yocto Project offre diversi tipi di test. Questi test coprono aree diverse e la loro fattibilità dipende dalle modifiche che apportata. Ad esempio, eseguire:

  • Per modifiche che interessano l'ambiente di build:

    • bitbake-selftest: per le modifiche all'interno di BitBake

    • oe-selftest: per testare combinazioni di esecuzioni di BitBake

    • oe-build-perf-test: per testare le prestazioni di scenari di compilazione comuni

  • Per modifiche a una ricetta:

    • ptest: esegue test specifici del pacchetto, se presenti

    • testimage: creare un'immagine, avviarla ed eseguirci i test

    • Se applicabile, eseguire anche le build delle varianti native e nativesdk

  • Per modifiche relative all'SDK:

    • testsdk: per compilare, installare ed eseguire test su un SDK

    • testsdk_ext: per compilare, installare ed eseguire test su un SDK esteso

Si noti che questo elenco fornisce solo suggerimenti e non è esaustivo. Maggiori dettagli sono disponibili qui: Yocto Project Tests --- Types of Testing Overview.

4.3 Creazione di Patch

Ecco la procedura generale per creare patch da inviare via email:

  1. Descrivere le Modifiche nel Proprio Branch: Se il branch contiene più di un commit, si consiglia di allegare una lettera di presentazione che descriva la serie di patch inviata.

    A questo scopo, una buona soluzione è quella di salvare il contenuto della lettera di presentazione direttamente nel branch:

    git branch --edit-description

    Questo aprirà un editor di testo in cui si potrà inserire la descrizione delle modifiche. Questa descrizione può essere aggiornata quando necessario e verrà utilizzata da Git per creare la lettera di presentazione insieme alle patch.

    Si consiglia di iniziare la descrizione con un titolo che fungerà da oggetto per la lettera di presentazione.

  2. Generare le Patch per il Branch: Il comando git format-patch genererà i file patch per ogni commit del branch. È necessario specificare il branch di riferimento da cui parte il branch.

    Se il branch non necessitava di una descrizione nel passaggio precedente:

    $ git format-patch <ref-branch>

    Se invece è stata inserita una descrizione per il branch, si dovrà generare anche una lettera di presentazione:

    $ git format-patch --cover-letter --cover-from-description=auto <ref-branch>

    Dopo l'esecuzione del comando, la directory corrente conterrà file .patch numerati per i commit del branch. Se c'è una lettera di presentazione, la si troverà nel file 0000-cover-letter.patch.

    Nota

    L'opzione --cover-from-description=auto fa sì che git format-patch utilizzi il primo paragrafo della descrizione del branch come titolo della lettera di presentazione. Un'altra possibilità, più facile da ricordare, è quella di passare solo l'opzione --cover-letter, ma si dovrà modificare manualmente l'oggetto ogni volta che si generano le patch.

    Consultare la pagina del manuale di git per maggiori dettagli.

  3. Rivedere Ogni File di Patch: Questa revisione finale delle patch prima dell'invio consente spesso di visualizzare le modifiche da una prospettiva diversa e di individuare difetti come errori di battitura, problemi di spaziatura o di riga, o persino file che non si intendevano modificare. Questa revisione dovrebbe includere anche la patch della lettera di presentazione.

    Se necessario, rielaborare i propri commit come descritto in "Considerazioni sulla Revisione delle Patch".

4.4 Validazione delle Patch con Patchtest

patchtest è disponibile in openembedded-core come strumento per garantire che le patch siano ben formattate e contengano informazioni importanti per la manutenzione, come la presenza di Signed-off-by. Si noti che patchtest non eseguirà alcun test funzionale delle modifiche. Attualmente, supporta solo il test delle patch per i branch di openembedded-core. Per configurarlo, procedere come segue:

pip install -r meta/lib/patchtest/requirements.txt
source oe-init-build-env
bitbake-layers add-layer ../meta-selftest

Una volta completati questi passaggi e generati i file delle patch, è possibile eseguire patchtest in questo modo:

patchtest --patch <patch_name>

In alternativa, se si desidera che patchtest esegua un'iterazione e testi più patch memorizzate in una directory, è possibile utilizzare:

patchtest --directory <directory_name>

Per default, patchtest utilizza i path dei file dei propri moduli per determinare il repository e la suite di test da utilizzare per il controllo delle patch. Per testare le patch su un repository diverso da openembedded-core e/o utilizzare un set di test diverso, si possono usare i flag --repodir e --testdir:

patchtest --patch <patch_name> --repodir <path/to/repo> --testdir <path/to/testdir>

Infine, si tenga presente che patchtest è progettato per testare le patch in modo indipendente, quindi se le patch devono essere applicate sopra le modifiche apportate da patch precedenti in una serie, è possibile che patchtest segnali falsi errori relativi al test "merge on head".

L'utilizzo di patchtest in questo modo fornisce un controllo finale sulla qualità complessiva delle modifiche prima che vengano inviate per la revisione da parte dei manutentori.

4.5 Invio delle Patch via Email

4.5.1 Utilizzo di Git per Inviare le Patch

Per inviare patch via email, è fondamentale che non contengano spazi bianchi o formattazione HTML, né introdotti manualmente né dal client di posta. Il manutentore che riceve le patch deve essere in grado di salvarle e applicarle direttamente dalle email, utilizzando il comando git am.

L'utilizzo del comando git send-email è l'unico modo sicuro per inviare patch via email, poiché elimina il rischio di compromettere la formattazione degli spazi bianchi nel corpo del messaggio, cosa che può accadere utilizzando il proprio client di posta. Inoltre, includerà correttamente le patch come inline attachments, cosa non facile da fare con i client di posta elettronica standard senza mandare a capo il testo. Utilizzando il normale client di posta elettronica e condividendo le patch come allegati, i revisori non sarebbero in grado di citare sezioni specifiche delle modifiche e di commentarle.

4.5.2 Configurazione di Git per l'Invio di Email

Il comando git send-email può inviare email utilizzando un Mail Transport Agent (MTA) locale o remoto, come msmtp, sendmail, oppure tramite una configurazione SMTP diretta nel file ~/.gitconfig di Git.

Ecco le impostazioni per consentire aHere are the settings for letting git send-email di inviare email tramite il tuo server SMTP abituale, utilizzando un account Google Mail come esempio:

git config --global sendemail.smtpserver smtp.gmail.com
git config --global sendemail.smtpserverport 587
git config --global sendemail.smtpencryption tls
git config --global sendemail.smtpuser ada.lovelace@gmail.com
git config --global sendemail.smtppass = XXXXXXXX

Queste impostazioni appariranno nel file .gitconfig nella propria directory home.

Se non si può utilizzare né un MTA locale né SMTP, si deve utilizzare un client di posta elettronica che non modifichi il messaggio (invertendo gli spazi in tabulazioni, mandando a capo le righe, ecc.). Un buon client di posta per questo scopo è Pine (o Alpine) o Mutt. Per ulteriori informazioni sui client compatibili, consultare la sezione Informazioni sui client di posta elettronica per Linux nei sorgenti del kernel Linux.

Se si utilizzano client di questo tipo, è sufficiente includere la patch nel corpo dell'e-mail.

4.5.3 Trovare una Mailing List Adatta

È necessario inviare le patch alla mailing list appropriata affinché possano essere esaminate dai collaboratori competenti e integrate dal manutentore di riferimento. La mailing list specifica da utilizzare dipende dalla posizione del codice che si sta modificando.

Se qualcuno ha dubbi su una qualsiasi delle patch, di solito li esprime tramite la mailing list. Se le patch non ricevono recensioni negative, il manutentore del layer interessato in genere le prende, le testa e, in base all'esito positivo dei test, le integra.

In generale, ogni componente (ad esempio, un layer) dovrebbe avere un file README che indica dove inviare le modifiche e quale procedura seguire.

Se si intende inviare una nuova ricetta che non rientra né in OpenEmbedded-Core (OE-Core), né in meta-openembedded, è necessario cercare un layer adatto su https://layers.openembedded.org. Se si prevedono ricette simili, si può consultare la sezione Creating Your Own Layer.

In caso di dubbi, si prega di chiedere sulla mailing list generale yocto o sulla mailing list openembedded-devel.

4.5.4 Iscrizione alla Mailing List

Dopo aver individuato la mailing list più adatta, si dovrà iscriversi se non già fatto.

Se si tenta di inviare patch a una lista a cui non si è iscritti, l'email verrà restituita come non recapitata.

Tuttavia, se non si desidera ricevere tutti i messaggi inviati a una mailing list, si può impostare l'iscrizione su "no email". Si rimarrà comunque iscritti e si potranno inviare messaggi, ma non si riceveranno email. Se qualcuno risponde al messaggio, il suo client di posta elettronica includerà automaticamente il proprio indirizzo email nella conversazione.

In ogni caso, si potrà accedere ai nuovi messaggi negli archivi delle mailing list, tramite un browser web oppure, per le liste archiviate su https://lore.kernel.org, tramite un feed di newsgroup individuale o un repository Git.

4.5.5 Invio delle Patch via Email

A questo punto, si è pronti per inviare le patch via email. Ecco l'utilizzo tipico di git send-email:

git send-email --to <mailing-list-address> *.patch

Successivamente, rivedere attentamente ogni riga dell'oggetto e l'elenco dei destinatari, quindi consentire al comando di inviare ogni messaggio.

Si noterà che git send-email invierà automaticamente una copia a tutti i destinatari indicati nei tag di commit, come Signed-off-by o Reported-by.

Nel caso in cui si stia inviando patch per meta-openembedded o per qualsiasi altro layer diverso da openembedded-core, aggiungere il prefisso appropriato in modo che sia chiaro a quale layer deve essere applicata la patch:

git format-patch --subject-prefix="meta-oe][PATCH" ...

Nota

È possibile inviare patch anche senza generarle prima. Tuttavia, assicurarsi di aver esaminato attentamente le modifiche, perché git send-email mostrerà solo le righe del titolo di ciascuna patch.

Ecco un comando utilizzabile se è stata cambiata una sola patch nel proprio branch:

git send-email --to <mailing-list-address> -1

Se si hanno più patch e una lettera di presentazione, si possono inviare le patch per tutti i commit tra il branch di riferimento e la fine del proprio branch:

git send-email --cover-letter --cover-from-description=auto --to <mailing-list-address> -M <ref-branch>

Consultare la pagina del manuale di send-email di git per maggiori dettagli.

4.5.6 Risoluzione dei Problemi Relativi alle Email

4.5.6.1 Correzione dell'Identità del Mittente

Abbiamo un problema frequente con i collaboratori le cui patch vengono ricevute tramite un campo From che non corrisponde alle informazioni Signed-off-by. Ecco un esempio tipico per chi invia da un nome di dominio con https://en.wikipedia.org/wiki/DMARC:

From: "Linus Torvalds via lists.openembedded.org <linus.torvalds=kernel.org@lists.openembedded.org>"

Questo campo From viene utilizzato da git am per ricreare i commit con il nome dell'autore corretto. Quanto segue garantirà che le e-mail abbiano un campo From aggiuntivo all'inizio del corpo dell'e-mail, in modo che i manutentori che accettano le patch non debbano correggere manualmente le informazioni sull'autore del commit:

git config --global sendemail.from "linus.torvalds@kernel.org"

Il campo sendemail.from deve corrispondere all'impostazione user.email, che appare nella riga Signed-off-by dei commit.

4.5.7 Ottimizzazione dell'utilizzo di "git send-email"

Per risparmiare tempo ed evitare di dover ricordare le opzioni corrette da utilizzare con git send-email, si possono utilizzare le impostazioni di configurazione di Git.

  • Per impostare l'indirizzo corretto della mailing list per un determinato repository:

    git config --local sendemail.to openembedded-devel@lists.openembedded.org

  • Se la mailing list richiede un prefisso per l'oggetto del layer (questo funziona solo se il repository contiene un solo layer):

    git config --local format.subjectprefix "meta-something][PATCH"

4.6 Uso di Script per il Push di una Modifica Upstream e il Pull Request

Per serie di patch più ampie, è preferibile inviare una pull request che includa non solo la patch, ma anche un puntatore a un branch da cui prelevare le modifiche. Questo comporta la creazione di un branch locale per le modifiche, il push di questo branch in un repository accessibile e quindi l'utilizzo degli script create-pull-request e send-pull-request di openembedded-core per creare e inviare una serie di patch con un link al branch per la revisione.

Seguire questa procedura per inviare una modifica a un repository Git "contrib" upstream dopo aver seguito i passaggi descritti in "Preparazione delle Modifiche per l'Invio":

Nota

Si possono trovare informazioni generali su Git e su come inviare una modifica upstream nel Git Community Book.

  1. Richiedere l'Accesso in Push a un Repository "Upstream" Contrib: Inviare un'email a helpdesk@yoctoproject.org:

    • Allegare la propria chiave pubblica SSH, che di solito si chiama id_rsa.pub.. Se non se ne possiede una, generala eseguendo ssh-keygen -t rsa -b 4096 -C "your_email@example.com".

    • Elencare i repository a cui si intende contribuire.

    • Includere il prefisso del branch che si preferisce per i repository -contrib.

  2. Eseguire il Push dei Commit al Repository "Contrib" Upstream: Eseguire il push delle modifiche a quel repository:

    $ git push upstream_remote_repo local_branch_name

    Ad esempio, supponiamo che si abbiano i permessi per eseguire il push nel repository upstream meta-intel-contrib e che si stia lavorando in un branch locale chiamato your_name/README. Il seguente comando invia i propri commit locali al repository upstream meta-intel-contrib e li inserisce in un branch denominato your_name/README:

    $ git push meta-intel-contrib your_name/README

  3. Determinare a Chi Notificare: Determinare il manutentore o la mailing list a cui notificare la modifica.

    Prima di inviare qualsiasi modifica, ci si deve accertare di chi sia il manutentore o a quale mailing list inviare la notifica. Utilizzare uno di questi metodi per scoprirlo:

    • File di Manutenzione: Esaminare il file maintainers.inc, che si trova in OpenEmbedded-Core (OE-Core) in meta/conf/distro/include, per vedere chi è responsabile del codice.

    • Ricercare per File: Utilizzando Git, è possibile inserire il seguente comando per visualizzare un breve elenco di tutti i commit relativi a un file specifico:

      git shortlog -- filename

      Basta fornire il nome del file di interesse. Le informazioni restituite non sono ordinate cronologicamente, ma includono un elenco di tutti coloro che hanno effettuato commit, raggruppati per nome. Dall'elenco, è possibile vedere chi è responsabile della maggior parte delle modifiche al file.

    • Trovare la Mailing List da Utilizzare: Consultare la sezione "Trovare una Mailing List Adatta" sopra.

  4. Creare una Pull Request: Notificare al manutentore o alla mailing list di aver inviato una modifica creando una pull request.

    Yocto Project fornisce due script che consentono di generare e inviare facilmente pull request a Yocto Project. Questi script sono create-pull-request e send-pull-request. Si trovano nella directory scripts in OpenEmbedded-Core (OE-Core).

    L'utilizzo di questi script formatta correttamente le richieste senza introdurre spazi bianchi o formattazione HTML. Il manutentore che riceve le patch, direttamente o tramite la mailing list, deve essere in grado di salvarle e applicarle direttamente dalle e-mail. Questo è il metodo preferito per l'invio delle patch.

    Innanzitutto, si crea la pull request. Ad esempio, il seguente comando esegue lo script, specifica il repository upstream nella directory contrib in cui si è effettuato il push della modifica e fornisce un oggetto nei file patch creati:

    $ ./scripts/create-pull-request -u meta-intel-contrib -s "Updated Manual Section Reference in README"

    L'esecuzione di questo script crea file *.patch in una cartella denominata pull-PID nella directory corrente. Uno dei file patch è una lettera di presentazione.

    Prima di eseguire lo script send-pull-request, è necessario modificare la patch della lettera di presentazione per inserire le informazioni sulla modifica. Dopo aver modificato la lettera di presentazione, si invia la pull request. Ad esempio, il seguente comando esegue lo script e specifica la directory della patch e l'indirizzo email. In questo esempio, l'indirizzo email è quello di una mailing list:

    $ ./scripts/send-pull-request -p ~/meta-intel/pull-10565 -t meta-intel@lists.yoctoproject.org

    È necessario seguire le istruzioni visualizzate, poiché lo script è interattivo.

    Nota

    Per ricevere assistenza sull'utilizzo di questi script, è sufficiente specificare l'argomento -h come segue:

    $ ./scripts/create-pull-request -h
$ ./scripts/send-pull-request -h

4.7 Invio di Modifiche ai Branch di Rilascio Stabili

La procedura per proporre modifiche a un branch stabile di Yocto Project differisce dai passaggi descritti sopra. Le modifiche a un branch stabile devono risolvere bug o CVE identificati e devono essere apportate con attenzione per evitare il rischio di introdurre nuovi bug o compromettere la compatibilità con le versioni precedenti. In genere, le correzioni di bug devono essere già state accettate nel branch master prima di poter essere retroportate a un branch stabile, a meno che il bug in questione non influisca sul branch master o la correzione sul branch master non sia adatta al "backporting" [retroportazione].

L'elenco dei branch stabili, insieme allo stato e al manutentore di ciascun branch, è disponibile nella pagina Releases.

Nota

Le patch inviate per un branch stabile devono essere modifiche isolate, leggibili e comprensibili. Le correzioni per CVE o altri problemi di elevata complessità, che consistono in un numero elevato di commit e/o un numero elevato di righe modificate, difficilmente verranno accettate a causa delle difficoltà che comportano in termini di manutenibilità e scalabilità.

In genere, le modifiche non vengono accettate per i branch contrassegnati come End-Of-Life (EOL).

Tenendo presente questo, i passaggi per inviare una modifica per un branch stabile sono i seguenti:

  1. Identificare il bug o la CVE da correggere: Queste informazioni devono essere raccolte in modo da poter essere incluse nella richiesta di modifica.

    Consultare Verifica delle Vulnerabilità per i dettagli sul tracciamento delle CVE.

  2. Verificare se la correzione è già presente nel branch master: Questo consentirà di individuare il path più semplice per l'integrazione della correzione nel branch stabile.

    1. Se la correzione è presente nel branch master, inviare una richiesta di backport via email: È necessario inviare un'e-mail al manutentore del branch stabile di riferimento e alla mailing list con i dettagli del bug o della CVE da correggere, l'hash del commit sul branch master che risolve il problema e i branch stabili su cui si desidera che la correzione venga retroportata.

    2. Se la correzione non è presente nel branch master, inviarla prima al branch master: Questo garantirà che la correzione superi i normali processi di revisione e test delle patch del progetto prima di essere accettata. Inoltre, assicurerà che non rimangano bug irrisolti nel branch master stesso. Una volta che la correzione è stata accettata nel branch master, è possibile inviare una richiesta di backport come descritto sopra.

    3. Se la correzione non è adatta al branch master, si invia una patch direttamente al branch stabile: Questo metodo dovrebbe essere considerato come ultima risorsa. In genere è necessario quando il branch master utilizza una versione più recente del software che include una correzione upstream per il problema o quando il problema è stato risolto sul branch master in un modo che introduce modifiche incompatibili con le versioni precedenti. In questo caso, si seguono i passaggi descritti in "Preparazione delle Modifiche per l'Invio" e nelle sezioni seguenti, ma si modifica l'oggetto dell'e-mail della patch includendo il nome del branch stabile a cui si sta indirizzando la patch. Questo può essere fatto utilizzando l'argomento --subject-prefix di git format-patch, ad esempio per inviare una patch al branch "wrynose" utilizzare:

      git format-patch --subject-prefix='wrynose][PATCH' ...

4.8 Considerazioni sulla Revisione delle Patch

Si potrebbe ricevere feedback sulle patch inviate da altri membri della community o dal servizio automatico di test delle patch. Se vengono identificati problemi nelle proprie patch, di solito è necessario risolverli prima che le patch vengano accettate nel progetto. In questo caso, si devono rivedere i propri commit in base al feedback e inviare una versione aggiornata alla mailing list pertinente.

In ogni caso, non correggere mai i problemi segnalati modificandoli in nuovi commit sul proprio branch. Creare sempre una nuova serie di commit senza i problemi segnalati.

Nota

È buona norma inviare una copia ai revisori che hanno fornito feedback sulla versione precedente della patch. Ciò avviene aggiungendo un tag CC alla descrizione del commit:

CC: William Shakespeare <bill@yoctoproject.org>

Una singola patch può essere modificata usando git commit --amend, e più patch possono essere facilmente rielaborate e riordinate tramite un rebase interattivo di Git:

git rebase -i <ref-branch>

Consultare questo tutorial this tutorial per una guida pratica sull'utilizzo del rebase interattivo di Git.

Si deve anche modificare il tag [PATCH] nell'oggetto dell'email quando si invia la patch rivista per contrassegnare la nuova iterazione come [PATCH v2], [PATCH v3], ecc. a seconda dei casi. Questo può essere fatto passando l'argomento -v a git format-patch con un numero di versione:

git format-patch -v2 <ref-branch>

Dopo aver generato patch aggiornate (v2, v3 e così via) tramite git format-patch, idealmente gli sviluppatori dovrebbero aggiungere un changelog della versione della patch a ciascuna patch, che descriva le modifiche apportate tra le varie revisioni. Aggiungere il changelog della versione della patch dopo il marcatore --- nella patch, indicando che queste informazioni fanno parte della patch stessa, ma non sono adatte per essere incluse nel messaggio di commit (ovvero nella cronologia di Git). Fornire un changelog della versione della patch facilita la comprensione sintetica delle modifiche apportate in tutte le versioni della patch da parte di manutentori e revisori, senza dover consultare fonti di informazione alternative, come ad esempio la ricerca tra i messaggi di una mailing list. Ad esempio:

<patch title>

<commit message>

<Signed-off-by/other trailers>
---
changes in v4:
- provide a clearer commit message
- fix spelling mistakes

changes in v3:
- replace func() to use other_func() instead

changes in v2:
- this patch was added in v2
---
<diffstat output>

<unified diff>

Infine, si devono testare anche le modifiche apportate. In particolare, non ci si limiti a modificare il file di patch generato da git format-patch e a inviarlo nuovamente.

4.9 Monitoraggio dello Stato delle Patch

Yocto Project utilizza un'istanza di Patchwork per monitorare lo stato delle patch inviate alle varie mailing list e per supportare il test automatico delle patch. Ogni patch inviata viene controllata per individuare errori comuni e deviazioni dal formato previsto, e gli autori vengono avvisati da patchtest se vengono rilevati tali errori. Questo processo contribuisce a ridurre il carico di lavoro dei manutentori per la revisione delle patch.

Nota

Questo sistema non è perfetto e a volte le modifiche possono andare perse. È opportuno chiedere informazioni sullo stato di una patch o di una modifica se questa è rimasta inattiva per un po' di tempo senza alcun feedback.

Se le patch non hanno ricevuto alcun feedback per alcuni giorni, potrebbero essere già state integrate. Si può eseguire git pull branch per verificarlo. Da tener presente che molti, se non la maggior parte, dei manutentori dei layer non inviano email di conferma quando accettano una patch. In alternativa, se non c'è risposta o integrazione dopo alcuni giorni, la patch potrebbe essere stata trascurata o i revisori appropriati potrebbero non essere disponibili al momento. È quindi perfettamente lecito rispondere personalmente con un promemoria per richiedere un feedback.

Nota

Le revisioni delle patch per gli aggiornamenti di funzionalità e ricette potrebbero subire ritardi durante un blocco delle funzionalità, poiché questo tipo di patch non viene unito in quel periodo; potrebbe essere necessario attendere la revoca del blocco.

I manutentori utilizzano comunemente anche i branch -next per testare le modifiche prima di unire le patch. Pertanto, è possibile farsi un'idea dello stato di una patch in base al fatto che sia stata unita o meno a uno di questi branch. I branch di test comunemente utilizzati per OpenEmbedded-Core sono i seguenti:

  • openembedded-core "master-next" branch: Questo branch fa parte del repository openembedded-core e contiene le modifiche proposte ai metadati del core.

  • bitbake "master-next" branch: Questo branch fa parte del repository bitbake e contiene modifiche a BitBake.

  • meta-yocto "master-next" branch: Questo branch fa parte del repository meta-yocto e contiene le modifiche proposte per meta-yocto.

Analogamente, i branch stabili gestiti dal progetto possono avere corrispondenti branch -next che raccolgono le modifiche proposte. Ad esempio, i branch blacksail-next e wrynose-next nei repository "openembedded-core" e "meta-yocto".

Altri layer possono avere branch di test simili, ma non esiste un requisito o uno standard formale in merito, quindi si deve di consultare la documentazione dei layer a cui si sta contribuendo.

4.10 Accettazione del Codice Generato dall'IA

Yocto Project e OpenEmbedded seguono le linee guida della Linux Foundation per quanto riguarda l'utilizzo di strumenti di IA generativa. Vedere: https://www.linuxfoundation.org/legal/generative-ai.

È necessario seguire tutte le linee guida presenti in questo documento, incluse quelle contenute nella Guida di Stile per le Ricette, e contribuire con modifiche e requisiti aggiuntivi agli elementi nella sezione Implementare e confermare le modifiche.

Tutto il codice generato dall'IA deve essere etichettato come tale nel messaggio di commit, prima della riga Signed-off-by. Si raccomanda inoltre vivamente che qualsiasi patch o codice all'interno del commit contenga un commento o un'altra indicazione che specifichi che tale codice è stato generato dall'IA.

Ad esempio, ecco un messaggio di commit formattato correttamente:

component: Add the ability to ...

AI-Generated: Uses GitHub Copilot

Signed-off-by: Your Name <your.name@domain>

La riga Signed-off-by deve essere scritta da un umano e non dall'IA. Come promemoria, quando si contribuisce con una modifica, è richiesta la riga Signed-off-by e le disposizioni contenute nella Developer's Statement of Origin 1.1 rimangono valide.

Inoltre, è necessario specificare che i contributi relativi all'IA siano conformi alle politiche della Linux Foundation, in particolare:

  1. I contributori devono assicurarsi che i termini e le condizioni dello strumento di IA generativa non impongano restrizioni contrattuali sull'utilizzo dell'output dello strumento che siano incompatibili con la licenza del software open source del progetto, le politiche sulla proprietà intellettuale del progetto o la Definizione di Open Source.

  2. Qualora l'output dello strumento di intelligenza artificiale includa materiale protetto da copyright preesistente (incluso codice open source preesistente) di proprietà o creato da terzi, prima di contribuire al progetto, il Contributore deve accertarsi di aver ottenuto l'autorizzazione dai proprietari terzi – ad esempio tramite una licenza open source o una dichiarazione di pubblico dominio conforme alle politiche di licenza del progetto – per utilizzare e modificare tale materiale preesistente e contribuire al progetto. Inoltre, il Contributore deve fornire, insieme al proprio contributo, una notifica e l'attribuzione di tali diritti di terzi, unitamente alle informazioni sui termini di licenza applicabili.
