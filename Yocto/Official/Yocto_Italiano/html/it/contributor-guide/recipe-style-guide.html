3 Guida di Stile per le Ricette

3.1 Convenzioni di Nomenclatura delle Ricette

In generale, la maggior parte delle ricette dovrebbe seguire la convenzione di denominazione recipes-category/recipename/recipename_version.bb. Le ricette per progetti correlati possono condividere la stessa directory. recipename e category possono contenere trattini, ma i trattini non sono consentiti in version.

Se la ricetta fa riferimento a una revisione Git che non corrisponde a una versione rilasciata del software, version può essere git (ad esempio, recipename_git.bb) e la ricetta imposterà PV.

3.2 Politica sulle Versioni

Le nostre versioni seguono il formato <epoch>:<version>-<revision> o, in termini di variabili BitBake, ${PE}:${PV}-${PR}. Generalmente seguiamo la politica sulle versioni di Debian che definisce questi termini.

Nella maggior parte dei casi, la versione PV verrà impostata automaticamente dal nome del file della ricetta. Si consiglia di utilizzare le versioni rilasciate del software, poiché si tratta delle revisioni che gli sviluppatori si aspettano vengano utilizzate.

Le versioni delle ricette dovrebbero sempre essere confrontate e ordinate correttamente in modo che gli aggiornamenti funzionino come previsto. Con le versioni convenzionali come 1.4 che vengono aggiornate a 1.5, questo avviene naturalmente, ma alcune versioni non vengono ordinate correttamente. Ad esempio, 1.5 Release Candidate 2 potrebbe essere scritto come 1.5rc2 ma questo ordine viene eseguito dopo 1.5, quindi gli aggiornamenti dai feed non avverranno correttamente.

In alternativa, è possibile utilizzare l'operatore tilde (~), che ordina prima della stringa vuota, quindi 1.5~rc2 viene prima di 1.5. Esiste una sintassi storica in cui PV viene impostato come una combinazione della versione precedente + della versione di pre-release, ad esempio PV=1.4+1.5rc2. Questa sintassi è valida, ma la forma con la tilde è preferibile.

Per i confronti tra versioni, il programma opkg-compare-versions di opkg-utils può essere utile per determinare come si confrontano due numeri di versione. Il nostro algoritmo definitivo per il confronto delle versioni è quello integrato in bitbake, che mira a essere il più possibile simile a quelli dei gestori di pacchetti e alle politiche di Debian.

Quando una ricetta fa riferimento a una revisione Git che non corrisponde a una versione rilasciata del software (ad esempio, non è una versione con tag), la variabile PV deve includere il segno +, in modo che bitbake includa automaticamente le informazioni sulla versione del pacchetto durante la fase di creazione del pacchetto.

PV = "<version>+git"

In questo caso, <version> dovrebbe essere la versione più recente del software rilasciata a partire dalla revisione corrente del codice sorgente (git describe può essere utile per determinarla). Sebbene non sia consigliato per i layer pubblicati, questo formato è utile anche quando si utilizza AUTOREV per impostare la ricetta in modo che incrementi automaticamente le revisioni del controllo di versione, il che può essere utile durante lo sviluppo locale.

3.3 Modifiche al Numero di Versione

La variabile PR viene utilizzata per indicare le diverse revisioni di una ricetta che fanno riferimento alla stessa versione del sorgente upstream. Può essere utilizzata per forzare l'installazione di una nuova versione di una ricetta su un dispositivo da un feed di pacchetti. In passato, queste variabili dovevano essere impostate manualmente, ma nella maggior parte dei casi ora possono essere impostate e incrementate automaticamente da un PR Server connesso a un feed di pacchetti.

Quando PV aumenta, qualsiasi valore PR esistente può e deve essere rimosso.

Se PV cambia in modo tale da non aumentare rispetto al valore precedente, è necessario incrementare PE per garantire che i gestori di pacchetti lo aggiornino correttamente. Se non è impostato, è consigliabile impostare PE a "1" poiché il valore predefinito vuoto può essere facilmente confuso con "0" a seconda del gestore di pacchetti. PE può assumere solo un valore intero.

3.4 Formattazione delle Ricette

3.4.1 Formattazione delle Variabili

  • L'assegnazione di una variabile deve includere uno spazio attorno all'operatore, ad esempio FOO = "bar", non FOO="bar".

  • Le virgolette doppie devono essere utilizzate a destra dell'assegnazione, ad esempio FOO = "bar" non FOO = 'bar'

  • Gli spazi devono essere utilizzati per l'indentazione delle variabili, con 4 spazi per tabulazione.

  • Le variabili long devono essere suddivise su più righe, quando possibile, utilizzando il carattere di continuazione (\)

  • Quando si suddivide una variabile lunga su più righe, tutte le righe di continuazione devono essere rientrate (con spazi) per allinearsi all'inizio della virgoletta sulla prima riga:

    FOO = "this line is \
       long \
       "

    Invece di:

    FOO = "this line is \
long \
"

3.4.2 Formattazione delle Funzioni Python

  • Gli spazi devono essere utilizzati per l'indentazione del codice Python, con 4 spazi per tabulazione.

3.4.3 Formattazione delle Funzioni Shell

  • La formattazione delle funzioni shell deve essere coerente all'interno dei layer. Alcune utilizzano le tabulazioni, altre gli spazi.

3.5 Metadati della ricetta

3.5.1 Variabili Obbligatorie

Le seguenti variabili devono essere incluse in tutte le ricette:

  • SUMMARY: una descrizione di una riga del progetto upstream.

  • DESCRIPTION: una descrizione estesa del progetto upstream, eventualmente su più righe. Se non è possibile scrivere una descrizione adeguata, questa può essere omessa poiché il valore di default è SUMMARY.

  • HOMEPAGE: l'URL della homepage del progetto upstream.

  • BUGTRACKER: l'URL del sito web di tracciamento dei bug del progetto upstream, se applicabile.

3.5.2 Ordinamento delle Ricette

Quando una variabile viene definita in ricette e classi, le variabili dovrebbero seguire, ove possibile, il seguente ordine generale:

  • SUMMARY

  • DESCRIPTION

  • HOMEPAGE

  • BUGTRACKER

  • SECTION

  • LICENSE

  • LIC_FILES_CHKSUM

  • DEPENDS

  • PROVIDES

  • PV

  • SRC_URI

  • SRCREV

  • S

  • inherit ...

  • PACKAGECONFIG

  • variabili specifiche per la classe di build come EXTRA_OECONF

  • Tasks come do_configure

  • PACKAGE_ARCH

  • PACKAGES

  • FILES

  • RDEPENDS

  • RRECOMMENDS

  • RSUGGESTS

  • RPROVIDES

  • RCONFLICTS

  • BBCLASSEXTEND

In alcuni casi, l'ordine è importante e in questi casi l'ordine di default viene sovrascritto. Ad esempio:

  • PACKAGE_ARCH deve essere impostato prima di inherit packagegroup

I task devono essere ordinati in base all'ordine di esecuzione. Per i task di uso comune, l'ordine sarebbe:

  • do_fetch

  • do_unpack

  • do_patch

  • do_prepare_recipe_sysroot

  • do_configure

  • do_compile

  • do_install

  • do_populate_sysroot

  • do_package

I task personalizzati devono essere ordinate in modo simile.

Le variabili specifiche del pacchetto sono generalmente raggruppate, ad esempio:

RDEPENDS:${PN} = "foo"
RDEPENDS:${PN}-libs = "bar"

RRECOMMENDS:${PN} = "one"
RRECOMMENDS:${PN}-libs = "two"

3.5.3 Campi di Licenza della Ricetta

Le ricette devono definire entrambe le variabili LICENSE e LIC_FILES_CHKSUM:

  • LICENSE: Questa variabile specifica la licenza del software. Se non si conosce la licenza con cui viene distribuito il software che si sta compilando, è necessario consultare il codice sorgente per trovare queste informazioni. I file tipici che contengono queste informazioni includono COPYING, LICENSE e README. È possibile trovare queste informazioni anche all'inizio di un file sorgente. Ad esempio, dato un software con licenza GNU General Public License versione 2, si imposterebbe LICENSE come segue:

    LICENSE = "GPL-2.0-only"

    Le licenze specificate in LICENSE possono avere qualsiasi nome, purché non contengano spazi, poiché questi vengono utilizzati come separatori tra i nomi delle licenze. Per le licenze standard, utilizzare i nomi dei file in meta/files/common-licenses/ o i nomi dei flag SPDXLICENSEMAP definiti in meta/conf/licenses.conf.

    Nota

    Impostare una LICENSE in una ricetta si applica al software da compilare tramite quella ricetta, non al file della ricetta stessa. La licenza delle ricette, dei file di configurazione e degli script deve essere specificata chiaramente, ad esempio tramite commenti o tramite una licenza presente nel layer che contiene questi file. Questi file di licenza si trovano solitamente nella directory principale del layer. Le eccezioni devono essere chiaramente indicate nel file README o nel file LICENSE del layer.

    Ad esempio, il layer OpenEmbedded-Core (OE-Core) fornisce sia i file di licenza GPL-2.0-only che MIT, oltre a un file "LICENSE" che spiega come queste due licenze vengono attribuite ai file presenti nel layer.

  • LIC_FILES_CHKSUM: Il sistema di build di OpenEmbedded utilizza questa variabile per verificare che il testo della licenza non sia cambiato. In caso contrario, la compilazione genera un errore, offrendoti la possibilità di individuarlo e correggerlo.

    È necessario specificare tutti i file di licenza applicabili al software. Al termine della fase di configurazione, il processo di compilazione confronterà i checksum dei file per verificare che il testo non sia cambiato. Eventuali differenze genereranno un errore con un messaggio contenente il checksum corrente. Per ulteriori spiegazioni ed esempi su come impostare la variabile LIC_FILES_CHKSUM, consultare la sezione "Tracking License Changes".

    Per determinare la stringa di checksum corretta, è possibile elencare i file appropriati nella variabile LIC_FILES_CHKSUM con stringhe MD5 errate, provare a compilare il software e quindi annotare i messaggi di errore risultanti che indicheranno le stringhe MD5 corrette. Consultare la sezione "Fetching Code" per ulteriori informazioni.

    Ecco un esempio che presuppone che il software abbia un file COPYING:

    LIC_FILES_CHKSUM = "file://COPYING;md5=xxx"

    Quando si tenta di compilare il software, il sistema di build genererà un errore e fornirà la stringa corretta che è possibile sostituire nel file di configurazione per una compilazione successiva.

3.5.3.1 Aggiornamenti delle Licenze

Quando si modificano i campi LICENSE o LIC_FILES_CHKSUM nella ricetta a seguito di modifiche apportate dal progetto originale ai file di licenza, è necessario spiegare brevemente il motivo della modifica tramite un tag License-Update:. Spesso si tratta di una spiegazione piuttosto semplice, ad esempio:

License-Update: copyright years refreshed

Meno frequentemente, i termini di licenza stessi potrebbero essere cambiati. In tal caso, si consiglia di fornire un link al progetto originale che ha preso/giustificato tale decisione.

Il tag License-Update: non è necessario per i commit che correggono dati di licenza errati nei nostri metadati (per un esempio, vedere il commit OE-Core 6c8b76d).

3.5.4 Suggerimenti e Linee Guida per la Scrittura di Ricette

  • Utilizzare BBCLASSEXTEND invece di creare ricette separate come -native e -nativesdk, quando possibile. Questo evita di dover gestire più file di ricetta contemporaneamente.

  • Le ricette dovrebbero contenere task idempotenti, ovvero l'esecuzione ripetuta di un determinato task non dovrebbe modificare il risultato finale. L'ambiente di compilazione si basa su questo presupposto e la sua violazione può causare errori di compilazione difficili da individuare.

  • Per garantire l'idempotenza durante la modifica dei file nelle attività, è generalmente consigliabile:

    • copiare il file X in X.orig (solo se non esiste già)

    • quindi, copiare X.orig nuovamente in X,

    • e, infine, modificare X.

    Questo garantisce che la riesecuzione del task produca sempre lo stesso risultato finale e che il file originale possa essere conservato per essere riutilizzato. Protegge inoltre dal rischio che un'interruzione della compilazione possa corrompere il file.

3.6 Stato della Patch Upstream

Per tenere traccia delle patch applicate dalle ricette e, in definitiva, ridurre il numero di patch da gestire, il sistema di build di OpenEmbedded richiede informazioni sullo stato di ciascuna patch nel progetto upstream [principale].

Nella sua descrizione, ogni patch dovrebbe fornire informazioni dettagliate sul bug che risolve, come l'URL in un sistema di tracciamento dei bug e i link agli archivi delle mailing list pertinenti.

Si dovrebbe anche aggiungere un tag Upstream-Status: ` contenente una delle seguenti stringhe di stato:

Pending

Non è stata ancora presa alcuna decisione oppure la patch non è stata ancora inviata al progetto upstream.

Si tenga presente che ogni patch inviata al progetto upstream riduce il carico di manutenzione di OpenEmbedded e di Yocto Project a lungo termine, quindi questo stato della patch dovrebbe essere utilizzato solo in casi eccezionali in cui sussistono ostacoli reali all'invio di una patch al progetto upstream; la motivazione di tali ostacoli deve essere inclusa nella patch.

Submitted [where]

Inviata al progetto upstream, in attesa di approvazione. Facoltativamente, includi dove è stata inviata, ad esempio l'autore, la mailing list, ecc.

Backport [version]

Accettata dal progetto upstream e inclusa nella prossima release, oppure retroportata da una versione più recente del progetto upstream, poiché ci troviamo a una versione fissa. Includi le informazioni sulla versione del progetto upstream (ad esempio, ID del commit o prossima versione prevista).

Denied

Non accettata dal progetto upstream; includere la motivazione nella patch.

Inactive-Upstream [lastcommit: when (and/or) lastrelease: when]

Il progetto upstream non è più disponibile. In genere si tratta di un progetto abbandonato, inattivo da molto tempo, anche in anni. Per valutare la situazione, si consiglia di verificare non solo la data dell'ultima release, ma anche la data dell'ultimo commit e se le segnalazioni di bug e le richieste di merge effettuate da allora non hanno ricevuto risposta. Si consiglia inoltre di aggiungere alla descrizione della patch eventuali link pertinenti che mostrino chiaramente l'inattività.

Inappropriate [reason]

La patch non è appropriata per l'invio al progetto upstream. Si prega di includere una breve motivazione sulla stessa riga, racchiusa tra parentesi quadre []. In passato, esistevano diverse ragioni per non inviare patch al progetto upstream, ma dobbiamo considerare che ogni patch non inviata al progetto upstream rappresenta un onere di manutenzione per i manutentori delle ricette. Attualmente, le uniche ragioni per contrassegnare una patch come non appropriata per l'invio al progetto upstream sono:

  • oe specific: il problema è specifico del modo in cui OpenEmbedded esegue le build o configura le cose in fase di runtime e può essere risolto solo con una patch che, tuttavia, non è rilevante o appropriata per l'invio generale al progetto upstream.

  • upstream ticket <link>: il problema non è specifico di OpenEmbedded e dovrebbe essere risolto al progetto upstream, ma la patch nella sua forma attuale non è adatta per l'unione al progetto upstream e l'autore non possiede le competenze sufficienti per sviluppare una patch adeguata. Il problema viene quindi gestito tramite una segnalazione di bug (includere il link).

Naturalmente, se in seguito un'altra persona si occupa di inviare questa patch al progetto upstream, lo stato dovrebbe essere modificato in Submitted [where] e la persona che si assume la responsabilità dell'invio dovrebbe aggiungere alla patch una riga aggiuntiva con la dicitura Signed-off-by:.

3.6.1 Esempi

Ecco un esempio di patch inviata in upstream:

rpm: Adjusted the foo setting in bar

[RPM Ticket #65] -- http://rpm5.org/cvs/tktview?tn=65,5

The foo setting in bar was decreased from X to X-50% in order to
ensure we don't exhaust all system memory with foobar threads.

Upstream-Status: Submitted [rpm5-devel@rpm5.org]

Signed-off-by: Joe Developer <joe.developer@example.com>

Un futuro aggiornamento potrebbe modificare il valore in Backport o Denied a seconda dei casi.

Un altro esempio di patch specifica per OpenEmbedded:

Do not treat warnings as errors

There are additional warnings found with musl which are
treated as errors and fails the build, we have more combinations
than upstream supports to handle.

Upstream-Status: Inappropriate [oe specific]

Ecco una patch che è stata retroportata da un commit upstream:

include missing sys/file.h for LOCK_EX

Upstream-Status: Backport [https://github.com/systemd/systemd/commit/ac8db36cbc26694ee94beecc8dca208ec4b5fd45]

3.7 Patch CVE

Per un migliore controllo delle vulnerabilità, le patch che risolvono le CVE devono contenere il tag CVE:. Questo tag dovrebbe elencare tutte le CVE risolte dalla patch. Se vengono risolte più CVE, separarle con degli spazi.

3.7.1 Esempi di CVE

Questo dovrebbe essere l'header della patch che risolve CVE-2015-8370 in GRUB2:

grub2: Fix CVE-2015-8370

[No upstream tracking] -- https://bugzilla.redhat.com/show_bug.cgi?id=1286966

Back to 28; Grub2 Authentication

Two functions suffer from integer underflow fault; the grub_username_get() and grub_password_get()located in
grub-core/normal/auth.c and lib/crypto.c respectively. This can be exploited to obtain a Grub rescue shell.

Upstream-Status: Backport [http://git.savannah.gnu.org/cgit/grub.git/commit/?id=451d80e52d851432e109771bb8febafca7a5f1f2]
CVE: CVE-2015-8370
Signed-off-by: Joe Developer <joe.developer@example.com>

3.8 Formato della Patch

Per default, le patch create con git format-patch hanno una firma di versione Git alla fine. Per evitare di avere una firma Git alla fine delle patch generate o aggiornate, è possibile utilizzare le impostazioni di configurazione di Git:

git config --global format.signature ""

Nota

Le patch generate o aggiornate da devtool vengono create senza firma.
