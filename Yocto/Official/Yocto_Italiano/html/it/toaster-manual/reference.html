4 Concetti e Riferimenti

Per configurare e utilizzare Toaster, è necessario comprendere alcuni concetti e disporre di un riferimento di base sui comandi. Questo capitolo finale fornisce informazioni concettuali sui sorgenti dei layer, le release e i file di configurazione JSON. Viene inoltre fornita una rapida panoramica di alcuni utili comandi manage.py specifici di Toaster. Informazioni sui comandi manage.py sono disponibili sul Web e questo manuale non intende in alcun modo fornire un riferimento completo dei comandi.

4.1 Sorgenti dei Layer

In generale, una "sorgente di layer" è una fonte di informazioni sui layer esistenti. In particolare, ci occupiamo dei layer utilizzabili con Yocto Project e Toaster. Questo capitolo descrive un tipo specifico di sorgente di layer, chiamato "layer index" [indice di layer].

Un indice di layer è un'applicazione web che contiene informazioni su un insieme di layer personalizzati. Un buon esempio di indice di layer esistente è l'OpenEmbedded Layer Index. Un'istanza pubblica di questo indice di layer è disponibile all'indirizzo https://layers.openembedded.org/. Il codice sorgente dell'applicazione web di questo indice di layer è disponibile all'indirizzo https://git.yoctoproject.org/layerindex-web/.

Quando si collega una sorgente di layer a Toaster, quest'ultimo può interrogare la sorgente tramite un'API REST, memorizzare le informazioni sui layer nel database di Toaster e quindi mostrare tali informazioni agli utenti. Gli utenti possono quindi visualizzare queste informazioni e creare layer direttamente da Toaster senza dover clonare o modificare il file di configurazione dei layer di BitBake build/conf/bblayers.conf.

Integrare una sorgente di layer in Toaster è utile quando si hanno molti layer personalizzati che devono essere creati regolarmente da una community di sviluppatori. Infatti, Toaster è preconfigurato con l'OpenEmbedded Metadata Index.

Nota

Non è obbligatorio utilizzare una sorgente di layer per usare Toaster. L'integrazione con una sorgente di layer è facoltativa.

4.1.1 Configurazione e Utilizzo di una Sorgente di Layer

Per utilizzare la propria sorgente di layer, è necessario configurarla e quindi integrarla in Toaster. Questa sezione descrive come integrarsi con un indice di layer in modo simile a come Toaster si integra con l'OpenEmbedded Metadata Index.

4.1.1.1 Comprensione dei Layer

Il primo passo ovvio per utilizzare un indice di layer è quello di avere diversi layer personalizzati che gli sviluppatori creano e a cui accedono regolarmente tramite Yocto Project. Questo set di layer deve esistere ed è necessario sapere dove si trovano. Queste informazioni saranno necessarie quando si configura il codice per l'applicazione web che si "aggancia" al set di layer.

Per informazioni generali sui layer, consultare la sezione "Il Modello a Layer di Yocto Project" nella Manuale Introduttivo e Concetti di Yocto Project. Per informazioni su come creare layer, consultare la sezione "Comprendere e Creare i Layer" nel Manuale di Sviluppo dei Task di Yocto Project.

4.1.1.2 Configurazione di Toaster per Agganciarsi al Proprio Indice di Layer

Affinché Toaster utilizzi il proprio indice di layer, si deve ospitare l'applicazione web su un server a cui Toaster possa connettersi. Si devono anche fornire a Toaster le informazioni sull'indice di layer. In altre parole, è necessario configurare Toaster per utilizzare il proprio indice di layer. Questa sezione descrive due metodi per configurare e utilizzare l'indice di layer.

Nella sezione precedente, è stato fatto riferimento al codice dell'Indice di Metadati OpenEmbedded (ovvero https://layers.openembedded.org/) È possibile utilizzare questo codice, che si trova in https://git.yoctoproject.org/layerindex-web/, come base per creare il proprio indice di layer.

4.1.1.2.1 Utilizzare l'Interfaccia di Amministrazione

Accedere all'interfaccia di amministrazione tramite un browser inserendo l'URL dell'istanza di Toaster e aggiungendo "/admin" alla fine dell'URL. Ad esempio, se si esegue Toaster in locale, utilizzare il seguente URL:

http://127.0.0.1:8000/admin

L'interfaccia di amministrazione presenta una sezione "Layer sources" che include un pulsante "Add layer source". Cliccare su questo pulsante e fornire le informazioni richieste. Assicurarsi di selezionare "layerindex" come tipo di origine layer.

4.1.1.2.2 Utilizzo della Funzionalità Fixture

La funzionalità Fixture di Django sovrascrive il server di layer di default quando la si utilizza per specificare un URL personalizzato. Per utilizzare la funzionalità Fixture, creare (o modificare) il file bitbake/lib/toaster.orm/fixtures/custom.xml e impostare la seguente configurazione di Toaster col proprio URL personalizzato:

<?xml version="1.0" ?>
<django-objects version="1.0">
   <object model="orm.toastersetting" pk="100">
      <field name="name" type="CharField">CUSTOM_LAYERINDEX_SERVER</field>
      <field name="value" type="CharField">https://layers.my_organization.org/layerindex/branch/master/layers/</field>
   </object>
<django-objects>

Quando si avva Toaster per la prima volta, o se si elimina il file toaster.sqlite e lo si riavvia, il database verrà popolato correttamente da questo server di indice dei layer.

Una volta aggiornate le informazioni, verificare che le nuove informazioni sui layer siano disponibili utilizzando l'interfaccia web di Toaster. Per farlo, visitare la pagina "All compatible layers" all'interno di un progetto Toaster. I layer della propria sorgente di layer dovrebbero essere elencati lì.

Se si modificano le informazioni nel server di indice dei layer, aggiornare il database di Toaster eseguendo il seguente comando:

$ bitbake/lib/toaster/manage.py lsupdates

Se Toaster riesce a raggiungere l'URL dell'API, verrà visualizzato un messaggio che informa che Toaster sta aggiornando le informazioni della sorgente dei layer.

4.2 Release

Quando si crea un progetto Toaster tramite l'interfaccia web, viene richiesto di scegliere una "Release". Nel contesto di Toaster, il termine "Release" si riferisce a un insieme di layer e a una versione di BitBake utilizzati dal sistema di build OpenEmbedded per la compilazione. Toaster è preconfigurato con release corrispondenti ai branch di rilascio di Yocto Project. Tuttavia, è possibile modificare, eliminare e creare nuove release in base alle proprie esigenze. Questa sezione fornisce alcune informazioni di base sulle release.

4.2.1 Release Pre-Configurate

Toaster è configurato per utilizzare un set specifico di release. Naturalmente, è sempre possibile configurare Toaster per utilizzare qualsiasi release. Ad esempio, si potrebbe voler compilare il progetto con una specifica commit di una qualsiasi delle release predefinite. Oppure, si potrebbe voler compilare il progetto con diverse revisioni di OpenEmbedded e BitBake.

Nella configurazione di default, Toaster è compatibile con le seguenti versioni:

  • Yocto Project 6.1 "Blacksail" o OpenEmbedded "Blacksail": Questa versione fa sì che i progetti Toaster vengano compilati utilizzando l'ultima versione del branch blacksail, disponibile all'indirizzo https://git.yoctoproject.org/poky/log/?h=blacksail o https://git.openembedded.org/openembedded-core/commit/?h=blacksail.

  • Yocto Project "Master" o OpenEmbedded "Master": Questa versione fa sì che i progetti Toaster vengano compilati utilizzando l'ultima versione del branch master, dove si svolge lo sviluppo attivo, disponibile all'indirizzo https://git.yoctoproject.org/poky/log/ o https://git.openembedded.org/openembedded-core/log/.

  • Local Yocto Project o Local OpenEmbedded: Questa versione fa sì che i progetti Toaster vengano compilati utilizzando la versione più recente del clone di poky o openembedded-core che si ha in locale sulla macchina su cui è in esecuzione Toaster.

4.3 Configurazione di Toaster

Per utilizzare Toaster, è necessario configurare il database con i contenuti di default. Le seguenti sottosezioni descrivono vari aspetti della configurazione di Toaster.

4.3.1 Configurazione del Flusso di Lavoro

Il file bldcontrol/management/commands/checksettings.py controlla la configurazione del workflow [flusso di lavoro]. Ecco la procedura per popolare inizialmente questo database.

  1. Le impostazioni di default del progetto vengono definite dal file orm/fixtures/settings.xml.

  2. La distribuzione e i layer di default del progetto vengono aggiunti dal file orm/fixtures/poky.xml se Poky è installato. Se Poky non è installato, vengono aggiunti dal file orm/fixtures/oe-core.xml.

  3. Se il file orm/fixtures/custom.xml esiste, i suoi valori vengono aggiunti.

  4. L'indice dei layer viene quindi scansionato e aggiunto al database.

Una volta completati questi passaggi, Toaster è configurato e pronto per l'uso.

4.3.2 Personalizzazione dei Dati Pre-Impostati

I dati preimpostati per Toaster sono facilmente personalizzabili. È possibile creare il file orm/fixtures/custom.xml per personalizzare i valori inseriti nel database. La personalizzazione è additiva e può estendere o sostituire completamente i valori esistenti.

Il file orm/fixtures/custom.xml viene utilizzato per modificare le impostazioni di default del progetto per la macchina, la distribuzione, le immagini dei file e i layer. Quando si crea un nuovo progetto, è possibile utilizzare il file per definire le opzioni alternative di rilascio del progetto. Ad esempio, è possibile aggiungere una o più opzioni aggiuntive che presentano set di layer o distribuzioni personalizzati e qualsiasi altro contenuto locale o proprietario.

Inoltre, è possibile disabilitare completamente il contenuto dei file oe-core.xml e poky.xml definendo la sezione mostrata di seguito nel file settings.xml. Ad esempio, questa opzione è particolarmente utile se la configurazione personalizzata definisce un numero inferiore di release o layer rispetto ai file di fixture di default.

L'esempio seguente imposta "name" a "CUSTOM_XML_ONLY" e il suo valore su "True".

<object model="orm.toastersetting" pk="99">
   <field type="CharField" name="name">CUSTOM_XML_ONLY</field>
   <field type="CharField" name="value">True</field>
</object>

4.3.3 Comprensione del Formato dei File di Fixture

Ecco una panoramica del formato dei file utilizzati da oe-core.xml, poky.xml e custom.xml.

Le seguenti sottosezioni descrivono ciascuna sezione dei file di fixture e forniscono un esempio di sezione del codice XML utilizzabile per comprendere queste informazioni e creare un file custom.xml locale.

4.3.3.1 Definizione della Distribuzione di Default e di Altri Valori

Questa sezione definisce il valore di default della distribuzione per i nuovi progetti. Per default, riserva il primo record di Toaster Setting "1". Di seguito viene mostrato come impostare il valore di default del progetto per DISTRO:

<!-- Set the project default value for DISTRO -->
<object model="orm.toastersetting" pk="1">
   <field type="CharField" name="name">DEFCONF_DISTRO</field>
   <field type="CharField" name="value">poky</field>
</object>

È possibile sovrascrivere altri valori di default del progetto aggiungendo ulteriori sezioni di Toaster Setting, come ad esempio le impostazioni provenienti dal file settings.xml. È inoltre possibile aggiungere valori personalizzati inclusi nell'ambiente BitBake. I valori "pk" devono essere univoci. Per convenzione, i valori che definiscono i valori predefiniti del progetto hanno il prefisso "DEFCONF".

4.3.3.2 Definizione della Versione di BitBake

Quanto segue definisce la versione di BitBake utilizzata per la successiva selezione della release:

<!-- Bitbake versions which correspond to the metadata release -->
<object model="orm.bitbakeversion" pk="1">
   <field type="CharField" name="name">blacksail</field>
   <field type="CharField" name="giturl">https://git.yoctoproject.org/poky</field>
   <field type="CharField" name="branch">blacksail</field>
   <field type="CharField" name="dirpath">bitbake</field>
</object>

4.3.3.3 Definizione della Release

Quanto segue definisce le release quando si crea un nuovo progetto:

<!-- Releases available -->
<object model="orm.release" pk="1">
   <field type="CharField" name="name">blacksail</field>
   <field type="CharField" name="description">Yocto Project 6.1 "Blacksail"</field>
   <field rel="ManyToOneRel" to="orm.bitbakeversion" name="bitbake_version">1</field>
   <field type="CharField" name="branch_name">blacksail</field>
   <field type="TextField" name="helptext">Toaster will run your builds using the tip of the <a href="https://git.yoctoproject.org/cgit/cgit.cgi/poky/log/?h=blacksail">Yocto Project Blacksail branch</a>.</field>
</object>

Il valore "pk" deve corrispondere alla rispettiva versione di BitBake indicata sopra.

4.3.3.4 Definizione dei Nomi dei Layer di Defaultper la Release

Quanto segue definisce i layer di default per ciascuna release:

<!-- Default project layers for each release -->
<object model="orm.releasedefaultlayer" pk="1">
   <field rel="ManyToOneRel" to="orm.release" name="release">1</field>
   <field type="CharField" name="layer_name">openembedded-core</field>
</object>

I valori 'pk' nell'esempio precedente devono iniziare da "1" e incrementare in modo univoco. È possibile utilizzare lo stesso nome di layer in più release.

4.3.3.5 Definizione delle Definizioni dei Layer

Le definizioni dei layer sono le più complesse. Quanto segue definisce ciascun layer e quindi specifica la versione esatta del layer utilizzata per ogni rispettiva release. È necessario avere una voce orm.layer per ogni layer. Quindi, per ogni voce è necessario un set di voci orm.layer_version che colleghino il layer a ogni release che lo include. In generale, tutte le release includono il layer.

<object model="orm.layer" pk="1">
   <field type="CharField" name="name">openembedded-core</field>
   <field type="CharField" name="layer_index_url"></field>
   <field type="CharField" name="vcs_url">https://git.yoctoproject.org/poky</field>
   <field type="CharField" name="vcs_web_url">https://git.yoctoproject.org/cgit/cgit.cgi/poky</field>
   <field type="CharField" name="vcs_web_tree_base_url">https://git.yoctoproject.org/cgit/cgit.cgi/poky/tree/%path%?h=%branch%</field>
   <field type="CharField" name="vcs_web_file_base_url">https://git.yoctoproject.org/cgit/cgit.cgi/poky/tree/%path%?h=%branch%</field>
</object>
<object model="orm.layer_version" pk="1">
   <field rel="ManyToOneRel" to="orm.layer" name="layer">1</field>
   <field type="IntegerField" name="layer_source">0</field>
   <field rel="ManyToOneRel" to="orm.release" name="release">1</field>
   <field type="CharField" name="branch">blacksail</field>
   <field type="CharField" name="dirpath">meta</field>
</object> <object model="orm.layer_version" pk="2">
   <field rel="ManyToOneRel" to="orm.layer" name="layer">1</field>
   <field type="IntegerField" name="layer_source">0</field>
   <field rel="ManyToOneRel" to="orm.release" name="release">2</field>
   <field type="CharField" name="branch">HEAD</field>
   <field type="CharField" name="commit">HEAD</field>
   <field type="CharField" name="dirpath">meta</field>
</object>
<object model="orm.layer_version" pk="3">
   <field rel="ManyToOneRel" to="orm.layer" name="layer">1</field>
   <field type="IntegerField" name="layer_source">0</field>
   <field rel="ManyToOneRel" to="orm.release" name="release">3</field>
   <field type="CharField" name="branch">master</field>
   <field type="CharField" name="dirpath">meta</field>
</object>

I valori "pk" del layer sopra indicati devono essere univoci e in genere iniziano da "1". Anche i valori "pk" della versione del layer devono essere univoci per tutti i layer e in genere iniziano da "1".

4.4 Monitoraggio Remoto di Toaster

Toaster dispone di un'API che consente alle applicazioni di gestione remota di interrogare direttamente lo stato del server Toaster e delle sue build in modalità machine-to-machine. Questa API utilizza l'interfaccia REST e il trasferimento di file JSON. Ad esempio, è possibile monitorare una build all'interno di un container tramite porte HTTP note e supportate per accedere facilmente a un server Toaster all'interno del container. In questo esempio, utilizzando questa API JSON diretta, si evita di dover analizzare la pagina web rispetto alla visualizzazione mostrata all'utente.

4.4.1 Verifica dello Stato di Salute

Prima di utilizzare il monitoraggio remoto di Toaster, è consigliabile eseguire una verifica dello stato di salute. Per farlo, si esegue un ping al server Toaster utilizzando la seguente chiamata per verificare se è ancora attivo:

http://host:port/health

Assicurarsi di specificare host e porta. Se il server è attivo, si riceverà la seguente risposta HTML:

<!DOCTYPE html>
<html lang="en">
   <head><title>Toaster Health</title></head>
   <body>Ok</body>
</html>

4.4.2 Determinare lo Stato delle Build in Corso

A volte è utile determinare lo stato di una build in corso. Per ottenere lo stato delle build in sospeso, si utilizza la seguente chiamata:

http://host:port/toastergui/api/building

Assicurarsi di specificare host e porta. L'output è un file JSON che elenca tutte le build in corso. Questo file include il tempo in secondi trascorso dall'avvio di ciascuna build, nonché l'avanzamento della clonazione, dell'analisi e dell'esecuzione dei task. Ecco un esempio di output per una build in corso:

{"count": 1,
 "building": [
   {"machine": "beaglebone",
     "seconds": "463.869",
     "task": "927:2384",
     "distro": "poky",
     "clone": "1:1",
     "id": 2,
     "start": "2017-09-22T09:31:44.887Z",
     "name": "20170922093200",
     "parse": "818:818",
     "project": "my_rocko",
     "target": "core-image-minimal"
   }]
}

I dati JSON per questa query vengono restituiti su una singola riga. Nell'esempio precedente, la riga è stata suddivisa artificialmente per una migliore leggibilità.

4.4.3 Verifica dello Stato delle Build Completate

Una volta completata una build, è possibile visualizzarne lo stato utilizzando la seguente chiamata:

http://host:port/toastergui/api/builds

Assicurarsi di specificare host e porta. L'output è un file JSON che elenca tutte le build completate e include informazioni di riepilogo. Ecco un esempio di output per una build completata:

{"count": 1,
 "builds": [
   {"distro": "poky",
      "errors": 0,
      "machine": "beaglebone",

      "id": 1,
      "start": "2017-09-22T09:25:17.824Z",
      "warnings": 1,
      "name": "20170922092618"
   }]
}

I dati JSON per questa query vengono restituiti su una singola riga. Nell'esempio precedente, la riga è stata suddivisa artificialmente per una migliore leggibilità.

4.4.4 Determinazione dello Stato di una Build Specifica

A volte è utile determinare lo stato di una build specifica. Per ottenere lo stato di una build specifica, utilizzare la seguente chiamata:

http://host:port/toastergui/api/build/ID

Assicurarsi di specificare host, porta e ID. È possibile trovare il valore di ID dalla query Builds Completed. Assicurarsi di specificare host, porta e ID. È possibile trovare il valore di ID dalla query "Verifica dello Stato delle Build Completate" per ulteriori informazioni.

L'output è un file JSON che elenca la build specifica e include informazioni di riepilogo. Ecco un esempio di output per una build specifica:

{"build":

   }

4.5 Comandi Utili

Oltre all'interfaccia utente web e agli script che avviano e arrestano Toaster, sono disponibili comandi da riga di comando tramite lo script di gestione manage.py. È possibile trovare la documentazione generale su manage.py sul sito di Django. Tuttavia, sono stati creati diversi comandi manage.py specifici per Toaster, utilizzati per controllare la configurazione e le attività di back-end. È possibile trovare questi comandi nella Source Directory (ad esempio poky) in bitbake/lib/manage.py. Questa sezione documenta tali comandi.

Nota

  • Quando si utilizzano i comandi manage.py con una configurazione di default, è necessario assicurarsi che la directory di lavoro sia impostata sulla Build Directory. Utilizzando i comandi manage.py dalla Build Directory, Toaster può trovare il file toaster.sqlite, che si trova nella Build Directory.

  • Per configurazioni di database non predefinite, è possibile utilizzare i comandi manage.py da una directory diversa da Build Directory. A tal fine, il file toastermain/settings.py deve essere configurato in modo da puntare al backend del database corretto.

4.5.1 buildslist

Il comando buildslist elenca tutte le build registrate da Toaster. Per accedervi, procedere come segue:

$ bitbake/lib/toaster/manage.py buildslist

Il comando restituisce un elenco, comprensivo di identificativi numerici, delle build registrate da Toaster nel database corrente.

Si deve eseguire il comando buildslist prima di identificare le build esistenti nel database prima di usare il comando builddelete. Ecco un esempio che presuppone i nomi di default per repository e della Build Directory:

$ cd poky/build
$ python ../bitbake/lib/toaster/manage.py buildslist

Se il database di Toaster contenesse una sola build, il comando buildslist restituirebbe un output simile al seguente:

1: qemux86 poky core-image-minimal

4.5.2 builddelete

Il comando builddelete elimina i dati associati a una build. Per accedervi, procedere come segue:

$ bitbake/lib/toaster/manage.py builddelete build_id

Il comando elimina tutti i dati del build_id specificato. Questo comando è utile per rimuovere i dati vecchi e inutilizzati dal database.

Prima di eseguire il comando builddelete, è necessario ottenere l'ID associato alle build utilizzando il comando buildslist.

4.5.3 perf

Il comando perf misura le prestazioni di Toaster. È possibile accedervi nel seguente modo:

$ bitbake/lib/toaster/manage.py perf

Questo comando esegue un controllo di base che restituisce i tempi di caricamento delle pagine per identificare eventuali problemi di prestazioni.

4.5.4 checksettings

Il comando checksettings verifica le impostazioni di Toaster esistenti. È possibile accedervi nel seguente modo:

$ bitbake/lib/toaster/manage.py checksettings

Toaster utilizza impostazioni basate sul database per configurare i task di compilazione. Il comando checksettings verifica che le impostazioni del database siano valide, ovvero che contengano le informazioni minime necessarie per avviare una build.

Affinché il comando checksettings funzioni, il database deve essere configurato correttamente e non contenere dati preesistenti. Per verificare che il database sia pronto, è possibile eseguire i seguenti comandi:

$ bitbake/lib/toaster/manage.py syncdb
$ bitbake/lib/toaster/manage.py migrate orm
$ bitbake/lib/toaster/manage.py migrate bldcontrol

Dopo aver eseguito questi comandi, è possibile eseguire il comando checksettings.

4.5.5 runbuilds

Il comando runbuilds avvia le build pianificate. Per accedervi, procedere come segue:

$ bitbake/lib/toaster/manage.py runbuilds

Il comando runbuilds verifica se nel database sono presenti build pianificate e, in caso affermativo, le avvia in base alla pianificazione. Il comando restituisce un valore al termine delle build, ma prima del loro completamento. L'interfaccia di registrazione di Toaster registra e aggiorna il database al termine delle build.
