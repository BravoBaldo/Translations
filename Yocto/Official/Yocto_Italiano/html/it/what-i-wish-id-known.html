Cosa sarebbe stato utile sapere sullo Yocto Project


Nota

Prima di procedere con la lettura, si raccomanda di consultare la pagina Technical Overview la quale contiene le definizioni di molti dei termini qui menzionati. Inoltre, è importante considerare che alcune informazioni potrebbero non risultare chiare nell'immediato ma, con l'inizio dello sviluppo, rappresenteranno i dettagli da tenere maggiormente a portata di mano. Queste costituiscono le migliori pratiche per l'utilizzo di Yocto Project e vengono aggiornate regolarmente.

L'utilizzo di Yocto Project è relativamente semplice, fino a quando non si verifica un problema. Senza una comprensione approfondita del funzionamento del processo di compilazione, si rischierebbe di dover effettuare la risoluzione dei problemi alla cieca, come davanti a "una scatola nera [black box]". Di seguito vengono riportati alcuni elementi che gli utenti esperti avrebbero voluto conoscere prima di intraprendere la loro prima compilazione con Yocto Project. È possibile inviare feedback per proporre ulteriori suggerimenti.

  1. Utilizzare Git, non il download del tarball: Con l'utilizzo di Git, il software viene aggiornato automaticamente con le correzioni dei bug grazie alle funzionalità intrinseche del sistema. Se invece si effettua il download del tarball, la gestione degli aggiornamenti rimarrà a carico esclusivo dell'utente.

  2. Conoscere l'indice dei layer: Tutti i layer sono reperibili nel layer index. I layer che hanno richiesto lo stato di compatibilità con Yocto Project (garanzia di continuità strutturale e test di conformità) sono disponibili alla pagina Yocto Project Compatible Layers. In genere si consiglia di consultare prima l'indice dei layer compatibili e, nel caso in cui non si trovi il layer necessario, di verificare l'indice generale dei layer. L'indice dei layer è un elemento originario del progetto Open Embedded. Di conseguenza, tale indice non dispone della supervisione e dei test che Yocto Project fornisce per l'elenco dei layer compatibili, sebbene quest'ultimo contenga meno voci. È opportuno sapere, quando si avvia una ricerca nell'indice dei layer, che non tutti i layer presentano lo stesso livello di maturità, convalida o usabilità. Inoltre, le ricerche non assegnano priorità ai risultati visualizzati. Non esiste un modo semplice per guidare l'utente nella scelta del layer più adatto alle proprie esigenze. Di conseguenza, si ricorre spesso a tentativi, alla consultazione delle mailing list o alla collaborazione con altri sviluppatori nelle apposite stanze virtuali per compiere le scelte migliori.

  3. Utilizzare layer BSP esistenti dei produttori di hardware quando possibile: Intel, TI, NXP e altri forniscono informazioni su quali layer BSP utilizzare con i rispettivi chip. Questi layer hanno nomi come "meta-intel" o "meta-ti". Si raccomanda di evitare la creazione di layer da zero. In caso di utilizzo di chip personalizzati, è opportuno usare uno di questi layer come guida o modello e familiarizzare con il manuale Manuale del Board Support Package (BSP) di Yocto Project.

  4. Non inserire tutto all'interno di un unico layer: Utilizzare layer diversi per separare logicamente le informazioni all'interno della build. A titolo di esempio, è possibile disporre di un layer BSP, un layer GUI, una configurazione di distribuzione (distro), un middleware o un'applicazione (es. "meta-filesystems", "meta-python", "meta-intel" e così via). L'inserimento dell'intera compilazione in un solo layer limita e complica la futura personalizzazione e il riutilizzo. Al contrario, l'isolamento delle informazioni nei singoli layer contribuisce a semplificare le personalizzazioni e il riutilizzo futuri.

  5. Mai modificare i layer core (BitBake, OpenEmbedded-Core (OE-Core) ed eventualmente meta-yocto). Mai, in nessun caso. Al momento dell'aggiornamento al rilascio successivo, tutto il lavoro svolto andrà perduto. COMPLETAMENTE.**

  6. Non farsi ingannare dai risultati di ricerca della documentazione: La documentazione di Yocto Project viene aggiornata costantemente. Sfortunatamente, quando si utilizza Google per cercare concetti o termini relativi a Yocto Project, il motore di ricerca individua e restituisce sistematicamente versioni datate dei manuali. Ad esempio, la ricerca di uno specifico argomento su Google potrebbe portare a un risultato all'interno di un manuale di Yocto Project vecchio di diversi rilasci. Per avere la certezza di consultare la documentazione più recente di Yocto Project, si raccomanda di utilizzare il menù a tendina situato nella parte superiore di qualsiasi pagina.

    Molti sviluppatori consultano il manuale All-in-one 'Mega' Manual per trovare un concetto o un termine effettuando una ricerca nell'intera pagina. Questo manuale è una concatenazione del set di manuali principali di Yocto Project. Pertanto, una semplice ricerca testuale tramite Ctrl+F all'interno di questo documento mostra tutte le corrispondenze per il termine o il concetto desiderato. Una volta individuata l'area di interesse, è possibile visualizzare il manuale effettivo, se lo si desidera. È inoltre possibile utilizzare la barra di ricerca presente nel menu o nel pannello di navigazione sinistro.

  7. Comprendere i concetti di base del funzionamento del sistema di build (il workflow): La comprensione del flusso di lavoro di Yocto Project è fondamentale, poiché permette sia di individuare il punto esatto in cui si verificano le anomalie, sia di capire le cause dell'interruzione della compilazione. Il flusso di lavoro si suddivide nelle seguenti fasi:

    1. Fetch - recupero del codice sorgente

    2. Extract - estrazione dei sorgenti

    3. Patch - applicazione delle patch per la correzione di bug e nuove funzionalità

    4. Configure - impostazione delle specifiche dell'ambiente

    5. Build - compilazione e collegamento (linking)

    6. Install - copia dei file nelle directory di destinazione

    7. Package - pacchettizzazione dei file per l'installazione

    Durante la fase di "fetch", potrebbe verificarsi l'impossibilità di reperire il codice. Durante la fase di "extract", è probabile che si riscontri un archivio zip non valido o un problema analogo. In altri termini, la funzione di una determinata parte del flusso di lavoro fornisce un'indicazione su cosa potrebbe non funzionare correttamente.

  8. Generazione del grafo delle dipendenze: È possibile generare un grafo delle dipendenze per visualizzare le relazioni tra ricette (recipes), attività (tasks) e obiettivi (targets). Per generare questo grafo, si utilizza l'opzione "-g" con BitBake. Quando si avvia una compilazione e questa si interrompe, potrebbero comparire pacchetti sconosciuti o inseriti dal sistema senza un motivo apparente. Il grafo delle dipendenze permette di chiarire tale ambiguità. Per approfondire l'argomento e comprendere come generare i grafi, si rimanda alla sezione Generating Dependency Graphs del Manuale Utente di BitBake.

  9. Decodifica dei nomi "magici" delle cartelle in tmp/work: Il sistema di build esegue il recupero, l'estrazione, la pre-elaborazione e la compilazione. In caso di errore, il sistema segnala direttamente il percorso di una cartella in cui risiedono i file temporanei (build/tmp) e i pacchetti risultanti dalla compilazione. Per un esempio dettagliato di questo processo, si veda l' esempio, sebbene sia basato su un rilascio precedente di Yocto Project.

    Quando si esegue una compilazione, è possibile utilizzare l'opzione da riga di comando "-u" di BitBake per specificare un'interfaccia utente di visualizzazione del grafo delle dipendenze (ad es. knotty, ncurses o taskexp), facilitando così la comprensione delle dipendenze di compilazione.

  10. Compilazione di elementi diversi dalle sole immagini: È possibile compilare ed eseguire una specifica attività [task] per un determinato pacchetto (incluso devshell) o persino una singola ricetta. Quando si inizia a utilizzare Yocto Project, le istruzioni contenute in Build Rapida di un'Immagine con lo Yocto Project mostrano come creare un'immagine e poi eseguirla o effettuarne il flash. Tuttavia, è consentito compilare anche una singola ricetta. Pertanto, se una dipendenza o una ricetta non funziona, è sufficiente eseguire il comando "bitbake foo" dove "foo" è il nome della specifica ricetta. Man mano che si acquisisce maggiore esperienza con Yocto Project, e nel caso in cui le compilazioni falliscano, può essere utile verificare che la fase di fetch funzioni correttamente. Ecco alcuni link utili: Using a Development Shell per informazioni su come compilare ed eseguire un task specifico con devshell. Inoltre il manuale SDK mostra come compilare una specifica ricetta.

  11. Una definizione ambigua: Pacchetto contro Ricetta: Una ricetta contiene le istruzioni che il sistema di compilazione utilizza per creare i pacchetti. Ricette e pacchetti rappresentano la differenza tra la fase iniziale (front end) e il risultato finale del processo di compilazione.

    Come menzionato, il sistema di compilazione [build] prende la ricetta e crea i pacchetti in base alle istruzioni in essa contenute. I pacchetti risultanti sono correlati all'elemento principale che la ricetta sta compilando, ma costituiscono parti diverse (pacchetti) della compilazione (ovvero il pacchetto principale, quello di documentazione, il pacchetto con i simboli di debug, quello con le utilità separate e così via). Il sistema suddivide i pacchetti in modo da evitare l'installazione di componenti non desiderati o non necessari, il che rappresenta un vantaggio significativo quando si sviluppa per piccoli dispositivi in ambito embedded e IoT.

  12. È importante conoscere e sapere cosa è contenuto nel filesystem di root.

  13. Creazione di una propria ricetta di immagine: Esistono diversi modi per creare una ricetta di immagine personalizzata. Si consiglia di creare una propria ricetta di immagine anziché estenderne una esistente. La scrittura di una ricetta di immagine è un'operazione semplice e immediata. Si ribadisce l'indicazione di non tentare l'estensione di una ricetta di immagine esistente, bensì di crearne una propria fin dall'inizio per procedere correttamente.

  14. Di seguito viene riportato l'elenco delle competenze fondamentali necessarie per uno sviluppatore di sistemi. È fondamentale essere in grado di:

    • gestire i proxy aziendali

    • aggiungere un pacchetto a un'immagine

    • comprendere la differenza tra una ricetta e un pacchetto

    • configurare un pacchetto in autonomia e capire l'utilità di tale procedura

    • identificare i pacchetti creati da una ricetta

    • identificare i file contenuti in un pacchetto

    • identificazione i file contenuti in un'immagine

    • aggiungere un server SSH a un'immagine (abilitazione del trasferimento file sul target)

    • conoscere l'anatomia di una ricetta

    • conoscere la creazione e l'utilizzo dei layer

    • cercare ricette (con lo OpenEmbedded Layer index)

    • Capire la differenza tra le impostazioni MACHINE e DISTRO

    • cercare e usare il BSP (machine) corretto per l'hardware in uso

    • cercare esempi di funzionalità DISTRO e individuare la loro corretta collocazione

    • capire la pipeline dei task e l'esecuzione dei singoli task

    • capire devtool e la semplificazione del flusso di lavoro

    • migliorare la velocità di build tramite download e cache di stato condivisi [shared]

    • generare e comprendere un grafo delle dipendenze

    • generare e comprendere l'ambiente BitBake

    • configurare un Extensible SDK per lo sviluppo di applicazioni

  15. A seconda degli interessi principali relativi a Yocto Project, si consiglia la lettura dei seguenti testi:

    • Consultare il Manuale di Sviluppo dei Task di Yocto Project: Questo manuale contiene informazioni sulle procedure raggruppate per aiutare nella configurazione, nel lavoro con i layer, nella personalizzazione delle immagini, nella scrittura di nuove ricette, nell'utilizzo delle librerie e nell'uso di QEMU. Le informazioni sono basate su task e coprono per intero a Yocto Project. Si veda la sezione dedicata Manuale di Sviluppo dei Task di Yocto Project.

    • Consultare il Manuale di Sviluppo di Applicazioni Yocto Project e Software Development Kit (SDK/eSDK): Questo manuale descrive l'utilizzo sia dell'SDK standard sia dell'SDK estensibile, impiegati principalmente per lo sviluppo di applicazioni. Il manuale Using the Extensible SDK fornisce inoltre esempi di flussi di lavoro che utilizzano devtool. Per ulteriori informazioni, si veda la sezione Using devtool in Your SDK Workflow.

    • Studio dello Sviluppo del Kernel: Per comprendere il funzionamento del kernel e dei kernel Linux Yocto, si rimanda alla guida specifica Manuale di Sviluppo del Kernel Linux di Yocto Project. Questo manuale fornisce informazioni su come applicare patch al kernel, modificare le ricette del kernel e configurare il kernel stesso.

    • Studio dei Board Support Package (BSP): Per informazioni sui BSP, si rimanda al manuale dedicato Manuale del Board Support Package (BSP) di Yocto Project. Tale manuale fornisce anche un esempio di flusso di lavoro per la creazione di un BSP. Si veda la sezione specifica Manuale del Board Support Package (BSP) di Yocto Project.

    • Studio di Toaster: Toaster è un'interfaccia web per il sistema di build OpenEmbedded di Yocto Project. Se vi è interesse nell'utilizzo di questo tipo di interfaccia per la creazione di immagini, si rimanda al manuale di Toaster Manuale Utente di Toaster.

    • Scoprire l'estensione per VSCode: L'estensione Yocto Project BitBake per l'IDE Visual Studio Code fornisce funzionalità di linguaggio e comandi per lavorare con Yocto Project. Se vi è interesse nell'utilizzo di questa estensione, è possibile visitarne la pagina sul marketplace.

    • Tenere a portata di mano il Manuale di Riferimento di Yocto Project: A differenza degli altri manuali di Yocto Project, questo testo è composto da materiale adatto alla consultazione piuttosto che a procedure passo-passo. È possibile ottenere dettagli sulla build, un'analisi approfondita dell'integrazione dei componenti nell'ambiente di sviluppo di Yocto Project , informazioni su dettagli tecnici, indicazioni sulla migrazione a versioni più recenti di Yocto Project e materiale di riferimento su struttura delle directory, classi e task. Yocto Project Reference Manual contiene inoltre un glossario completo delle variabili utilizzate all'interno di Yocto Project.
