4 Verifica delle Vulnerabilità

4.1 Vulnerabilità in OpenEmbedded-Core (OE-Core)

Yocto Project dispone di un'infrastruttura per tracciare e risolvere le vulnerabilità di sicurezza note e non ancora corrette, monitorate dal database pubblico Common Vulnerabilities and Exposures (CVE).

Yocto Project mantiene un elenco di vulnerabilità note per i pacchetti di OpenEmbedded-Core (OE-Core), monitorando l'evoluzione del numero di CVE non ancora corrette e lo stato delle patch. Queste informazioni sono disponibili per la versione di sviluppo corrente e per ogni release supportata.

La sicurezza è un processo, non un prodotto, e pertanto, in qualsiasi momento, diversi problemi di sicurezza potrebbero interessare OpenEmbedded-Core (OE-Core). Spetta ai manutentori, agli utenti, ai collaboratori e a chiunque sia interessato ai problemi indagare e, se possibile, risolverli aggiornando i componenti software a versioni più recenti o applicando patch per correggerli. Si consiglia di collaborare con i manutentori di OpenEmbedded-Core (OE-Core) e di inviare patch per risolverli; per maggiori dettagli, consultare "Apportare Modifiche a un Componente".

4.2 Verifica delle vulnerabilità in fase di build

Per abilitare la verifica delle vulnerabilità di sicurezza CVE nell'immagine o nel target specifico che si sta compilando, eseguire il seguente comando dalla propria Build Directory:

$ bitbake-config-build enable-fragment core/yocto/sbom-cve-check

Oppure aggiungere la seguente istruzione a un configuration file:

OE_FRAGMENTS += "core/yocto/sbom-cve-check"

Questo abiliterà la classe sbom-cve-check e imporrà le impostazioni consigliate per il suo utilizzo.

Il database CVE contiene alcune voci obsolete e incomplete che sono state ritenute non rilevanti per OpenEmbedded-Core (OE-Core). È possibile escludere queste voci CVE dal controllo aggiungendo la seguente istruzione:

include conf/distro/include/cve-extra-exclusions.inc

Con il frammento core/yocto/sbom-cve-check abilitato, la build BitBake di un'immagine tenterà di mappare il nome della ricetta e le informazioni sulla versione di ciascun componente software compilato al database CVE e genererà report nella directory di distribuzione (DEPLOY_DIR_IMAGE), uno dei quali è: tmp/deploy/images/<machine>/<image-name>-<machine>.rootfs.sbom-cve-check.yocto.json, un report contenente:

  • Metadati relativi al componente software, come nomi e versioni

  • Metadati relativi al problema CVE, come descrizione e collegamento NVD

  • Per ogni componente software, un elenco di CVE che potrebbero avere un impatto su questa versione

  • Stato di ogni CVE: Patched, Unpatched o Ignored

Nota

Viene generato anche un altro report denominato <image-name>-<machine>.rootfs.sbom-cve-check.spdx.json: si tratta del file SPDX arricchito dell'immagine, contenente le stesse informazioni del punto precedente e molte più informazioni sui metadati relativi ai pacchetti inclusi nell'immagine. Per ulteriori informazioni su SPDX, consultare la sezione Creating a Software Bill of Materials del Manuale di Sviluppo dei Task di Yocto Project.

Ogni elemento nell'elenco "package" corrisponde a un pacchetto installato sull'immagine compilata. Ciascuno di questi pacchetti contiene un certo numero di voci CVE nella sottolista "issue". Queste CVE possono avere i seguenti stati:

  • Patched significa che è stato applicato un file di patch per risolvere il problema di sicurezza.

  • Unpatched significa che non sono state applicate patch per risolvere il problema e che è necessario indagare sul problema stesso.

  • Ignored significa che, dopo l'analisi, si è ritenuto opportuno ignorare il problema, ad esempio perché interessa il componente software su una piattaforma di sistema operativo diversa.

In fase di compilazione, la classe sbom-cve-check genererà anche warning relativi alle CVE Unpatched CVEs (quando SBOM_CVE_CHECK_SHOW_WARNINGS è impostato su "1"):

WARNING: core-image-minimal-1.0-r0 do_sbom_cve_check: glibc-2.43+git: Found unpatched CVEs: CVE-2010-4756

4.3 Correzione delle mappature tra nome prodotto e versione CVE

Per default, sbom-cve-check utilizza il nome della ricetta BPN come nome prodotto CVE quando interroga il database CVE. Se questa mappatura contiene falsi positivi, ad esempio Alcune vulnerabilità CVE segnalate potrebbero non riguardare il componente software in questione, oppure potrebbero verificarsi falsi negativi, ad esempio alcune vulnerabilità CVE non risultano avere un impatto sulla ricetta quando invece dovrebbero. In questi casi, il problema potrebbe risiedere nella mappatura tra il nome della ricetta e il prodotto CVE. Questi problemi di mappatura possono essere risolti impostando la variabile CVE_PRODUCT all'interno della ricetta. Questa variabile definisce il nome del componente software nel database CVE NIST upstream.

La variabile supporta l'utilizzo di nomi di fornitori e prodotti come segue:

CVE_PRODUCT = "flex_project:flex westes:flex"

In questo esempio, abbiamo due possibili nomi di fornitori, flex_project e westes, con il nome del prodotto flex. Con questa impostazione, la ricetta flex viene mappata solo a questo specifico prodotto e non a prodotti di altri fornitori con lo stesso nome flex.

Analogamente, quando la versione della ricetta PV non è compatibile con le versioni del software utilizzate dalle release dei componenti software a monte e con il database CVE, è possibile risolvere il problema utilizzando la variabile CVE_VERSION.

Si noti che se le voci CVE nel database NVD contengono bug o informazioni mancanti o incomplete, si consiglia di correggere direttamente le informazioni nel database stesso, anziché cercare di aggirare i problemi, eventualmente per lungo tempo, nelle ricette di OpenEmbedded-Core (OE-Core). È possibile fornire feedback a NVD in merito alle voci CVE tramite il modulo di contatto NVD.

4.4 Correzione delle vulnerabilità nelle ricette

Supponiamo che una vulnerabilità di sicurezza CVE interessi un componente software. In tal caso, è possibile risolverla aggiornando a una versione più recente, applicando una patch o contrassegnandola come "patched" tramite il flag della variabile CVE_STATUS. Per i branch master di OpenEmbedded-Core (OE-Core), l'aggiornamento a una versione più recente del componente software con le correzioni è l'opzione migliore, ma è possibile applicare delle patch se le versioni non sono ancora disponibili.

Per i branch stabili, è preferibile evitare incompatibilità con le API (Application Programming Interface) o le ABI (Application Binary Interface). Quando si invia un aggiornamento, è preferibile un aggiornamento a una versione minore del componente se la versione è retrocompatibile. Molti componenti software hanno versioni stabili retrocompatibili, con un esempio notevole del kernel Linux. Tuttavia, se la nuova versione introduce o potrebbe introdurre incompatibilità, è preferibile estrarre e applicare le patch.

Ecco un esempio di come correggere le vulnerabilità di sicurezza CVE con i file di patch, tratto dalla ricetta ffmpeg recipe per dunfell:

SRC_URI = "https://www.ffmpeg.org/releases/${BP}.tar.xz \
           file://mips64_cpu_detection.patch \
           file://CVE-2020-12284.patch \
           file://0001-libavutil-include-assembly-with-full-path-from-sourc.patch \
           file://CVE-2021-3566.patch \
           file://CVE-2021-38291.patch \
           file://CVE-2022-1475.patch \
           file://CVE-2022-3109.patch \
           file://CVE-2022-3341.patch \
           file://CVE-2022-48434.patch \
       "

La ricetta include sia correzioni generiche che specifiche per la sicurezza. I file di patch CVE prendono il nome dalla vulnerabilità CVE che correggono.

Quando si prepara il file di patch, utilizzare la patch originale dal repository upstream. Non utilizzare patch provenienti da distribuzioni diverse, a meno che non siano l'unica fonte disponibile.

Modificare la patch aggiungendo i metadati relativi a OE. Seguiremo l'esempio della patch CVE-2022-3341.patch.

Il messaggio di commit originale è:

From 9cf652cef49d74afe3d454f27d49eb1a1394951e Mon Sep 17 00:00:00 2001
From: Jiasheng Jiang <jiasheng@iscas.ac.cn>
Date: Wed, 23 Feb 2022 10:31:59 +0800
Subject: [PATCH] avformat/nutdec: Add check for avformat_new_stream

Check for failure of avformat_new_stream() and propagate
the error code.

Signed-off-by: Michael Niedermayer <michael@niedermayer.cc>
---
 libavformat/nutdec.c | 16 ++++++++++++----
 1 file changed, 12 insertions(+), 4 deletions(-)

Per il corretto funzionamento di sbom-cve-check, è necessario includere l'identificativo CVE nel tag CVE: del messaggio di commit del file patch, utilizzando il seguente formato:

CVE: CVE-2022-3341

È inoltre necessario aggiungere il tag Upstream-Status: con un link alla patch originale e la firma del team che ha lavorato al backport. Eventuali modifiche alla patch originale devono essere annotate nel tag Comments:.

Con queste informazioni aggiuntive, l'header del file patch in OE-core diventa:

From 9cf652cef49d74afe3d454f27d49eb1a1394951e Mon Sep 17 00:00:00 2001
From: Jiasheng Jiang <jiasheng@iscas.ac.cn>
Date: Wed, 23 Feb 2022 10:31:59 +0800
Subject: [PATCH] avformat/nutdec: Add check for avformat_new_stream

Check for failure of avformat_new_stream() and propagate
the error code.

Signed-off-by: Michael Niedermayer <michael@niedermayer.cc>

CVE: CVE-2022-3341

Upstream-Status: Backport [https://github.com/FFmpeg/FFmpeg/commit/9cf652cef49d74afe3d454f27d49eb1a1394951e]

Comments: Refreshed Hunk
Signed-off-by: Narpat Mali <narpat.mali@windriver.com>
Signed-off-by: Bhabu Bindu <bhabu.bindu@kpit.com>
---
 libavformat/nutdec.c | 16 ++++++++++++----
 1 file changed, 12 insertions(+), 4 deletions(-)

Una buona pratica consiste nell'includere l'identificativo CVE nel nome del file patch, nel messaggio di commit del file patch e, facoltativamente, nel messaggio di commit della ricetta.

sbom-cve-check acquisirà quindi queste informazioni e modificherà lo stato del CVE in Patched nei report generati.

Se l'analisi mostra che il problema CVE non ha un impatto sulla ricetta a causa della configurazione, della piattaforma, della versione o di altri motivi, il CVE può essere contrassegnato come Ignored utilizzando il flag della variabile CVE_STATUS con il motivo appropriato, che viene mappato a Ignored. La voce dovrebbe avere il seguente formato:

CVE_STATUS[CVE-2016-10642] = "cpe-incorrect: This is specific to the npm package that installs cmake, so isn't relevant to OpenEmbedded"

Come accennato in precedenza, se i dati nel database CVE sono errati, si consiglia di correggere tali problemi direttamente nel database CVE (NVD nel caso di OpenEmbedded-Core (OE-Core)).

Si noti che se sono presenti più CVE con lo stesso stato e motivo, questi possono essere condivisi utilizzando la variabile CVE_STATUS_GROUPS.

Quando si analizzano le CVE, si raccomanda di:

  • studiare le informazioni più recenti nel database CVE.

  • verificare come gli sviluppatori del componente software hanno affrontato il problema, ad esempio quale patch è stata applicata e quale release contiene la correzione.

  • controllare cosa hanno fatto altre distribuzioni Linux, come Debian, per analizzare e risolvere il problema.

  • seguire gli avvisi di sicurezza di altre distribuzioni Linux.

  • seguire le mailing list pubbliche sulla sicurezza open source per discussioni e notifiche anticipate sui bug CVE e sulle release software con le relative correzioni.

4.5 Dettagli di implementazione

Poiché sbom-cve-check è un tool esterno, la sua implementazione è descritta in dettaglio nella documentazione ufficiale: https://sbom-cve-check.readthedocs.io/en/latest/index.html

4.6 Vulnerabilità del kernel Linux

Dal momento che il kernel Linux è diventato un CVE Numbering Authority (CNA), i numero di CVE associato è aumentato drammaticamente. I team di sicurezza devono affrontare questi CVE per soddisfare i requisiti normativi e dei clienti. L'automazione sull'identificazione dei problemi aiuta a ridurre il carico di lavoro.

OpenEmbedded-Core (OE-Core) dispone di due script che aiutano a caratterizzare e filtrare le CVE che interessano il kernel Linux:

  • openembedded-core/meta/recipes-kernel/linux/generate-cve-exclusions.py

  • openembedded-core/scripts/contrib/improve_kernel_cve_report.py

4.6.1 generate-cve-exclusions.py

Quando si aggiorna una ricetta del kernel, è necessario eseguire manualmente uno script di supporto per aggiornare il CVE_STATUS per la ricetta del kernel. Lo script può essere utilizzato per i kernel personalizzati.

Prima dobbiamo ottenere una versione aggiornata delle informazioni CVE dal CVE Project. Eseguirlo in questo modo:

$ git clone https://github.com/CVEProject/cvelistV5 ~/cvelistV5

Oppure, se è stato già clonato il repository, si devono scaricare i dati più recenti:

$ git -C ~/cvelistV5 pull

Successivamente, generare le informazioni CVE_STATUS per la versione desiderata del kernel:

$ ./generate-cve-exclusions.py ~/cvelistV5 <version> > cve-exclusion_<kernel_version>.inc

Esempio

$ git clone https://github.com/CVEProject/cvelistV5 ~/cvelistV5
$ cd openembedded-core/meta/recipes-kernel/linux/
$ ./generate-cve-exclusions.py ~/cvelistV5 6.12.27 > ~/meta-custom/recipes-kernel/linux/cve-exclusion_6.12.inc

Non dimenticare di aggiornare la ricetta del kernel con:

include cve-exclusion_6.12.inc

A questo punto, le informazioni CVE verranno aggiunte automaticamente al report cve-check o vex.

4.6.2 improve_kernel_cve_report.py

Lo script openembedded-core/scripts/contrib/improve_kernel_cve_report.py sfrutta i metadati CVE del kernel e la variabile SPDX_INCLUDE_COMPILED_SOURCES per aggiornare un file di report di output .sbom-cve-check.yocto.json (vedere la sezione Verifica delle vulnerabilità in fase di build per i dettagli su questi file di report). Riduce i falsi positivi CVE del 70%-80% e fornisce risposte dettagliate per tutte le CVE relative al kernel analizzando i file utilizzati per la compilazione del kernel. Lo script è indipendente dal processo di compilazione e può essere eseguito al di fuori dell'ambiente BitBake.

Lo script utilizza l'output di vex come input, insieme alle informazioni CVE del kernel Linux CNA, per arricchire il file di report con informazioni CVE aggiornate.

Il nome del file può essere specificato come argomento. Facoltativamente, può anche utilizzare l'elenco dei file compilati dal kernel SPDX per ignorare le CVE non interessate perché i file non sono stati compilati.

A tal fine, BitBake utilizza le informazioni di debug per estrarre i sorgenti utilizzati per la creazione di un binario. Pertanto, è necessario configurarlo nel kernel per estrarre i file compilati dal kernel.

Se si utilizza la ricetta linux-yocto, abilitarla aggiungendo quanto segue in un configuration file o in un file .bbappend:

KERNEL_EXTRA_FEATURES:append = " features/debug/debug-kernel.scc"

Oppure modificando la configurazione del kernel per includere le informazioni di debug di DWARF4.

Per ulteriori informazioni, consultare la sezione Changing the Configuration del Manuale di Sviluppo del Kernel Linux di Yocto Project.

Nell'esempio seguente, considereremo come ricetta del kernel utilizzata linux-yocto. Le istruzioni si applicano anche ad altre ricette del kernel con nomi diversi.

I sorgenti del kernel sono memorizzati in tmp/pkgdata/<MACHINE>/debugsources/linux-yocto-debugsources.json.zstd. Per includere le informazioni nel file SPDX e filtrare i file sorgente non utilizzati per la compilazione del kernel, aggiungere quanto segue in un configuration file:

SPDX_INCLUDE_COMPILED_SOURCES:pn-linux-yocto = "1"

Infine, salvare il file recipe-linux-yocto.spdx.json o il file linux-yocto-debugsources.json.zstd al di fuori della build directory.

Il file SPDX si trova in tmp/deploy/spdx/<spdx_version>/<MACHINE>/recipes/recipe-linux-yocto.spdx.json

Una volta ottenuti i dati di input, è necessario clonare o scaricare le informazioni CVE più recenti da https://git.kernel.org:

$ git clone https://git.kernel.org/pub/scm/linux/security/vulns.git ~/vulns

Oppure, se già presenti per un checkout:

$ git -C ~/vulns pull

Infine, eseguire lo script utilizzando uno degli esempi seguenti. I primi due esempi sono i più precisi e utilizzano il vecchio file cve-summary.json.

  • Esempio con --old-cve-report come input:

    $ python3 openembedded-core/scripts/contrib/improve_kernel_cve_report.py \
   --spdx tmp/deploy/spdx/3.0.1/qemux86_64/recipes/recipe-linux-yocto.spdx.json \
   --datadir ~/vulns \
   --old-cve-report build/tmp/deploy/images/<machine>/<image-name>-<machine>.rootfs.sbom-cve-check.yocto.json

  • Esempio con il file --debug-sources al posto del file del kernel SPDX:

    $ python3 openembedded-core/scripts/contrib/improve_kernel_cve_report.py \
   --debug-sources tmp/pkgdata/qemux86_64/debugsources/linux-yocto-debugsources.json.zstd \
   --datadir ~/vulns \
   --old-cve-report build/tmp/deploy/images/<machine>/<image-name>-<machine>.rootfs.sbom-cve-check.yocto.json

  • Esempio con --kernel-version:

    $ python3 openembedded-core/scripts/contrib/improve_kernel_cve_report.py \
   --spdx tmp/deploy/spdx/3.0.1/qemux86_64/recipes/recipe-linux-yocto.spdx.json \
   --kernel-version 6.12.27 \
   --datadir ~/vulns

Esempio di output per una CVE il cui stato è stato modificato in "Ignored" perché i file sorgente associati alla CVE non sono stati compilati:perché i file sorgente associati alla CVE non sono stati compilati:

{
   "id": "CVE-2025-38384",
   "status": "Ignored",

   "description": "Source code not compiled by config. {'drivers/mtd/nand/spi/core.c'}"
}

{
   "id": "CVE-2025-40017",
   "status": "Patched",

   "summary": "In the Linux kernel, the following vulnerability has been resolved (...)",

}

Esempio di output per una CVE vulnerabile:

{
   "id": "CVE-2024-58093",
