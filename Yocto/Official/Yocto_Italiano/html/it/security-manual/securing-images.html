3 Come Rendere le Immagini più Sicure

Quando la sicurezza di un'immagine è una priorità, esistono passaggi, strumenti e variabili da considerare per raggiungere gli obiettivi di sicurezza necessari per il proprio dispositivo. Non tutte le situazioni sono identiche quando si tratta di proteggere un'immagine. Pertanto, questa sezione fornisce alcune indicazioni e suggerimenti da tenere in considerazione quando si desidera rendere la propria immagine più sicura.

Nota

Poiché i requisiti e i rischi per la sicurezza variano a seconda del tipo di dispositivo, questa sezione non può fornire un riferimento completo sulla protezione del proprio sistema operativo personalizzato. Si raccomanda vivamente di consultare anche altre fonti di informazione sulla protezione dei sistemi Linux embedded e sulla sicurezza in generale.

3.1 Considerazioni Generali

Esistono considerazioni generali che possono aiutare a creare immagini più sicure. Per rendere il dispositivo più sicuro, si devono tenere in considerazione i seguenti suggerimenti:

  • Analizzare [scan] il codice aggiuntivo che si sta inserendo nel sistema (ad esempio, il codice dell'applicazione) utilizzando strumenti di analisi statica. Cercare buffer overflow e altri potenziali problemi di sicurezza.

  • Prestare particolare attenzione alla sicurezza di qualsiasi interfaccia di amministrazione basata sul web.

    Le interfacce web in genere devono svolgere funzioni amministrative e tendono a richiedere privilegi elevati. Pertanto, le conseguenze derivanti da una compromissione della sicurezza dell'interfaccia possono essere gravi. Cerca vulnerabilità web comuni come cross-site scripting (XSS), input non validati e così via.

    Come per le password di sistema, le credenziali di default per accedere a un'interfaccia basata sul web non dovrebbero essere le stesse su tutti i dispositivi. Questo è particolarmente vero se l'interfaccia è abilitata di default, poiché si può presumere che molti utenti finali non modificheranno le credenziali.

  • Si deve poter aggiornare il software sul dispositivo per mitigare le vulnerabilità che potrebbero essere scoperte in futuro. Questa considerazione è particolarmente importante quando il dispositivo è connesso alla rete.

  • Eseguire regolarmente scansioni e applicare le correzioni per le vulnerabilità di sicurezza CVE che interessano tutti i componenti software del prodotto. Vedere "Verifica delle Vulnerabilità".

  • Aggiornare regolarmente la versione di BitBake e dei layer (ad esempio OpenEmbedded-Core (OE-Core), meta-yocto, ...), ad esempio per applicare aggiornamenti e correzioni di sicurezza dai branch stable e LTS.

  • Rimuovere o disabilitare la funzionalità di debug prima di generare l'immagine finale. Per informazioni su come procedere, consultare la sezione "Considerazioni Specifiche per il Sistema di Build OpenEmbedded".

  • Non ci devono essere in ascolto servizi di rete non necessari.

  • Rimuovere dall'immagine qualsiasi software non necessario.

  • Abilitare il supporto hardware per la funzionalità di avvio protetto (Secure Boot) se il dispositivo la supporta.

3.2 Flag di Sicurezza

Yocto Project dispone di flag di sicurezza che è possibile abilitare per rendere più sicuro l'output della build. I flag di sicurezza si trovano nel file meta/conf/distro/include/security_flags.inc all'interno di OpenEmbedded-Core (OE-Core).

Nota

A seconda della ricetta, alcuni flag di sicurezza sono abilitati o disabilitati per impostazione predefinita.

Utilizzare la seguente riga nel file build/conf/local.conf o nel configuration file della propria distribuzione per abilitare i flag di sicurezza del compilatore e del linker per la build:

require conf/distro/include/security_flags.inc

3.3 Considerazioni Specifiche per il Sistema di Build OpenEmbedded

È possibile adottare alcune misure specifiche per il sistema di build OpenEmbedded per rendere le immagini più sicure:

  • Durante lo sviluppo, è utile ridurre il livello di sicurezza delle build e consentire l'utilizzo di password vuote o accessi come root. Questo viene generalmente fatto aggiungendo i valori "allow-empty-password", "allow-root-login" e "empty-root-password" alle funzionalità dell'immagine di build, solitamente aggiungendo la riga:

    EXTRA_IMAGE_FEATURES = "allow-empty-password empty-root-password allow-root-login"

    al configuration file della propria distribuzione, oppure abilitando il frammento di configurazione esattamente equivalente core/yocto/root-login-with-empty-password.

    Se si utilizza uno di questi approcci durante lo sviluppo, si devono rimuovere o disattivare queste impostazioni prima di generare l'immagine di produzione finale.

  • È possibile impostare una password di root per l'immagine e anche impostare password per eventuali utenti aggiuntivi (ad esempio, utenti amministrativi o di servizio). Quando si impostano password per più immagini o utenti, è importante non duplicarle.

    Per impostare le password, utilizzare la classe extrausers, che è il metodo consigliato. Per un esempio su come impostare le password di root e degli utenti, consultare la sezione "extrausers".

    Nota

    Quando si aggiungono ulteriori account utente o si imposta una password di root, prestare attenzione a non utilizzare la stessa password su tutti i dispositivi. In tal caso, se la password impostata viene esposta, tutti i dispositivi potrebbero essere compromessi. Se è necessario questo accesso ma si desidera garantire la sicurezza, è consigliabile impostare una password diversa e casuale per ogni dispositivo. In genere, questa operazione viene eseguita separatamente dopo aver distribuito l'immagine sul dispositivo.

  • Si consiglia di abilitare un framework di controllo degli accessi obbligatorio (MAC) come SMACK o SELinux e di configurarlo in modo appropriato in base all'utilizzo del dispositivo. Maggiori informazioni nel layer meta-selinux.

3.4 Tool per Rafforzare la Sicurezza dell'Immagine

Yocto Project fornisce strumenti per rendere l'immagine più sicura. Si possono trovare questi strumenti nel layer meta-security dei Repository del Codice Sorgente di Yocto Project.
