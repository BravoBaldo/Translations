5 Creazione di un Filesystem Root di Sola Lettura

Supponiamo che, per motivi di sicurezza, sia necessario disabilitare i permessi di scrittura del filesystem root del dispositivo di target (ovvero, sia necessario un filesystem root di sola lettura). Oppure, si potrebbe eseguire il sistema operativo del dispositivo da un'unità di archiviazione di sola lettura. In entrambi i casi, è possibile personalizzare l'immagine per ottenere tale comportamento.

Nota

Il supporto di un filesystem root di sola lettura richiede che il sistema e le applicazioni non tentino di scrivere sul filesystem root. È necessario configurare tutte le parti del sistema di target in modo che scrivano altrove o che interrompano l'operazione in modo controllato qualora tentassero di scrivere sul filesystem root.

5.1 Creazione del Filesystem Root

Per creare il filesystem root di sola lettura, è sufficiente aggiungere la funzionalità "read-only-rootfs" all'immagine, solitamente in uno dei due modi seguenti. Il primo metodo consiste nell'aggiungere la funzionalità "read-only-rootfs" al file di configurazione dell'immagine tramite la variabile IMAGE_FEATURES:

IMAGE_FEATURES += "read-only-rootfs"

In alternativa, è possibile aggiungere la stessa funzionalità dal configuration file della propria distribuzione utilizzando la variabile EXTRA_IMAGE_FEATURES associata, come segue:

EXTRA_IMAGE_FEATURES = "read-only-rootfs"

Per ulteriori informazioni sull'utilizzo di queste variabili, consultare la sezione "Customizing Images Using Custom IMAGE_FEATURES and EXTRA_IMAGE_FEATURES". Per informazioni sulle variabili, consultare i documenti IMAGE_FEATURES e EXTRA_IMAGE_FEATURES.

5.2 Script di Post-Installazione e Filesystem Root di Sola Lettura

È fondamentale assicurarsi che tutti gli script di post-installazione (pkg_postinst) per i pacchetti installati nell'immagine possano essere eseguiti al momento della creazione del filesystem root durante la compilazione sul sistema host. Questi script non possono essere eseguiti al primo avvio del dispositivo target. Con la funzionalità "read-only-rootfs" abilitata, il sistema di build si assicura che tutti gli script di post-installazione vengano eseguiti correttamente al momento della creazione del filesystem. Se uno qualsiasi di questi script deve ancora essere eseguito dopo la creazione del filesystem root, la compilazione fallisce immediatamente. Questi controlli in fase di build garantiscono che sia la compilazione a fallire, anziché il dispositivo target a fallire in un secondo momento durante il suo boot iniziale.

La maggior parte degli script di post-installazione comuni generati dal sistema di build per Yocto Project di default sono progettati per essere eseguiti durante la creazione del filesystem root (ad esempio, gli script di post-installazione per la cache dei font). Tuttavia, se si creano e si aggiungono script personalizzati, è necessario assicurarsi che possano essere eseguiti durante la creazione del filesystem.

Ecco alcuni problemi comuni che impediscono l'esecuzione degli script di post-installazione durante la creazione del filesystem root:

  • Mancato utilizzo di $D davanti ai path assoluti: Il sistema di build definisce $D quando viene creato il filesystem root. Inoltre, $D è vuoto quando lo script viene eseguito sul dispositivo target. Ciò implica due scopi per $D: garantire che i path siano validi sia nell'ambiente host che in quello target e verificare quale ambiente viene utilizzato per intraprendere le azioni appropriate.

  • Tentativo di eseguire processi specifici o dipendenti dall'architettura target: È possibile ovviare a questi tentativi utilizzando strumenti nativi, che vengono eseguiti sul sistema host, per svolgere le stesse attività [task], oppure eseguendo i processi in QEMU, che dispone della funzione qemu_run_binary. Per ulteriori informazioni, consultare la classe qemu.

5.3 Aree con Accesso in Scrittura

Con la funzionalità "read-only-rootfs" abilitata, qualsiasi tentativo da parte del sistema target di scrivere sul filesystem di root in fase di esecuzione fallisce. Di conseguenza, è necessario assicurarsi che i processi e le applicazioni che tentano questo tipo di scritture lo facciano su directory con accesso in scrittura (ad esempio /tmp o /var/run).
