4 Rilasci di Yocto Project e Iter dei Rilasci Stabili

Il processo di rilascio di Yocto Project è prevedibile e consiste in rilasci principali [major] e secondari [minor] (punto). Questo breve capitolo fornisce informazioni su come vengono denominati i rilasci, sul loro ciclo di vita e sulla loro stabilità.

4.1 Cadenza dei Rilasci Major e Minor

Yocto Project ha rilasci "major" (ad esempio la 6.1) con una cadenza di sei mesi, all'incirca ad aprile e ottobre di ogni anno. Ecco alcuni esempi di rilasci principali di YP con i relativi nomi in codice. Consultare la sezione "Nomi in Codice delle Release Major" per informazioni sui nomi in codice utilizzati per i rilasci principali [major].

  • 4.1 ("Langdale")

  • 4.0 ("Kirkstone")

  • 3.4 ("Honister")

Sebbene la cadenza non sia mai perfetta, questa tempistica facilita rilasci regolari con cicli di QA rigorosi, senza sovraccaricare gli utenti con troppi nuovi rilasci. La cadenza di rilascio è prevedibile ed evita molte festività importanti in diverse aree geografiche.

Yocto project rilascia versioni minori (point) in modo non programmato, solitamente in seguito all'accumulo di un numero sufficiente di correzioni o miglioramenti significativi alla versione principale associata. Alcuni esempi di versioni minori precedenti sono:

  • 4.1.3

  • 4.0.8

  • 3.4.4

Il punto della release indica un punto nel ramo della versione principale in cui un ciclo completo di controllo qualità e processo di rilascio convalida il contenuto del nuovo ramo [branch].

Nota

È importante notare che le patch possono essere integrate nei rami della versione stabile non appena disponibili.

4.2 Ciclo di Sviluppo

Come spiegato nella precedente sezione Cadenza dei Rilasci Major e Minor, una nuova release viene rilasciata ogni sei mesi.

Durante questo periodo di sei mesi, Yocto Project rilascia quattro release "Milestone" che rappresentano punti di riferimento distinti. Le release milestone vengono testate attraverso il processo Test e Garanzia di Qualità, che aiuta a individuare i problemi prima del rilascio effettivo.

L'intervallo di tempo tra le release milestone può variare, ma in genere sono distribuite uniformemente durante questo periodo di sei mesi.

Queste release milestone sono contrassegnate da una "M" maiuscola dopo il nome della release futura. Ad esempio, le release milestone "6.1M1", "6.1M2" e "6.1M3" vengono rilasciate prima della release "6.1" vera e propria.

Nota

La quarta milestone (M4) non viene effettivamente rilasciata e annunciata, ma rappresenta un momento in cui il team di Controllo Qualità avvia il processo di Test e Garanzia di Qualità prima di etichettare e rilasciare la versione finale.

Dopo la terza release (M3), Yocto Project entra in Feature Freeze. Ciò significa che i manutentori di OpenEmbedded-Core (OE-Core), BitBake e altri repository centrali smettono di accettare modifiche significative sul branch "master". Le modifiche che possono essere accettate sono piccoli aggiornamenti ai componenti principali e correzioni di bug/sicurezza.

Durante il periodo di Feature Freeze, viene creato e gestito separatamente un nuovo branch [ramo] per testare le nuove funzionalità e i miglioramenti ricevuti dai collaboratori, ma queste modifiche verranno integrate nel branch master solo dopo il rilascio della release.

4.3 Nomi in Codice delle Release Major

Ogni release major riceve un nome in codice che la identifica nei I Repository del Codice Sorgente di Yocto Project. L'idea è che i branche di Metadata con lo stesso nome in codice siano probabilmente compatibili e quindi funzionino insieme.

Nota

I nomi in codice sono associati alle release principali perché un numero di release di Yocto Project (ad esempio 6.1) potrebbe entrare in conflitto con un determinato layer o schema di versioning aziendale. I nomi in codice sono univoci, interessanti e facilmente identificabili.

Anche alle release viene assegnata una versione nominale, ma il nome in codice viene utilizzato nei repository per questo scopo. Informazioni sulle release e sui nomi in codice di Yocto Project si trovano nella pagina pagina dei rilasci.

La nostra Informazioni sulla Release descrive in dettaglio come migrare da una release di Yocto Project alla successiva.

4.4 Iter per il Rilascio Stabile

Una volta rilasciata, la release entra nel processo di rilascio stabile, momento in cui viene assegnata una persona come responsabile della manutenzione per quella release stabile. Questo responsabile monitora l'attività relativa alla release, esaminando e gestendo le patch proposte e le attività di backport. Solo le correzioni e i miglioramenti che sono stati prima applicati sul branch "master" (ovvero il ramo corrente in fase di sviluppo) vengono presi in considerazione per il backporting in una release stabile.

Nota

L'attuale politica di Yocto Project in merito al backporting prevede di considerare solo le correzioni di bug e le patch di sicurezza. La politica stabilisce che le nuove funzionalità non vengono retroportate in una release stabile. Questa politica implica che gli aggiornamenti generici di versione delle ricette difficilmente verranno accettati per il backporting. L'eccezione a questa politica si verifica quando esiste una valida ragione, ad esempio quando la correzione è anche l'approccio preferito a monte [upstream].

4.5 Politiche di Accettazione delle Patch per le Release Stabili/LTS

Tutte le modifiche devono essere già state accettate nella release master corrente e in qualsiasi altra release ancora all'interno del suo periodo di supporto stabile.

Accettabile:

  • Correzioni di sicurezza e CVE

  • Correzioni di bug

  • Aggiornamenti di versione che seguono una serie stabile o LTS upstream allineata alla release originale (in base alla compatibilità). Per maggiori dettagli, consultare Aggiornamenti a Release Stabili.

Nota

Una volta che UPSTREAM_STABLE_RELEASE_REGEX è stato accettato per una ricetta, gli aggiornamenti di versione che corrispondono al modello accettato sono considerati accettabili per default (con la possibilità di rifiutarli se la versione upstream non segue le proprie linee guida per le versioni stabili).

Potenzialmente accettabili:

  • Correzioni per rendere il codice sorgente compatibile con le distribuzioni appena rilasciate, ad esempio aggiornamenti del tarball uninative o correzioni di compilazione per una nuova versione di GCC sul Build Host.

Inaccettabile:

  • Aggiornamenti di versione generali

  • Nuove funzionalità

  • Modifiche all'ABI/API

  • Miglioramenti e refactoring dei metadati, a meno che non siano una dipendenza di una correzione necessaria

Nota

Eventuali eccezioni a queste regole devono essere approvate dal TSC.

4.6 Aggiornamenti a Release Stabili

Alcuni progetti upstream mantengono branch stabili che includono solo correzioni di bug e patch di sicurezza, in modo simile alla politica di rilascio stabile di Yocto Project. Per le ricette che seguono tali progetti upstream, è possibile eseguire stable point release upgrades [aggiornamenti a release stabili] (ad esempio, l'aggiornamento dalla versione 1.0.2 alla 1.0.3) anziché accettare solo patch retroportate. Questo è il meccanismo alla base della politica "accettabili: aggiornamenti di versione che seguono una serie stabile upstream" descritta sopra.

4.6.1 Criteri per l'Approvazione degli Upstream

Impostando UPSTREAM_STABLE_RELEASE_REGEX per una ricetta, determinati aggiornamenti di versione possono essere considerati con sicurezza come aggiornamenti stabili secondo i criteri di OpenEmbedded. L'Automated Upgrade Helper (AUH) invierà automaticamente le patch per aggiornare le ricette con questa variabile impostata durante le release stabili.

Nota

È comunque possibile inviare patch per aggiornare ricette senza questa variabile per i branch stabili, ma la soglia di accettazione è elevata. Il messaggio di commit deve giustificare che l'aggiornamento di versione segue la nostra politica per i branch stabili o che esiste un motivo eccezionale per effettuare l'aggiornamento.

Una ricetta può avere UPSTREAM_STABLE_RELEASE_REGEX impostato in base ai seguenti criteri:

  1. Esistono rami [branch] stabili upstream --- il progetto upstream mantiene rami denominati con un componente di versione stabile, ed esiste la prova che questi rami raccolgono solo correzioni di bug e aggiornamenti di sicurezza (nessuna nuova funzionalità o modifica di ABI/API). Ad esempio, la versione 2.41.3 di util-linux ha tre parti nella sua versione e upstream ha rami come stable/v2.41 con due parti. Ciò dimostra che gli incrementi nella terza parte (ad esempio da 2.41.3 a 2.41.4) sono release stabili. Allo stesso modo, systemd mantiene stable/v259-stable.

E almeno uno dei seguenti:

  1. Conferma del manutentore upstream --- il manutentore del progetto upstream conferma esplicitamente che un incremento in una determinata parte della versione riguarda solo la correzione di bug.

  2. Prove storiche o di buon senso inequivocabili --- la cronologia delle modifiche del progetto mostra chiaramente che una determinata classe di aggiornamenti di versione riguarda solo la correzione di bug, oppure è una convenzione ampiamente riconosciuta. Ad esempio, gli incrementi del suffisso p di openssh (da 10.2p1 a 10.2p2) e gli aggiornamenti di livello di patch di kmod sono storicamente rilasci che riguardano solo la correzione di bug.

Nota

Le patch per impostare UPSTREAM_STABLE_RELEASE_REGEX vengono inviate prima al ramo master e seguono il normale processo di revisione. Una volta accettate su master, possono essere retroportate ai rami di rilascio stabili. Possono essere fatte delle eccezioni quando necessario, ad esempio impostando UPSTREAM_STABLE_RELEASE_REGEX su un ramo stabile per una ricetta che è stata successivamente rimossa su master.

4.6.2 Come Funzionano le Espressioni Regolari per le Release Stabili

Il meccanismo di aggiornamento a punto stabile utilizza un filter regex [espressione regolare di filtro] per limitare il controllo della versione upstream, in modo che vengano considerate solo le versioni appartenenti alla stessa serie stabile. Quando una ricetta imposta UPSTREAM_STABLE_RELEASE_REGEX, l'infrastruttura di controllo della versione nei fetcher di BitBake (git, wget, crate) applica tale espressione regolare per filtrare le versioni upstream rilevate. Solo le versioni che corrispondono all'espressione regolare vengono considerate come potenziali aggiornamenti.

Ad esempio, se una ricetta è attualmente alla versione 1.4.2 e l'espressione regolare è ^1\.4(\.\d+)*$, la versione 1.4.7 sarebbe una valida candidata all'aggiornamento, mentre la versione 1.5.0 non lo sarebbe.

Per le ricette la cui versione utilizza uno schema separato da punti, la classe upstream-stable-release-point può generare automaticamente questa espressione regolare. Per altri schemi di versioning, impostare UPSTREAM_STABLE_RELEASE_REGEX direttamente nella ricetta.

4.7 Versioni con Supporto a Lungo Termine

Mentre le versioni stabili sono supportate per una durata di sette mesi, alcune versioni specifiche sono ora supportate per un periodo più lungo da Yocto Project e sono chiamate versioni Long Term Support (LTS).

Quando vengono rilevati problemi significativi, le versioni LTS consentono di pubblicare correzioni non solo per la versione stabile corrente, ma anche per le versioni LTS ancora supportate. Le versioni stabili più vecchie che hanno raggiunto la fine del loro ciclo di vita [End of Life] (EOL) non riceveranno tali aggiornamenti.

Questo è iniziato con la versione 3.1 ("Dunfell"), rilasciata nell'aprile 2020, che il progetto inizialmente si era impegnato a supportare per due anni, ma questa durata è stata successivamente estesa a quattro anni.

Una nuova versione LTS viene rilasciata ogni due anni ed è supportata per quattro anni. Questo offre maggiore stabilità agli utenti del progetto e lascia più tempo per l'aggiornamento alla successiva versione LTS.

Le versioni LTS attualmente supportate sono:

  • Versione 6.0 ("Wrynose"), rilasciata a maggio 2026 e supportata fino ad aprile 2030.

  • Versione 5.0 ("Scarthgap"), rilasciata ad aprile 2024 e supportata fino ad aprile 2028.

Consultare https://wiki.yoctoproject.org/wiki/Stable_Release_and_LTS per i dettagli sulla gestione delle versioni stabili e LTS.

Questa documentazione è stata creata per la versione Blacksail.

Nota

In alcuni casi, la community può creare un layer per aggiungere una funzionalità specifica o supportare una nuova versione di un pacchetto per una versione LTS. Questo viene chiamato layer Mixin. Si tratta di layer sottili e specifici che possono essere sovrapposti a una release LTS per "integrare" una funzionalità specifica in quella build. Vengono creati in base alle necessità e gestiti da chi ne ha bisogno.

Le politiche di test di questi layer dipendono dalla loro diffusione e vengono determinate caso per caso. È possibile trovare alcuni layer Mixin nel repository meta-lts-mixins. Sebbene il Yocto Project fornisca l'hosting per questi repository, non si occupa del loro test. Altri layer Mixin potrebbero essere rilasciati altrove dalla community.

4.8 Test e Garanzia di Qualità

Parte del processo di sviluppo e rilascio di Yocto Project è la garanzia di qualità attraverso l'esecuzione di strategie di test. Le strategie di test forniscono al team di Yocto Project un modo per garantire che una release sia valida. Inoltre, poiché le strategie di test sono visibili agli sviluppatori, è possibile validare i propri progetti. Questa sezione fornisce una panoramica dell'infrastruttura di test disponibile utilizzata in Yocto Project. Per informazioni su come eseguire i test disponibili sui propri progetti, consultare la sezione "Performing Automated Runtime Testing" nel Manuale dell'Ambiente di Test di Yocto Project.

L'infrastruttura di QA/testing è talmente integrata nel progetto che gli sviluppatori principali la danno per scontata. L'infrastruttura è composta dai seguenti elementi:

  • bitbake-selftest: Un comando standalone che esegue unit test su componenti chiave di BitBake e sui suoi fetcher.

  • sanity: Questa classe, inclusa automaticamente, verifica la presenza di strumenti mancanti nell'ambiente di build (ad esempio gcc) o di errori di configurazione comuni, come ad esempio un parametro MACHINE impostato in modo errato.

  • insane: Questa classe verifica la validità dell'output generato dalle build. Ad esempio, se la build è destinata a un target ARM, controlla se sono stati prodotti binari ARM. Se, ad esempio, la build produce binari PPC, allora c'è un problema.

  • testimage: Questa classe esegue test a runtime sulle immagini dopo la loro creazione. I test vengono solitamente utilizzati con QEMU per avviare le immagini e verificare il risultato combinato dell'avvio e le relative funzionalità. Tuttavia, il test può anche utilizzare l'indirizzo IP di una macchina.

  • ptest: Esegue test sui pacchetti prodotti durante la compilazione di un determinato software. Il test consente di eseguire i pacchetti all'interno di un'immagine target.

  • oe-selftest: Testa combinazioni di invocazioni di BitBake. Questi test operano al di fuori del sistema di compilazione di OpenEmbedded. oe-selftest può eseguire tutti i test per default oppure test o suite di test selezionati.

In origine, gran parte di questi test veniva eseguita manualmente. Tuttavia, sono stati compiuti sforzi significativi per automatizzare i test in modo che più persone possano utilizzarli e il team di sviluppo di Yocto Project possa eseguirli più velocemente ed efficientemente.

Il principale strumento di compilazione automatica (Autobuilder) di Yocto Project testa pubblicamente il codice di ogni release di Yocto Project nei repository openembedded-core, meta-yocto e bitbake. I test vengono eseguiti sia per lo stato corrente del branch "master" sia per le patch inviate. I test per le patch inviate vengono solitamente eseguiti nel ramo "master-next" nei repository openembedded-core, meta-yocto e bitbake.

Nota

È possibile trovare tutti questi rami in I Repository del Codice Sorgente di Yocto Project.

I test all'interno di questi rami pubblici garantiscono, in modo visibile a tutti, che tutte le principali architetture e ricette previste in OE-Core vengano compilate e funzionino correttamente.

Varie funzionalità, come multilib, le sottoarchitetture (ad esempio x32, poky-tiny, musl, no-x11 e così via), bitbake-selftest e oe-selftest, vengono testate come parte del processo di controllo qualità di una release. Il test e la validazione completi di una release richiedono diverse ore ai worker di Autobuilder.

Nota

I worker di Autobuilder non sono omogenei, il che significa che vengono eseguiti regolarmente test su una varietà di distribuzioni Linux. Autobuilder è limitato al test di configurazioni basate su QEMU e non di hardware reale.

Infine, oltre ai test di Autobuilder, il team di controllo qualità di Yocto Project esegue test anche su diverse piattaforme, incluso hardware reale, per garantire i risultati attesi.
