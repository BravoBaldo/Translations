1 Requisiti di Sistema

Benvenuti nel Manuale di Riferimento di Yocto Project. Questo manuale fornisce informazioni di riferimento per la versione corrente di Yocto Project ed è più efficace se si hanno familiarità con i concetti di base del progetto. Il manuale non deve essere letto come punto di partenza per Yocto Project, né dall'inizio alla fine. Piuttosto, va utilizzato per trovare definizioni di variabili, descrizioni di classi e così via, a seconda delle necessità durante l'utilizzo di Yocto Project.

Per informazioni introduttive su Yocto Project, consultate il Sito Web di Yocto Project e il capitolo "L'Ambiente di Sviluppo di Yocto Project" nel Manuale Introduttivo e Concetti di Yocto Project.

Per utilizzare Yocto Project per creare rapidamente un'immagine senza dover comprendere i concetti, consultate il documento Build Rapida di un'Immagine con lo Yocto Project. Le istruzioni pratiche sono disponibili nel file Manuale di Sviluppo dei Task di Yocto Project. Una panoramica di Yocto Project e informazioni concettuali sono disponibili nel file Manuale Introduttivo e Concetti di Yocto Project.

Nota

Per ulteriori informazioni sulla documentazione di Yocto Project, consultare la sezione Links and Related Documentation.

1.1 Spazio Libero Minimo su Disco

Per creare un'immagine come core-image-sato per la macchina qemux86-64, è necessario un sistema con almeno 140 GB di spazio libero su disco. Tuttavia, sarà necessario molto più spazio su disco per creare immagini più complesse, per eseguire più build e per memorizzare nella cache gli artefatti di build, migliorando l'efficienza del processo.

Se lo spazio su disco è insufficiente, consultare la sezione "Conserving Disk Space" del Manuale dei Task di Sviluppo.

1.2 RAM Minima di Sistema

Sarà possibile creare un'immagine come core-image-sato per la macchina qemux86-64 con soli 32 GB di RAM su un vecchio sistema con 4 core CPU, ma le build saranno molto più veloci su un sistema con la massima quantità di RAM e il maggior numero possibile di core CPU.

Nota

  • Sebbene il team di Yocto Project si impegni a garantire la piena compatibilità di tutte le release con ogni distribuzione Linux ufficialmente supportata, è possibile che si verifichino problemi specifici di una determinata distribuzione.

  • Le release di Yocto Project vengono testate sulle distribuzioni Linux stabili elencate sopra. Yocto Project dovrebbe funzionare anche su altre distribuzioni, ma non vengono eseguite validazioni su di esse.

  • In particolare, Yocto Project non supporta e al momento non prevede di supportare distribuzioni "rolling release" o di sviluppo, data la loro natura in continua evoluzione. Accogliamo con favore patch e segnalazioni di bug, ma si tenga presente che la nostra priorità è rappresentata dalle piattaforme supportate elencate sopra.

  • Se la propria distribuzione Linux non è presente nell'elenco, consigliamo di scaricare i tarball buildtools o buildtools-extended contenenti gli strumenti host richiesti dalla release di Yocto Project, in genere eseguendo scripts/install-buildtools come spiegato nella sezione "Versioni richieste di Git, tar, Python, make e gcc".

  • È possibile utilizzare Windows Subsystem for Linux v2 per configurare un host di build con Windows 10 o versioni successive, oppure Windows Server 2019 o versioni successive, ma la convalida non viene eseguita sugli host di build che utilizzano WSL 2.

    Per ulteriori informazioni, consultare la sezione Setting Up to Use Windows Subsystem For Linux (WSL 2) nel Manuale di Sviluppo dei Task di Yocto Project.

  • In caso di problemi, si prega di visitare Yocto Project Bugzilla e segnalare un bug. Siamo interessati a conoscere la vostra esperienza. Per informazioni su come segnalare un bug, consultare la pagina wiki di Yocto Project Bugzilla wiki page e la sezione "Segnalazione di un Difetto in Yocto Project e in OpenEmbedded" nella Guida per i Collaboratori di Yocto Project e di OpenEmbedded.

1.4 Pacchetti Richiesti per l'Host di Build

L'elenco dei pacchetti necessari sul sistema di sviluppo host può essere lungo quando si considerano tutti gli scenari di compilazione con Yocto Project. Questa sezione descrive i pacchetti richiesti in base alla distribuzione Linux e alla funzione.

1.4.1 Ubuntu e Debian

Ecco i pacchetti necessari per creare un'immagine su un sistema senza interfaccia grafica con una distribuzione Linux Ubuntu o Debian supportata:

sudo apt-get install build-essential chrpath cpio debianutils diffstat file gawk gcc git iputils-ping libacl1 libcrypt-dev locales python3 python3-git python3-jinja2 python3-pexpect python3-pip python3-subunit socat texinfo unzip wget xz-utils zstd

È inoltre necessario assicurarsi che sia abilitata la localizzazione en_US.UTF-8:

$ locale --all-locales | grep en_US.utf8

In caso contrario, è possibile riconfigurare il pacchetto locales per aggiungerla (richiede una shell interattiva):

$ sudo dpkg-reconfigure locales

Nota

  • Se non si utilizza una shell interattiva, dpkg-reconfigure non funzionerà come previsto. Per aggiungere la localizzazione, è necessario modificare il file /etc/locale.gen per aggiungere/decommentare la localizzazione en_US.UTF-8. Un modo semplice per farlo come root è il seguente:

    $ echo "en_US.UTF-8 UTF-8" >> /etc/locale.gen
$ locale-gen

  • Se il sistema di build ha installato il pacchetto oss4-dev, si potrebbero riscontrare errori di compilazione di QEMU a causa dell'installazione, da parte del pacchetto, di una propria versione personalizzata di /usr/include/linux/soundcard.h sul sistema Debian. Se ci si imbatte in questa situazione, provare una di queste soluzioni:

    $ sudo apt build-dep qemu
$ sudo apt remove oss4-dev

Inoltre, su distribuzioni diverse da Debian 11 e Ubuntu 22.04 (altrimenti vedere la nota seguente), installare il seguente pacchetto:

$ sudo apt-get install python3-websockets

Nota

Su Debian 11 e Ubuntu 22.04, la versione minima di python3-websockets non è soddisfatta dalla distribuzione host. Questo pacchetto viene utilizzato per scaricare gli artefatti shared state precompilati dai server di Yocto Project (vedere core/yocto/sstate-mirror-cdn per maggiori informazioni).

Per utilizzare questa funzionalità, si può ottenere la versione corretta di python3-websockets in uno dei seguenti modi:

  • Utilizzando un tarball buildtools seguendo la sezione Versioni richieste di Git, tar, Python, make e gcc qui di seguito.

  • Installazione di python3-websockets tramite Pip in un ambiente virtuale, ad esempio:

    $ python3 -m venv --clear ./yocto-docs-venv
$ . ./yocto-docs-venv/bin/activate
$ pip install websockets

Ecco i pacchetti necessari per creare i manuali di documentazione del Progetto:

sudo apt install git librsvg2-bin locales make python3-pip python3-venv

python3 -m venv --clear ./yocto-docs-venv
. ./yocto-docs-venv/bin/activate
python3 -m pip install sphinx sphinx_rtd_theme pyyaml sphinx-copybutton 'sphinxcontrib-svg2pdfconverter>=2.0.0'

Oltre ai pacchetti precedenti, ecco quelli necessari per creare la documentazione in formato PDF:

sudo apt install fonts-freefont-otf latexmk tex-gyre texlive-fonts-extra texlive-fonts-recommended texlive-lang-all texlive-latex-extra texlive-latex-recommended texlive-xetex

1.4.4 Pacchetti AlmaLinux

Ecco i pacchetti necessari per creare un'immagine su un sistema senza interfaccia grafica con una distribuzione AlmaLinux supportata:

sudo dnf install -y epel-release
sudo dnf install -y dnf-plugins-core
sudo dnf config-manager --set-enabled crb || sudo dnf config-manager --set-enabled powertools
sudo dnf makecache
sudo dnf install -y bzip2 chrpath cpio cpp diffstat diffutils gawk gcc gcc-c++ git glibc-devel glibc-langpack-en gzip libacl make patch perl perl-Data-Dumper perl-Text-ParseWords perl-Thread-Queue python3 python3-GitPython python3-jinja2 python3-pexpect python3-pip rpcgen socat tar texinfo unzip wget which xz zstd

Sarà inoltre necessario utilizzare un file tarball buildtools che fornisce una serie di strumenti host di base con versioni fisse. Seguire la sezione Versioni richieste di Git, tar, Python, make e gcc di seguito per scoprire come scaricare e installare questo file tarball.

Nota

Le distribuzioni AlmaLinux 9, CentOS 9 e RockyLinux 9 sono interessate da un bug descritto in https://bugzilla.yoctoproject.org/show_bug.cgi?id=16143, motivo per cui è necessario un file tarball buildtools.

Nota

  • Extra Packages for Enterprise Linux (ovvero epel-release) è una raccolta di pacchetti di Fedora basati su RHEL/CentOS per facilitare l'installazione di pacchetti non inclusi di default in Enterprise Linux. È necessario installare questi pacchetti separatamente.

  • Il repository PowerTools/CRB fornisce pacchetti aggiuntivi come rpcgen e texinfo.

  • Il comando makecache utilizza Metadati aggiuntivi da epel-release.

Ecco i pacchetti necessari per creare i manuali di documentazione del Progetto:

sudo dnf install -y git glibc-locale-source librsvg2-tools make python3-pip which

python3 -m venv --clear ./yocto-docs-venv
. ./yocto-docs-venv/bin/activate
python3 -m pip install sphinx sphinx_rtd_theme pyyaml sphinx-copybutton 'sphinxcontrib-svg2pdfconverter>=2.0.0'

Oltre ai pacchetti precedenti, per creare la documentazione in formato PDF sono necessari i seguenti pacchetti TeX Live, installabili tramite il gestore di pacchetti TeX Live:

sudo dnf install -y wget perl
textooldir=${TEXTOOLDIR:-"./docs-build-tex-tools"}
mkdir -p "$textooldir"/tl
wget https://mirror.ctan.org/systems/texlive/tlnet/install-tl-unx.tar.gz -O "$textooldir"/install-tl-unx.tar.gz
tar xzf "$textooldir"/install-tl-unx.tar.gz -C "$textooldir"
"$textooldir"/install-tl-*/install-tl --scheme=small --texdir="${textooldir}"/tl --no-interaction
PATH="$PATH:${textooldir}/tl/bin/x86_64-linux" tlmgr install titlesec varwidth tabulary needspace upquote framed capt-of wrapfig fncychap gnu-freefont ctex latexmk nimbus15
rm -r "$textooldir"/install-tl*

Avvertimento

L'installazione di TeX Live sopra descritta è valida solo per sistemi host x86_64.

Prima di creare la documentazione in PDF, impostare la variabile d'ambiente PATH per utilizzare i pacchetti installati (con ${textooldir} che punta all'installazione di TeX Live del passaggio precedente):

$ export PATH="${PATH}:${textooldir}/tl/bin/x86_64-linux"

1.5 Versioni richieste di Git, tar, Python, make e gcc

Per utilizzare il sistema di build, il sistema host di sviluppo deve soddisfare i seguenti requisiti di versione per Git, tar e Python:

  • Git 2.22.0 o superiore

  • tar 1.28 o superiore

  • Python 3.9.0 o superiore

  • GNU make 4.0 o superiore

Se il sistema host di sviluppo non soddisfa tutti questi requisiti, è possibile risolvere il problema installando un file tarball buildtools contenente questi strumenti. È possibile scaricare un file tarball precompilato oppure utilizzare BitBake per crearne uno.

Inoltre, il sistema host di sviluppo deve soddisfare il seguente requisito di versione per gcc:

  • gcc 10.1 o superiore

Se il sistema host di sviluppo non soddisfa questo requisito, è possibile risolvere il problema installando un tarball buildtools-extended che contiene strumenti aggiuntivi, l'equivalente del pacchetto build-essential di Debian/Ubuntu.

Per i sistemi con una versione di make non funzionante (ad esempio make 4.2.1 senza patch) ma in cui gli altri strumenti host sono utilizzabili, è possibile utilizzare il tarball buildtools-make.

Nelle sezioni seguenti, verranno descritti tre diversi metodi per installare i toolset buildtools, buildtools-extended o buildtools-make.

1.5.1 Installazione di un tarball buildtools Pre-Built con lo script install-buildtools

Lo script install-buildtools è il più semplice dei tre metodi per ottenere questi strumenti. Scaricare un programma di installazione precompilato di buildtools e installare automaticamente gli strumenti:

  1. Eseguire lo script install-buildtools. Ecco un esempio:

    $ cd /path/to/bitbake-builds
$ ./layers/openembedded-core/scripts/install-buildtools \
  --without-extended-buildtools \
  --base-url https://downloads.yoctoproject.org/releases/yocto \
  --release yocto-6.1 \
  --installer-version 6.1

    Durante l'esecuzione, verrà scaricato il file tarball di buildtools, verrà verificato il checksum del download, verrà eseguito il programma di installazione e verranno effettuati alcuni controlli di base per assicurarsi che l'installazione sia funzionante.

    Per evitare la necessità di privilegi sudo, lo script install-buildtools , per default, indicherà al programma di installazione di installare i pacchetti nella directory:

    /path/to/bitbake-builds/buildtools

    Se il sistema host di sviluppo necessita degli strumenti aggiuntivi forniti nel file tarball buildtools-extended, è possibile eseguire lo script install-buildtools con i parametri di default:

    $ cd /path/to/bitbake-builds
$ ./layers/openembedded-core/scripts/install-buildtools

    In alternativa, se il sistema host di sviluppo ha una versione di make non funzionante e si necessita solo di una versione funzionante, è possibile utilizzare l'opzione --make-only:

    $ cd /path/to/bitbake-builds
$ ./layers/openembedded-core/scripts/install-buildtools --make-only

  2. Eseguire lo script di configurazione dell'ambiente degli strumenti utilizzando un comando simile al seguente:

    $ source /path/to/bitbake-builds/buildtools/environment-setup-x86_64-pokysdk-linux

    Dopo aver eseguito lo script di configurazione, gli strumenti vengono aggiunti a PATH e vengono inizializzate tutte le altre variabili d'ambiente necessarie per il loro funzionamento. Il risultato saranno versioni funzionanti di Git, tar, Python e chrpath. E nel caso del tarball buildtools-extended, sono presenti versioni funzionanti aggiuntive di strumenti tra cui gcc, make e gli altri strumenti inclusi in packagegroup-core-buildessential.

1.5.2 Download di un Archivio Tarball Precompilato di buildtools

Se si preferisce non utilizzare lo script install-buildtools, si può scaricare ed eseguire autonomamente un programma di installazione precompilato di buildtools seguendo questi passaggi:

  1. Go to https://downloads.yoctoproject.org/releases/yocto/yocto-6.1_M3/buildtools/, locate and download the .sh file corresponding to your host architecture and to buildtools, buildtools-extended or buildtools-make.

  2. Eseguire lo script di installazione. Ecco un esempio per il programma di installazione tradizionale:

    $ sh ~/Downloads/x86_64-buildtools-nativesdk-standalone-6.1.sh

    Ecco un esempio per il programma di installazione esteso:

    $ sh ~/Downloads/x86_64-buildtools-extended-nativesdk-standalone-6.1.sh

    Esempio per il programma di installazione solo make:

    $ sh ~/Downloads/x86_64-buildtools-make-nativesdk-standalone-6.1.sh

    Durante l'esecuzione, verrà visualizzato un prompt che permetterà di scegliere la directory di installazione. Ad esempio, si potrebbe scegliere il seguente path: /home/your-username/buildtools

  3. Come indicato dallo script di installazione, dovrai eseguire lo script di configurazione dell'ambiente degli strumenti:

    $ source /home/your_username/buildtools/environment-setup-x86_64-pokysdk-linux

    Dopo aver eseguito lo script di configurazione, gli strumenti vengono aggiunti a PATH e vengono inizializzate tutte le altre variabili d'ambiente necessarie per il loro funzionamento. Il risultato saranno versioni funzionanti di Git, tar, Python e chrpath. E nel caso del tarball buildtools-extended, sono presenti versioni funzionanti aggiuntive di strumenti tra cui gcc, make e gli altri strumenti inclusi in packagegroup-core-buildessential.

1.5.3 Building del Proprio Archivio tar di buildtools

La creazione e l'esecuzione del proprio programma di installazione di buildtools è possibile solo se si dispone di un host di build in grado di eseguire BitBake. In questo caso, si utilizza tale macchina per creare il file .sh e quindi si procede al trasferimento e all'esecuzione su una macchina che non soddisfa i requisiti minimi di Git, tar e Python (o gcc).

Ecco i passaggi da seguire per creare ed eseguire il proprio programma di installazione di buildtools:

  1. Sulla macchina in grado di eseguire BitBake, assicurarsi di aver configurato l'ambiente di build con lo script di configurazione (oe-init-build-env).

  2. Eseguire il comando BitBake per creare il tarball:

    $ bitbake buildtools-tarball

    oppure per creare il tarball esteso:

    $ bitbake buildtools-extended-tarball

    oppure per creare il tarball con soll make:

    $ bitbake buildtools-make-tarball

    Nota

    The SDKMACHINE variable determines whether you build tools for a 32-bit or 64-bit system.

    Una volta completata la compilazione, è possibile trovare il file .sh che installa gli strumenti nella sottocartella tmp/deploy/sdk della directory di Build Directory. Il file di installazione ha la stringa "buildtools" o "buildtools-extended" nel nome.

  3. Trasferire il file .sh dall'host di compilazione alla macchina che non soddisfa i requisiti di Git, tar o Python (o gcc).

  4. Su questa macchina, si esegue il file .sh per installare gli strumenti. Ecco un esempio per l'installazione tradizionale:

    $ sh ~/Downloads/x86_64-buildtools-nativesdk-standalone-6.1.sh

    Per l'installazione estesa:

    $ sh ~/Downloads/x86_64-buildtools-extended-nativesdk-standalone-6.1.sh

    E per l'installazione solo con make:

    $ sh ~/Downloads/x86_64-buildtools-make-nativesdk-standalone-6.1.sh

    Durante l'esecuzione, verrà visualizzato un prompt che consente di scegliere la directory di installazione. Ad esempio, è possibile scegliere la seguente: /home/your_username/buildtools

  5. Eseguire lo script di configurazione dell'ambiente degli strumenti utilizzando un comando simile al seguente:

    $ source /home/your_username/buildtools/environment-setup-x86_64-poky-linux

    Dopo aver eseguito lo script di configurazione, gli strumenti vengono aggiunti a PATH e vengono inizializzate tutte le altre variabili d'ambiente necessarie per il loro funzionamento. Il risultato saranno versioni funzionanti di Git, tar, Python e chrpath. E nel caso del tarball buildtools-extended, sono presenti versioni funzionanti aggiuntive di strumenti tra cui gcc, make e gli altri strumenti inclusi in packagegroup-core-buildessential.
