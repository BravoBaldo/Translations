5 Struttura della Directory Sorgente

La Source Directory [Directory Sorgente] è composta da numerosi file, directory e sottodirectory; comprenderne la posizione e il contenuto è fondamentale per utilizzare efficacemente il Yocto Project. Questo capitolo descrive la Source Directory e fornisce informazioni su file e directory.

Nota

Il sistema di build OpenEmbedded non supporta nomi di file o directory contenenti spazi. Assicurarsi che la directory sorgente utilizzata non contenga questo tipo di nomi.

Nelle sezioni seguenti, si presume che i componenti principali della Source Directory siano organizzati come segue:

├── build/
│   └── ...
└── layers/
    ├── bitbake/
    ├── meta-yocto/
    ├── openembedded-core/
    └── yocto-docs/

5.1 Componenti Principali di Primo Livello

Questa sezione descrive i componenti principali della Source Directory.

5.1.1 bitbake/

Questa directory include una copia di BitBake per facilità d'uso. La copia corrisponde solitamente alla versione stabile corrente di BitBake rilasciata dal progetto BitBake. BitBake, un interprete di Metadata, legge i Metadati di Yocto Project ed esegue i task [attività] definiti da tali dati. Gli errori sono generalmente causati da problemi nei Metadati e non da BitBake stesso.

Quando si esegue il comando bitbake, viene avviato l'eseguibile principale di BitBake (che si trova nella directory bitbake/bin/). L'esecuzione dello script di configurazione dell'ambiente (ad esempio, oe-init-build-env) aggiunge le directory scripts/ e bitbake/bin/ (in quest'ordine) alla variabile d'ambiente PATH della shell.

Per ulteriori informazioni su BitBake, consultare il Manuale Utente di BitBake.

5.1.2 build/

Questa directory contiene i file di configurazione utente e l'output generato dal sistema di build OpenEmbedded nella sua configurazione standard, in cui l'albero dei sorgenti è combinato con l'output. La Build Directory viene creata inizialmente quando si esegue source lo script di configurazione dell'ambiente di build di OpenEmbedded (ovvero oe-init-build-env).

È anche possibile posizionare i file di output e di configurazione in una directory separata dalla Source Directory, specificando un nome di directory quando si esegue source lo script di configurazione. Per informazioni su come separare l'output dai file della Source Directory locale (comunemente descritta come una build "out of tree" [fuori albero]), consultare la sezione "oe-init-build-env".

Consultare la sezione "The Build Directory --- build/" per dettagli sul contenuto della Build Directory.

5.1.3 layers/yocto-docs/

Il repository della documentazione di Yocto è ospitato in https://git.yoctoproject.org/yocto-docs.

Questa directory contiene il codice sorgente della documentazione di Yocto Project, nonché template e tool che consentono di generare versioni PDF e HTML dei manuali. Ogni manuale è contenuto in una propria sottocartella; ad esempio, i file per questo manuale di riferimento si trovano nella directory ref-manual/.

Questa directory non è obbligatoria per la compilazione con BitBake.

5.1.4 layers/openembedded-core/

Il repository di OpenEmbedded-Core (OE-Core) è ospitato su https://git.openembedded.org/openembedded-core.

5.1.4.1 meta/

Questa directory contiene i metadati minimi di base di OpenEmbedded-Core (OE-Core). La directory contiene ricette, classi comuni e configurazione della macchina per target strettamente emulati (qemux86, qemuarm, e così via).

5.1.4.2 meta-selftest/

Questa directory aggiunge ricette e file append aggiuntivi utilizzati dagli autotest di OpenEmbedded per verificare il comportamento del sistema di compilazione. Non è necessario aggiungere questo layer al file build/conf/bblayers.conf a meno che non si desideri eseguire gli autotest.

5.1.4.3 meta-skeleton/

Questa directory contiene ricette template per lo sviluppo di BSP e kernel.

5.1.4.4 scripts/

Questa directory contiene vari script di integrazione che implementano funzionalità aggiuntive nell'ambiente di Yocto Project (ad esempio, script QEMU). Lo script oe-init-build-env aggiunge questa directory all'inizio della variabile d'ambiente PATH della shell.

La directory scripts contiene script utili per contribuire a Yocto Project, come create-pull-request e send-pull-request.

5.1.4.5 oe-init-build-env

Questo script configura l'ambiente di build di OpenEmbedded. Eseguendo questo script con il comando source nella shell, vengono apportate modifiche alla variabile PATH e vengono impostate altre variabili principali di BitBake in base alla directory di lavoro corrente. È necessario eseguire uno script di configurazione dell'ambiente prima di eseguire i comandi di BitBake. Lo script utilizza altri script presenti nella directory scripts per svolgere la maggior parte del lavoro.

Quando so esegue questo script, l'ambiente di Yocto Project viene configurato, viene creata una Build Directory, la directory di lavoro diventa la Build Directory e vengono presentati alcuni semplici suggerimenti su cosa fare successivamente, incluso un elenco di possibili target da compilare. Ecco un esempio:

$ source oe-init-build-env

### Shell environment set up for builds. ###

You can now run 'bitbake <target>'

Common targets are:
    core-image-minimal
    core-image-sato
    meta-toolchain
    meta-ide-support

You can also run generated QEMU images with a command like 'runqemu qemux86-64'

Nota

Quando si utilizza bitbake-setup, questo script viene eseguito indirettamente quando si esegue init-build-env he si trova nella directory di build di Setup. Tuttavia, rispetto a oe-init-build-env, init-build-env di bitbake-setup non accetta argomenti, poiché si trova già in una Build Directory.

Per ulteriori informazioni, consultare la documentazione Setting Up The Environment With bitbake-setup.

L'output di default dello script oe-init-build-env proviene dai file conf-summary.txt e conf-notes.txt, che si trovano nella directory meta/conf/templates/default di OpenEmbedded-Core (OE-Core). Se si progetta una distribuzione personalizzata, è possibile includere versioni personalizzate di questi file di configurazione, in cui è possibile fornire un breve riepilogo e note dettagliate sull'utilizzo, come ad esempio un elenco dei target definiti dalla distribuzione. Per ulteriori informazioni, consultare la sezione "Creating a Custom Template Configuration Directory" del Manuale delle attività di sviluppo del progetto Yocto.

Per default, l'esecuzione di questo script senza l'argomento Build Directory crea la directory build/ nella directory di lavoro corrente. Se si specifica l'argomento Build Directory quando si esegue lo script con source, si indica al sistema di build di OpenEmbedded di creare una Build Directory a propria scelta. Ad esempio, il seguente comando crea una Build Directory denominata mybuilds/ al di fuori della Source Directory:

$ source oe-init-build-env ~/mybuilds

Il sistema di build OpenEmbedded utilizza i file di configurazione dei template, che si trovano per default nella directory meta/conf/templates/default in OpenEmbedded-Core (OE-Core). Per ulteriori informazioni, consultare la sezione "Creating a Custom Template Configuration Directory" nel Manuale di Sviluppo dei Task di Yocto Project.

Nota

Il sistema di build OpenEmbedded non supporta nomi di file o directory contenenti spazi. Se si tenta di eseguire lo script oe-init-build-env da una Source Directory che contiene spazi nei nomi di file o directory, lo script restituisce un errore indicando che il file o la directory non esiste. Assicurarsi di utilizzare una Source Directory priva di nomi contenenti spazi.

5.1.5 layers/meta-yocto/

Il repository meta-yocto è ospitato in https://git.yoctoproject.org/meta-yocto.

5.1.5.1 meta-poky/

A seconda dei metadati di OpenEmbedded-Core (OE-Core), questa directory aggiunge i metadati necessari per definire la distribuzione di riferimento di Poky.

Nello specifico, contiene il configuration file della distribuzione per Poky: conf/distro/poky.conf.

5.1.5.2 meta-yocto-bsp/

Questa directory contiene i Board Support Package (BSP) di riferimento per l'hardware di Yocto Project. Per ulteriori informazioni sui BSP, consultare il manuale Manuale del Board Support Package (BSP) di Yocto Project.

5.2 La Directory di Build --- build/

Il sistema di build OpenEmbedded crea la Build Directory quando si esegue lo script di configurazione dell'ambiente di build oe-init-build-env. Se non si specifica un nome per la Build Directory durante l'esecuzione dello script di configurazione, il nome predefinito è build/.

Per le successive analisi ed elaborazioni, il nome della directory di Build è disponibile tramite la variabile TOPDIR.

5.2.1 build/buildhistory/

Il sistema di build OpenEmbedded crea questa directory quando si abilita la cronologia delle compilazioni tramite il file di classe buildhistory. La directory organizza le informazioni di compilazione in sottodirectory per immagini, pacchetti e SDK. Per informazioni sulla funzionalità di cronologia delle build, consultare la sezione "Maintaining Build Output Quality with buildhistory" nel Manuale di Sviluppo dei Task di Yocto Project.

5.2.2 build/cache/

Questa directory contiene diversi file interni utilizzati dal sistema di build OpenEmbedded. Il path di questa directory è definito dalla variabile PERSISTENT_DIR.

Contiene anche sanity_info, un file di testo che tiene traccia di importanti informazioni di compilazione, come i valori di TMPDIR, SSTATE_DIR, nonché il nome e la versione della distribuzione host.

Questa directory non deve essere condivisa tra diverse compilazioni. [build].

Nota

La posizione di default del database Equivalenza degli Hash è questa directory (quando BB_HASHSERVE è impostato su auto). Se si deve condividere il database Equivalenza degli Hash, non condividere questo file e fare invece riferimento al documento Setting up a Hash Equivalence Server del Manuale di Sviluppo dei Task di Yocto Project per configurare un server Hash Equivalence.

5.2.3 build/conf/local.conf

Questo file contiene le configurazioni utente locali per l'ambiente di build.

Ad esempio, è possibile sperimentare impostando (o aggiungendo) le variabili DISTRO_FEATURES o IMAGE_FEATURES, oppure adattare le configurazioni di compilazione per ricette specifiche impostando le variabili PACKAGECONFIG corrispondenti. Per pubblicare e condividere le modifiche apportate a questo file, si consiglia di inserirle in un configuration file della distribuzione oppure di creare frammenti di configurazione a partire dalle modifiche apportate qui.

Il OpenEmbedded Build System può creare il file build/conf/local.conf da un file local.conf.sample quando si esegue il comando source dello script di configurazione dell'ambiente di compilazione di livello superiore oe-init-build-env.

Il file sorgente local.conf.sample utilizzato dipende dalla variabile di script TEMPLATECONF, che per default è meta/conf/templates/default in OpenEmbedded-Core (OE-Core). Poiché la variabile di script punta al file sorgente local.conf.sample, ciò implica che è possibile configurare l'ambiente di compilazione da qualsiasi layer impostando la variabile nello script di configurazione dell'ambiente di compilazione di livello superiore in questo modo:

TEMPLATECONF=your_layer/conf/templates/your_template_name

Una volta che il processo di compilazione riceve il file di esempio, utilizza sed per sostituire i valori finali ${OEROOT} a tutti i valori ##OEROOT##.

Nota

È possibile vedere come viene utilizzata la variabile TEMPLATECONF esaminando lo script layers/openembedded-core/scripts/oe-setup-builddir in OpenEmbedded-Core (OE-Core).

5.2.4 build/conf/bblayers.conf

Questo file di configurazione definisce i layer, ovvero le strutture ad albero delle directory attraversate (o percorse) da BitBake. Il file build/conf/bblayers.conf utilizza la variabile BBLAYERS per elencare i layer che BitBake cerca.

Il sistema di build OpenEmbedded può crearlo a partire da un file bblayers.conf.sample quando si esegue il comando source sullo script di configurazione dell'ambiente di compilazione di livello superiore (ovvero oe-init-build-env).

Come per il file build/conf/local.conf, il file sorgente bblayers.conf.sample utilizzato dipende dalla variabile di script TEMPLATECONF, il cui valore predefinito è meta/conf/templates/default. Poiché la variabile di script punta al file sorgente bblayers.conf.sample, ciò implica che è possibile basare la build su qualsiasi layer impostando la variabile nello script di configurazione dell'ambiente di build di livello superiore come segue:

TEMPLATECONF=your_layer/conf/templates/your_template_name

Una volta che il processo di build ottiene il file di esempio, utilizza sed per sostituire i valori finali di ${OEROOT} per tutte le occorrenze di ##OEROOT##.

Nota

È possibile visualizzare come la variabile TEMPLATECONF viene definita dallo script scripts/oe-setup-builddir in OpenEmbedded-Core (OE-Core).

5.2.5 build/conf/site.conf

Questo file contiene le configurazioni specifiche del sito per l'ambiente di build [compilazione].

Ad esempio, si può modificare questo file per limitare il numero di thread utilizzati da BitBake (BB_NUMBER_THREADS) o impostare la posizione da cui desideri accedere ai file scaricati (DL_DIR).

Questo file può essere condiviso per più directory di build. Ad esempio, bitbake-setup crea un link simbolico al file build/conf/site.conf, che punta a un file comune build/conf/auto.conf:

├── poky-master-poky-distro_poky-machine_qemux86-64/
│   └── build/
│       └── conf/
│           └── site.conf -> ../../../site.conf
├── poky-master-poky-with-sstate-distro_poky-machine_qemux86-64/
│   └── build/
│       └── conf/
│           └── site.conf -> ../../../site.conf
└── site.conf

In questo modo, le impostazioni specifiche del sito possono essere condivise tra diverse configurazioni di build.

Nota

Per ulteriori informazioni su come utilizzare bitbake-setup, consultare il documento Build Rapida di un'Immagine con lo Yocto Project.

5.2.6 build/conf/bblock.conf

Questo file di configurazione viene generato da bblock e contiene le firme bloccate da bblock. Per default, non esiste e verrà creato alla prima esecuzione di bblock.

5.2.7 build/conf/toolcfg.conf

Questo file contiene variabili di configurazione che vengono modificate automaticamente da strumenti come bitbake-config-build. Questo file non deve essere modificato manualmente.

5.2.8 build/conf/auto.conf

Questo file è destinato all'uso in ambienti di "continuous integration", come l'Autobuilder di Yocto Project. Non deve essere creato o modificato durante l'esecuzione di build locali.

5.2.9 build/downloads/

Questa directory contiene i tarball del codice sorgente scaricati dal progetto upstream. È possibile riutilizzare la directory per più build o spostarla in un'altra posizione. È possibile controllare la posizione di questa directory tramite la variabile DL_DIR.

5.2.10 build/sstate-cache/

Questa directory contiene la cache di shared state [stato condivisa]. È possibile riutilizzare la directory per più build o spostarla in un'altra posizione. È possibile controllare la posizione di questa directory tramite la variabile SSTATE_DIR.

5.2.11 build/tmp/

Il sistema di build OpenEmbedded crea e utilizza questa directory per tutti gli output del sistema di build. La variabile TMPDIR punta a questa directory.

BitBake crea questa directory se non esiste. Come ultima risorsa, per ripulire una build e riavviarla da zero (esclusi i download), è possibile rimuovere tutto il contenuto della directory tmp o eliminarla completamente. In tal caso, è necessario rimuovere completamente anche la directory build/sstate-cache.

5.2.11.1 build/tmp/buildstats/

Questa directory memorizza le statistiche di compilazione generate dalla classe buildstats.

5.2.11.2 build/tmp/cache/

Quando BitBake analizza i metadati (ricette e file di configurazione), memorizza nella cache i risultati in build/tmp/cache/ per velocizzare le compilazioni future. I risultati vengono memorizzati per ogni singola macchina.

Durante le compilazioni successive, BitBake controlla ogni ricetta (insieme, ad esempio, a tutti i file inclusi o aggiunti ad essa) per verificare se sono state modificate. Le modifiche possono essere rilevate, ad esempio, tramite le variazioni dell'ora di modifica (mtime) del file e l'hashing del contenuto del file. Se non vengono rilevate modifiche al file, il risultato dell'analisi memorizzato nella cache viene riutilizzato. Se il file è stato modificato, viene rianalizzato.

5.2.11.3 build/tmp/deploy/

Questa directory contiene tutti gli "end result" [risultati finali] del processo di build di OpenEmbedded. La variabile DEPLOY_DIR punta a questa directory. Per maggiori dettagli sul contenuto della directory deploy, consultare le sezioni "Immagini" e "SDK per lo Sviluppo di Applicazioni" nel Manuale Introduttivo e Concetti di Yocto Project.

5.2.11.3.1 build/tmp/deploy/deb/

Questa directory contiene tutti i pacchetti .deb prodotti dal processo di compilazione. I pacchetti sono suddivisi in feed per diversi tipi di architettura.

5.2.11.3.2 build/tmp/deploy/rpm/

Questa directory contiene tutti i pacchetti .rpm prodotti dal processo di compilazione. I pacchetti sono suddivisi in feed per diversi tipi di architettura.

5.2.11.3.3 build/tmp/deploy/ipk/

Questa directory contiene i pacchetti .ipk prodotti dal processo di compilazione.

5.2.11.3.4 build/tmp/deploy/licenses/

Questa directory contiene le informazioni di licenza dei pacchetti. Ad esempio, la directory contiene sottocartelle per bash, busybox e glibc (tra gli altri) che a loro volta contengono i relativi file di licenza COPYING con altre informazioni di licenza. Per informazioni sulle licenze, consultare la sezione "Maintaining Open Source License Compliance During Your Product's Lifecycle" nel Manuale di Sviluppo dei Task di Yocto Project.

5.2.11.3.5 build/tmp/deploy/spdx/

Questa directory contiene file JSON in formato SPDX utilizzati per creare una Software Bill of Materials (SBOM) [distinta base], come spiegato in dettaglio nella sezione "Creating a Software Bill of Materials" del Manuale di Sviluppo dei Task di Yocto Project.

5.2.11.3.6 build/tmp/deploy/images/

Questa directory contiene gli oggetti di output di base della build (considerali come gli "artefatti generati" dal processo di build), tra cui l'immagine del boot loader, il kernel, il filesystem root e altro ancora. Per caricare l'immagine risultante da una build su un dispositivo, consultare questa directory per trovare i componenti necessari.

Fare attenzione quando si eliminano i file in questa directory. È possibile eliminare in sicurezza le vecchie immagini da questa directory (ad esempio, core-image-*). Tuttavia, il kernel (*zImage*, *uImage*, ecc.), il bootloader e altri file supplementari potrebbero essere distribuiti qui prima della creazione dell'immagine. Poiché questi file non vengono prodotti direttamente dall'immagine, se si eliminano non verranno ricreati automaticamente quando si creerà nuovamente l'immagine.

Se si eliminano accidentalmente dei file in questa directory, sarà necessario forzarne la ricreazione. Per farlo, è necessario conoscere il target che li ha generati. Ad esempio, questi comandi ricompilano e ricreano i file del kernel:

$ bitbake -c clean virtual/kernel
$ bitbake virtual/kernel
5.2.11.3.7 build/tmp/deploy/sdk/

Il sistema di build OpenEmbedded crea questa directory per contenere gli script di installazione della toolchain che, una volta eseguiti, installano il sysroot corrispondente all'hardware target. Ulteriori informazioni su questi programmi di installazione sono disponibili nella sezione "Building an SDK Installer" del Manuale di Sviluppo di Applicazioni Yocto Project e Software Development Kit (eSDK).

5.2.11.4 build/tmp/hosttools/

Il sistema di build OpenEmbedded utilizza questa directory per creare link simbolici ad alcuni componenti host che possono essere richiamati all'interno dei task. Questi sono i componenti di base elencati nella sezione Pacchetti Richiesti per l'Host di Build. Questi componenti sono elencati anche nella variabile HOSTTOOLS e sono limitati a questo elenco per evitare la contaminazione dell'host.

5.2.11.5 build/tmp/pkgdata/

Il sistema di build OpenEmbedded utilizza questa directory per memorizzare i metadati dei pacchetti generati durante il task do_packagedata. I file memorizzati in questa directory contengono informazioni su ciascun pacchetto di output prodotto dal sistema di build OpenEmbedded e vengono utilizzati in diversi modi dal sistema di build, ad esempio per "Viewing Package Information with oe-pkgdata-util".

5.2.11.6 build/tmp/sstate-control/

Il sistema di build OpenEmbedded utilizza questa directory per i file manifest dello "shared state" [stato condiviso]. Il codice di "shared state" utilizza questi file per registrare i file installati da ciascuna attività di stato condiviso, in modo che possano essere rimossi durante la pulizia della ricetta o quando sta per essere installata una versione più recente. Il sistema di build utilizza inoltre i manifest per rilevare e generare un warning quando i file di un task sovrascrivono quelli di un'altro.

5.2.11.7 build/tmp/sysroots-components/

Questa directory contiene il contenuto del sysroot che il task do_prepare_recipe_sysroot collega o copia nel sysroot specifico della ricetta per ciascuna ricetta elencata in DEPENDS. Il popolamento di questa directory viene gestito tramite lo "shared state" [stato condiviso], mentre il path è specificato dalla variabile COMPONENTS_DIR. A parte alcune circostanze eccezionali, la gestione della directory sysroots-components dovrebbe essere automatica e le ricette non dovrebbero fare riferimento direttamente a build/tmp/sysroots-components.

5.2.11.8 build/tmp/sysroots/

Nelle versioni precedenti del sistema di build OpenEmbedded, veniva creata una directory sysroot globale condivisa per ogni macchina, insieme a una directory sysroot nativa. Dalla versione 2.3 di Yocto Project, le directory sysroot si trovano in directory WORKDIR specifiche per ogni ricetta. Pertanto, la directory build/tmp/sysroots/ non viene più utilizzata.

Nota

È comunque possibile popolare la directory build/tmp/sysroots/ utilizzando il comando bitbake build-sysroots e, in alcuni casi, può essere utilizzata per garantire la compatibilità. Tuttavia, in generale, non è consigliabile popolare questa directory. È preferibile utilizzare directory sysroot specifiche per ogni ricetta.

5.2.11.9 build/tmp/stamps/

Questa directory contiene informazioni che BitBake utilizza a fini contabili per tenere traccia dei task eseguiti e del momento in cui sono stati eseguiti. La directory è suddivisa per architettura, nome del pacchetto e versione. Ecco un esempio:

stamps/all-poky-linux/distcc-config/1.0-r0.do_build-2fdd....2do

Sebbene i file nella directory siano vuoti, BitBake utilizza i nomi dei file e i timestamp a scopo di tracciamento.

Per informazioni su come BitBake utilizza i file di timestamp per determinare se un task deve essere rieseguito, consultare la sezione "File Stamp e Riesecuzione dei Task" nel Manuale Introduttivo e Concetti di Yocto Project.

5.2.11.10 build/tmp/log/

Questa directory contiene i log generali che non vengono altrimenti inseriti utilizzando la directory WORKDIR del pacchetto. Esempi di log sono l'output dei task do_check_pkg o do_distro_check. L'esecuzione di una build non implica necessariamente la creazione di questa directory.

5.2.11.11 build/tmp/work/

Questa directory contiene sottodirectory di lavoro specifiche per l'architettura dei pacchetti compilati da BitBake. Tutte le operazioni vengono eseguite dalla directory di lavoro appropriata. Ad esempio, il codice sorgente di un determinato pacchetto viene decompresso, patchato, configurato e compilato all'interno della sua directory di lavoro. All'interno della directory di lavoro, l'organizzazione si basa sul gruppo di pacchetti e sulla versione per cui il codice sorgente viene compilato, come definito da WORKDIR.

Vale la pena considerare la struttura di una tipica directory di lavoro. Ad esempio, si consideri linux-yocto-kernel-3.0 sulla macchina qemux86 compilata nell'ambito di Yocto Project. Per questo pacchetto, viene creata una directory di lavoro tmp/work/qemux86-poky-linux/linux-yocto/3.0+git1+<.....>, denominata WORKDIR. All'interno di questa directory, il codice sorgente viene estratto in sources/linux-qemux86-standard-build e quindi patchato da Quilt. (Per ulteriori informazioni, consultare la sezione "Using Quilt in Your Workflow" del Manuale di Sviluppo dei Task di Yocto Project). All'interno della directory linux-qemux86-standard-build, vengono create le directory standard di Quilt linux-3.0/patches e linux-3.0/.pc, e si possono utilizzare i comandi standard di Quilt.

Vengono generate altre directory all'interno di WORKDIR. La directory più importante è WORKDIR/temp/, che contiene i file di log per ogni attività (log.do_*.pid) e gli script che BitBake esegue per ogni task (run.do_*.pid). La directory WORKDIR/image/ è quella in cui il comando "make install" inserisce il suo output, che viene poi suddiviso in sottocartelle all'interno di WORKDIR/packages-split/.

5.2.11.11.1 build/tmp/work/tunearch/recipename/version/

La directory di lavoro della ricetta --- ${WORKDIR}.

Come descritto in precedenza nella sezione "build/tmp/sysroots/", a partire dalla versione 2.3 di Yocto Project, il sistema di build OpenEmbedded compila ogni ricetta nella propria directory di lavoro (ovvero WORKDIR). Il path alla directory di lavoro viene costruito utilizzando l'architettura della build specificata (ad esempio, TUNE_PKGARCH, MACHINE_ARCH o "allarch"), il nome della ricetta e la versione della ricetta (ad esempio, PE:PV-PR).

Ecco le principali sottodirectory all'interno di ciascuna directory di lavoro della ricetta:

  • ${WORKDIR}/temp: Contiene i file di log di ogni task eseguito per questa ricetta, i file "run" per ogni task eseguito, che contengono il codice eseguito, e un file log.task_order, che elenca l'ordine in cui sono state eseguiti i task.

  • ${WORKDIR}/image: Contiene l'output dei task do_install, che corrisponde alla variabile ${D} in tale task.

  • ${WORKDIR}/pseudo: Contiene il database pseudo e il log per tutti i task eseguiti in ambiente pseudo per la ricetta.

  • ${WORKDIR}/sysroot-destdir: Contiene l'output del task do_populate_sysroot.

  • ${WORKDIR}/package: Contiene l'output del task do_package prima che venga suddiviso in singoli pacchetti.

  • ${WORKDIR}/packages-split: Contiene l'output del task do_package dopo che è stato suddiviso in singoli pacchetti. Esistono sottocartelle per ogni singolo pacchetto creato dalla ricetta.

  • ${WORKDIR}/recipe-sysroot: Una directory contenente le dipendenze dal target della ricetta. Questa directory ha la stessa struttura del filesystem target e contiene le librerie che la ricetta potrebbe dover linkare (ad esempio, la libreria C).

  • ${WORKDIR}/recipe-sysroot-native: Una directory contenente le dipendenze native della ricetta. Questa directory contiene i tool necessari alla ricetta per la compilazione (ad esempio, il compilatore, Autoconf, libtool e così via).

  • ${WORKDIR}/build: Questa sottocartella si applica solo alle ricette che supportano build in cui il codice sorgente è separato dagli artefatti di build. Il sistema di build OpenEmbedded utilizza questa directory come directory di build separata (ovvero ${B}).

5.2.11.12 build/tmp/work-shared/

Per motivi di efficienza, il sistema di build OpenEmbedded crea e utilizza questa directory per contenere le ricette che condividono una directory di lavoro con altre ricette. Viene utilizzata, ad esempio, per gcc e le sue varianti (ad esempio gcc-cross, libgcc, gcc-runtime e così via), oppure dalla classe kernel per rendere il codice sorgente del kernel e gli artefatti di compilazione del kernel disponibili ai moduli del kernel esterni all'albero o ad altre ricette dipendenti dal kernel.

In pratica, solo poche ricette utilizzano la directory work-shared. Questa directory è particolarmente utile per le ricette che richiederebbero molto spazio di archiviazione se fossero condivise con il meccanismo standard Sysroot.

5.3 Metadati di OpenEmbedded-Core (OE-Core) --- meta/

Come accennato in precedenza, i metadata OpenEmbedded-Core (OE-Core) sono il nucleo di Yocto Project. Questi metadati sono suddivisi in diverse sezioni importanti:

5.3.1 meta/classes*/

Queste directory contengono i file *.bbclass. I file di classe vengono utilizzati per astrarre il codice comune in modo che possa essere riutilizzato da più pacchetti. Ogni pacchetto eredita il file base. Esempi di altre classi importanti sono autotools*, che in teoria consente a qualsiasi pacchetto abilitato per Autotools di funzionare con Yocto Project con il minimo sforzo. Un altro esempio è kernel, che contiene codice e funzioni comuni per lavorare con il kernel Linux. Funzioni come la generazione di immagini o il packaging hanno anch'esse i propri file di classe specifici, come image, rootfs* e package*.bbclass.

Per informazioni di riferimento sulle classi, consultare il capitolo "Classi".

5.3.2 meta/conf/

Questa directory contiene il set principale di file di configurazione che partono da bitbake.conf e da cui vengono inclusi tutti gli altri file di configurazione. Osservando le istruzioni di inclusione alla fine del file bitbake.conf, si noterà che anche build/conf/local.conf viene caricato da lì. Sebbene bitbake.conf imposti i valori di default, è spesso possibile sovrascriverli utilizzando il file (build/conf/local.conf), il file di configurazione della macchina o il file di configurazione della distribuzione.

5.3.2.1 meta/conf/machine/

Questa directory contiene tutti i file di configurazione della macchina. Se si imposta MACHINE = "qemux86", il sistema di build OpenEmbedded cerca il file qemux86.conf in questa directory. La directory include contiene vari dati comuni a diverse macchine. Per aggiungere il supporto per una nuova macchina a Yocto Project, consultare questa directory.

5.3.2.2 meta/conf/distro/

Il contenuto di questa directory controlla le configurazioni specifiche della distribuzione. Per Yocto Project, il file principale è defaultsetup.conf. Questa directory include le versioni e le definizioni di SRCDATE per le applicazioni configurate qui. Un esempio di configurazione alternativa potrebbe essere poky-bleeding.conf, sebbene questo file erediti principalmente la sua configurazione da Poky.

5.3.2.3 meta/conf/machine-sdk/

Il sistema di build OpenEmbedded cerca in questa directory i file di configurazione corrispondenti al valore di SDKMACHINE. Per default, Yocto Project include file x86 a 32 e 64 bit che supportano alcuni host SDK. Tuttavia, è possibile estendere tale supporto ad altri host SDK aggiungendo ulteriori file di configurazione in questa sottodirectory all'interno di un altro layer.

5.3.3 meta/files/

Questa directory contiene i file di licenza comuni e diversi file di testo utilizzati dal sistema di compilazione, nonché i file Wic files che definiscono il layout delle immagini prodotte dalla compilazione. I file di testo contengono informazioni minime sul dispositivo ed elenchi di file e directory con permessi noti.

5.3.4 meta/lib/

Questa directory contiene il codice della libreria Python di OpenEmbedded utilizzato durante il processo di build. È abilitato tramite la direttiva addpylib nel file meta/conf/layer.conf. Per ulteriori informazioni, consultare Extending Python Library Code.

5.3.5 meta/recipes-bsp/

Questa directory contiene tutti i collegamenti a hardware specifici o informazioni di configurazione hardware, come "u-boot" e "grub".

5.3.6 meta/recipes-connectivity/

Questa directory contiene librerie e applicazioni relative alla comunicazione con altri dispositivi.

5.3.7 meta/recipes-core/

Questa directory contiene tutto il necessario per creare un'immagine Linux di base funzionante, incluse le dipendenze più comuni.

5.3.8 meta/recipes-devtools/

Questa directory contiene tool utilizzati principalmente dal sistema di build. Tuttavia, questi strumenti possono essere utilizzati anche sui dispositivi target.

5.3.9 meta/recipes-extended/

Questa directory contiene applicazioni non essenziali che aggiungono funzionalità rispetto alle alternative presenti nel core. Potrebbe essere necessaria per sfruttare appieno tutte le funzionalità dei tool.

5.3.10 meta/recipes-gnome/

Questa directory contiene tutto ciò che riguarda il framework applicativo GTK+.

5.3.11 meta/recipes-graphics/

Questa directory contiene X e altre librerie di sistema relative alla grafica.

5.3.12 meta/recipes-kernel/

Questa directory contiene il kernel e le applicazioni e librerie generiche che hanno forti dipendenze dal kernel.

5.3.13 meta/recipes-multimedia/

Questa directory contiene codec e utility di supporto per audio, immagini e video.

5.3.14 meta/recipes-rt/

Questa directory contiene le ricette di pacchetti e immagini per l'utilizzo e il test del kernel PREEMPT_RT.

5.3.15 meta/recipes-sato/

Questa directory contiene il demo/reference UI/UX di Sato e le relative applicazioni e dati di configurazione.

5.3.16 meta/recipes-support/

Questa directory contiene le ricette utilizzate da altre ricette, ma non incluse direttamente nelle immagini (ovvero, dipendenze di altre ricette).

5.3.17 meta/site/

Questa directory contiene un elenco di risultati memorizzati nella cache per diverse architetture. Poiché alcuni risultati dei test di "autoconf" non possono essere determinati durante la cross-compilazione, in quanto i test non sono eseguibili su un sistema live, le informazioni contenute in questa directory vengono passate ad "autoconf" per le diverse architetture.
