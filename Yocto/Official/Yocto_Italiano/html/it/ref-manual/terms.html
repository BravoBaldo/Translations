3 Terminologia di Yocto Project

Ecco un elenco di termini e definizioni che potrebbero essere utili agli utenti che si avvicinano per la prima volta all'ambiente di sviluppo del Yocto Project. Sebbene alcuni di questi termini siano universali, l'elenco li include per completezza:

File Append

File che aggiungono informazioni di build a un file di ricetta. I file append sono noti come file append di BitBake e file .bbappend. Il sistema di build OpenEmbedded prevede che ogni file append abbia un file di ricetta (.bb) corrispondente. Inoltre, il file append e il file ricetta corrispondente devono utilizzare lo stesso nome file radice. I nomi dei file possono differire solo per il suffisso del tipo di file utilizzato (ad esempio, formfactor_0.0.bb e formfactor_0.0.bbappend).

Le informazioni contenute nei file append estendono o sovrascrivono le informazioni presenti nel file di ricetta con lo stesso nome. Per un esempio di file append in uso, consultare la sezione "Appending Other Layers Metadata With Your Layer" nel Manuale di Sviluppo dei Task di Yocto Project.

Quando si assegna un nome a un file append, è possibile utilizzare il carattere jolly "%" per consentire la corrispondenza con i nomi delle ricette. Ad esempio, si supponga di avere un file append denominato come segue:

busybox_1.21.%.bbappend

Questo file append corrisponderà a qualsiasi versione della ricetta busybox_1.21.x.bb. Quindi, il file append corrisponderà a uno qualsiasi dei seguenti nomi di ricetta:

busybox_1.21.1.bb
busybox_1.21.2.bb
busybox_1.21.3.bb
busybox_1.21.10.bb
busybox_1.21.25.bb

Nota

L'uso del carattere "%" è limitato al fatto che funziona solo direttamente prima della parte .bbappend del nome del file di append. Non è possibile utilizzare il carattere jolly in nessun'altra posizione del nome.

BitBake

L'esecutore e lo scheduler di task utilizzati dal sistema di build OpenEmbedded per creare le immagini. Per ulteriori informazioni su BitBake, consultare il Manuale Utente di BitBake.

Board Support Package (BSP)

Un gruppo di driver, definizioni e altri componenti che forniscono supporto per una specifica configurazione hardware. Per ulteriori informazioni sui BSP, consultare il Manuale del Board Support Package (BSP) di Yocto Project.

Directory di Build

Questo termine si riferisce all'area utilizzata dal sistema di compilazione OpenEmbedded per le build. L'area viene creata quando si esegue source lo script di configurazione dell'ambiente che si trova nella directory dei sorgenti (ad esempio, oe-init-build-env o init-build-env quando si utilizza bitbake-setup). La variabile TOPDIR punta alla Build Directory.

Quando si configura la build manualmente (vedere Setting Up the Poky Reference Distro Manually), si ha molta flessibilità nella creazione della Build Directory. Ecco alcuni esempi che mostrano come creare la directory. Gli esempi presuppongono che la Source Directory si chiami bitbake-builds:

  • Creare la Build Directory all'interno della Source Directory e lascia che il nome predefinito della Build Directory sia build:

    $ cd bitbake-builds
$ source layers/openembedded-core/oe-init-build-env

  • In alternativa, specifica il percorso della Build Directory quando si esegue oe-init-build-env. Tutte le cartelle intermedie nel path devono esistere. L'esempio seguente crea una Build Directory denominata YP-6.1 all'interno della directory esistente mybuilds:

    $ source bitbake-builds/layers/openembedded-core/oe-init-build-env mybuilds/YP-6.1

    Questo path può anche essere un percorso assoluto e trovarsi al di fuori della directory di lavoro corrente:

    $ source bitbake-builds/layers/openembedded-core/oe-init-build-env /opt/mybuilds/YP-6.1

Nota

Per default, la Build Directory contiene TMPDIR, una directory temporanea utilizzata dal sistema di compilazione. TMPDIR non può trovarsi su un server NFS. Pertanto, per default, la Build Directory non può trovarsi su un server NFS. Tuttavia, se è necessario che la Build Directory si trovi su NFS, è possibile configurarla impostando TMPDIR nel file build/conf/site.conf in modo che utilizzi un'unità locale. In questo modo, TMPDIR viene effettivamente separato da TOPDIR, che rappresenta la Build Directory.

Host di Build

Il sistema utilizzato per creare immagini in un Ambiente di Aviluppo di Yocto Project. Il sistema di compilazione viene talvolta chiamato "Host di Sviluppo" o "Build Host".

buildtools

Tool di compilazione in formato binario, che forniscono le versioni necessarie degli strumenti di sviluppo (come Git, GCC, Python e make) per eseguire il sistema di build di OpenEmbedded su un host di sviluppo che non dispone di tali versioni minime.

Consultare il paragrafo "Versioni richieste di Git, tar, Python, make e gcc" nel Manuale di Riferimento per i dettagli sul download o la creazione di un archivio di tali strumenti.

buildtools-extended

Un set di binari buildtools esteso con strumenti di sviluppo aggiuntivi, come una versione necessaria del compilatore GCC per eseguire il sistema di build di OpenEmbedded.

Consultare il paragrafo "Versioni richieste di Git, tar, Python, make e gcc" nel Manuale di Riferimento per i dettagli sul download o la creazione di un archivio di tali strumenti.

buildtools-make

Una variante di buildtools, che fornisce solo la versione necessaria di make per eseguire il sistema di build di OpenEmbedded.

Built-in Fragment

Un built-in fragment [frammento nativo] è un tipo specifico di Configuration Fragment che influenza il valore di una singola variabile a livello globale. I Built-in Fragments non richiedono un file di configurazione separato, ma, come un normale Configuration Fragment, possono essere abilitati o disabilitati tramite l'utilità da riga di comando bitbake-config-build.

Quando viene dichiarato, un "built-in fragment" segue la seguente convenzione di nomenclatura:

<fragment>:<variable name>

Dove:

  • <fragment> è il nome del frammento integrato.

  • <variable name> è il nome della variabile da modificare tramite questo frammento.

Per esempio:

machine:MACHINE

Questo codice configura il Built-in Fragment machine per modificare il valore della variabile MACHINE.

L'impostazione della variabile MACHINE tramite questo frammento deve seguire questa sintassi:

machine/qemux86-64

Questo imposta il valore di MACHINE a qemux86-64.

In OpenEmbedded-Core (OE-Core), l'elenco dei Built-in Fragments disponibili può essere ottenuto dalla variabile OE_FRAGMENTS_BUILTIN.

Per maggiori dettagli sui frammenti, consultare:

  • La sezione Using Configuration Fragments del Manuale di Riferimento di Yocto Project per un elenco dei frammenti supportati da OpenEmbedded Build System e una guida rapida su come gestire i frammenti.

  • Consultare la sezione Creating New Configuration Fragments In Your Build del Manuale di Sviluppo dei Task di Yocto Project per i dettagli su come creare nuovi frammenti nella build.

Classi

File che forniscono incapsulamento logico ed ereditarietà, in modo che i pattern di uso comune possano essere definiti una sola volta e poi facilmente utilizzati in più ricette. Per informazioni di riferimento sulle classi di Yocto Project , consultare il capitolo "Classi". I file delle classi terminano con l'estensione .bbclass.

File di Configurazione

File che contengono definizioni globali di variabili, variabili definite dall'utente e informazioni sulla configurazione hardware. Questi file indicano al sistema di build di OpenEmbedded cosa compilare e cosa includere nell'immagine per supportare una particolare piattaforma.

Configuration files end with a .conf filename extension. There are multiple types of configuration files, such as:

  • The build/conf/local.conf configuration file in the Build Directory contains user-defined variables that affect every build.

  • The meta-poky/conf/distro/poky.conf configuration file defines Yocto "distro" configuration variables used only when building with this policy. See the Creating Your Own Distribution section of the Yocto Project Reference Manual for more information.

  • Machine configuration files, which are located in Layer BSP, define variables for specific hardware and are only used when building for that target (e.g. the machine/beaglebone.conf configuration file defines variables for the Texas Instruments ARM Cortex-A8 development board).

  • Configuration Fragments such as core/yocto/sstate-mirror-cdn define snippets of configuration that can be enabled from the command-line.

See also the Struttura della Directory Sorgente section of the Yocto Project Reference Manual for more example of configuration files.

Configuration Fragment

Un Configuration Fragment (chiamato anche Configuration Fragment Standard) è un configuration file che contiene istruzioni di configurazione, come ad esempio le assegnazioni di variabili, che influenzano la build a livello globale quando il frammento è abilitato. Per default, i frammenti di configurazione si trovano nella directory conf/fragments/ di un Layer.

Nota

Un'altra tipologia di frammento da non confondere con i Configuration Fragment Standard sono i Built-in Fragment, utilizzati per assegnare un singolo valore a una variabile a livello globale.

Um frammento di configuration file deve contenere un riepilogo [summary] (BB_CONF_FRAGMENT_SUMMARY) e una descrizione (BB_CONF_FRAGMENT_DESCRIPTION) che ne spieghino lo scopo.

In OpenEmbedded-Core (OE-Core), la posizione dei frammenti e le variabili necessarie per ciascun frammento sono specificate nel file bitbake.conf grazie alla direttiva addfragments e alle variabili OE_FRAGMENTS, OE_FRAGMENTS_METADATA_VARS e OE_FRAGMENTS_BUILTIN.

I frammenti possono essere elencati, abilitati e disabilitati tramite l'utility da riga di comando bitbake-config-build.

Per maggiori dettagli sui frammenti, consultare:

  • La sezione Using Configuration Fragments del Manuale di Riferimento di Yocto Project per un elenco dei frammenti supportati da OpenEmbedded Build System e una guida rapida su come gestire i frammenti.

  • Consultare la sezione Creating New Configuration Fragments In Your Build del Manuale di Sviluppo dei Task di Yocto Project per i dettagli su come creare nuovi frammenti nella build.

Container Layer

A flexible definition that typically refers to a single Git checkout which contains multiple (and typically related) sub-layers which can be included independently in your project's build/conf/bblayers.conf file.

In some cases, such as with OpenEmbedded's meta-openembedded layer, the top level meta-openembedded/ directory is not itself an actual layer, so you would never explicitly include it in a build/conf/bblayers.conf file; rather, you would include any number of its layer subdirectories, such as meta-oe, meta-python and so on.

On the other hand, some container layers (such as meta-security) have a top-level directory that is itself an actual layer, as well as a variety of sub-layers, both of which could be included in your build/conf/bblayers.conf file.

In entrambi i casi, l'espressione "container layer" viene semplicemente utilizzata per descrivere una struttura di directory che contiene più layer OpenEmbedded validi.

Cross-Development Toolchain

In generale, una toolchain di cross-sviluppo è una raccolta di strumenti e utilità di sviluppo software che vengono eseguiti su un'architettura e consentono di sviluppare software per un'architettura diversa, o di destinazione [target]. Queste toolchain contengono cross-compilatori, linker e debugger specifici per l'architettura target.

Yocto Project supporta due diverse toolchain di cross-development:

  • Una toolchain utilizzata esclusivamente da e all'interno di BitBake durante la creazione di un'immagine per un'architettura target.

  • Una toolchain riallocabile utilizzata dagli sviluppatori al di fuori di BitBake durante lo sviluppo di applicazioni destinate a un dispositivo specifico.

La creazione di queste toolchain è semplice e automatizzata. Per informazioni sui concetti relativi alle toolchain applicati a Yocto Project, consultare la sezione "Generazione di Toolchain di Cross-Sviluppo" nel Manuale Introduttivo e Concetti di Yocto Project. Ulteriori informazioni sull'utilizzo della toolchain riallocabile sono disponibili nel manuale Manuale di Sviluppo di Applicazioni Yocto Project e Software Development Kit (SDK/eSDK).

Extensible Software Development Kit (eSDK)

Un SDK custom per gli sviluppatori di applicazioni. Questo eSDK consente agli sviluppatori di integrare le proprie librerie e modifiche di programmazione nell'immagine, rendendo il codice disponibile ad altri sviluppatori di applicazioni.

Per informazioni sull'eSDK, consultare il manuale Manuale di Sviluppo di Applicazioni Yocto Project e Software Development Kit (SDK/eSDK).

Immagine

Una immagine [image] è un artefatto del processo di build di BitBake, data una raccolta di ricette e Metadati correlati. Le immagini sono l'output binario che viene eseguito su hardware specifico o su QEMU e sono utilizzate per casi d'uso specifici. Per un elenco dei tipi di immagine supportati da Yocto Project, consultare il capitolo "Immagini".

Initramfs

Un filesystem in RAM iniziale (Initramfs) è un archivio cpio, eventualmente compresso, che viene estratto dal kernel Linux nella RAM in un'istanza speciale di tmpfs, utilizzata come filesystem root iniziale.

Questa tecnica sostituisce il vecchio disco RAM di inizializzazione ("initrd"), che si avviava su un dispositivo a blocchi emulato nella RAM, ma risultava meno efficiente a causa dell'overhead dovuto al passaggio attraverso un filesystem e alla necessità di duplicare il contenuto dei file a cui si accede nella cache dei file nella RAM, come avviene per qualsiasi dispositivo a blocchi.

Nota

Per quanto riguarda i bootloader, le immagini Initramfs e "initrd" vengono comunque copiate nella RAM nello stesso modo. Per questo motivo, la maggior parte dei bootloader si riferisce alle immagini Initramfs come "initrd" o "init RAM disk".

Questo tipo di meccanismo viene tipicamente utilizzato per due motivi:

  • Per avviare lo stesso binario del kernel su più sistemi che richiedono "device driver" differenti. L'immagine Initramfs viene quindi personalizzata per ogni tipo di sistema, includendo i moduli del kernel specifici necessari per accedere al filesystem root finale. Questa tecnica è utilizzata in tutte le distribuzioni GNU/Linux per desktop e server.

  • Per un avvio più rapido. Poiché il filesystem root viene estratto nella RAM, l'accesso alle prime applicazioni nello spazio utente è molto più veloce rispetto all'inizializzazione di un dispositivo a blocchi, all'accesso a più blocchi da esso e all'attraversamento di un filesystem con il suo overhead. Ad esempio, questo permette di visualizzare una schermata iniziale molto presto e di occuparsi successivamente del montaggio del filesystem root finale e del caricamento dei driver del kernel meno critici in termini di tempo.

Questo archivio cpio può essere caricato nella RAM dal bootloader oppure incluso nel binario del kernel.

Per informazioni sulla creazione e l'utilizzo di un Initramfs, consultare la sezione "Building an Initial RAM Filesystem (Initramfs) Image" nel Manuale di Sviluppo dei Task di Yocto Project.

Layer

Una raccolta di ricette correlate. I layer consentono di consolidare i metadati correlati per personalizzare la build. I layer isolano inoltre le informazioni utilizzate durante la build per architetture multiple. I layer sono gerarchici nella loro capacità di sovrascrivere le specifiche precedenti. È possibile includere un numero qualsiasi di layer disponibili da Yocto Project e personalizzare la build aggiungendo i layer desiderati. È possibile cercare nel "Layer Index" i layer utilizzati all'interno di Yocto Project.

Per informazioni introduttive sui layer, consultare la sezione "Il Modello a Layer di Yocto Project" nel Manuale Introduttivo e Concetti di Yocto Project. Per informazioni più dettagliate sui layer, consultare la sezione "Comprendere e Creare i Layer" nel Manuale di Sviluppo dei Task di Yocto Project. Per una discussione specifica sui layer BSP, consultare la sezione "Layer BSP" nella Guida degli Sviluppatori di Board Support Packages (BSP) di Yocto Project.

LTS

Questo termine ("Long Term Support") significa "Supporto a lungo termine" e, nel contesto di Yocto Project, corrisponde a versioni stabili selezionate per le quali vengono forniti aggiornamenti di bug e sicurezza per almeno quattro anni. Per maggiori dettagli, consultare la sezione Versioni con Supporto a Lungo Termine.

Metadata

Un elemento chiave di Yocto Project sono i metadati utilizzati per costruire una distribuzione Linux, contenuti nei file che l'OpenEmbedded Build System analizza durante la creazione di un'immagine. In generale, i Metadati includono ricette, file di configurazione e altre informazioni relative alle istruzioni di compilazione [build], nonché i dati utilizzati per controllare cosa viene compilato e gli effetti della compilazione. I Metadati includono anche comandi e dati che indicano le versioni del software utilizzate, la loro provenienza e le modifiche o aggiunte al software stesso (patch o file ausiliari) utilizzate per correggere bug o personalizzare il software per un utilizzo specifico. OpenEmbedded-Core è un importante insieme di metadati validati.

Nel contesto del kernel ("kernel Metadata"), il termine si riferisce ai frammenti di configurazione del kernel e alle funzionalità contenute nel repository Git yocto-kernel-cache.

Mixin

Un layer Mixin è un layer che può essere creato dalla community per aggiungere una funzionalità specifica o supportare una nuova versione di un pacchetto per una release LTS. Per maggiori dettagli, consultare la sezione Versioni con Supporto a Lungo Termine.

OpenEmbedded Build System

Il sistema di build utilizzato da Yocto Project, che impiega Bitbake come esecutore di task. Nella documentazione di Yocto Project, il sistema di build OpenEmbedded viene talvolta indicato semplicemente come "il sistema di build". Qualora vengano menzionati altri sistemi di build, come ad esempio un sistema di build host o target, la documentazione ne specifica chiaramente la differenza.

Nota

Per informazioni storiche su Poky, consultare il termine Poky.

OpenEmbedded-Core (OE-Core)

OE-Core è un insieme di metadati composto da ricette, classi e file associati fondamentali, pensati per essere comuni a molti sistemi derivati ​​da OpenEmbedded, incluso Yocto Project. OE-Core è un sottoinsieme curato di un repository originale sviluppato dalla comunità OpenEmbedded, ridotto a un insieme più piccolo e centrale di ricette continuamente validate. Il risultato è un insieme di ricette di base rigorosamente controllato e di qualità garantita.

È possibile consultare il codice sorgente di OpenEmbedded-Core (OE-Core) su openembedded-core.

Package

Nel contesto di Yocto Project, questo termine [pacchetto] si riferisce all'output impacchettato di una ricetta prodotto da BitBake (ovvero una "baked recipe"). Un pacchetto [package] è generalmente costituito dai binari compilati prodotti dai sorgenti di una ricetta. Si "cucina" (ndt: bake=cucinare ovvero compilare) qualcosa eseguendola tramite BitBake [ndt:CucinaBit].

È importante notare che il termine "pacchetto" [package] può, in generale, avere significati più sfumati. Ad esempio, i pacchetti a cui si fa riferimento nella sezione "Pacchetti Richiesti per l'Host di Build" sono binari compilati che, una volta installati, aggiungono funzionalità alla distribuzione Linux.

Un altro punto degno di nota è che storicamente, all'interno di Yocto Project, le ricette venivano chiamate pacchetti [package]; da qui l'esistenza di diverse variabili BitBake apparentemente denominate in modo errato (ad esempio, PR, PV e PE).

Package Groups

Gruppi arbitrari di Ricette software. I "Package Group" [gruppi di pacchetti] vengono utilizzati per contenere ricette che, una volta compilate, solitamente svolgono una singola attività. Ad esempio, un gruppo di pacchetti potrebbe contenere le ricette per il software proprietario o a valore aggiunto di un'azienda. Oppure, il gruppo di pacchetti potrebbe contenere le ricette che abilitano la grafica. Un gruppo di pacchetti è essenzialmente un'altra ricetta. Poiché i file dei gruppi di pacchetti sono ricette, terminano con l'estensione .bb.

Poky

Poky, che si pronuncia Pochi, è una distribuzione embedded di riferimento e una configurazione di test di riferimento. Poky offre quanto segue:

  • Una distribuzione funzionale di base utilizzata per illustrare come personalizzare una distribuzione.

  • Un mezzo per testare i componenti di Yocto Project (ovvero, Poky viene utilizzato per validare Yocto Project).

Poky non è una distribuzione a livello di prodotto. Piuttosto, è un buon punto di partenza per la personalizzazione.

Nota

Poky also used to be a repository containing the combination of BitBake, OpenEmbedded-Core (OE-Core), the meta-yocto repository and the Yocto Project documentation -- which were combined with the combo-layer tool.

This repository is still hosted at https://git.yoctoproject.org/poky and is still updated for maintained releases that are older than Whinlatter (5.3). Newer releases now use bitbake-setup to clone and setup the initial OpenEmbedded Build System environment. For more information on how to use bitbake-setup, see the Build Rapida di un'Immagine con lo Yocto Project document. An alternative can be to setup the above repositories manually, by following the Setting Up the Poky Reference Distro Manually section of the Yocto Project Development Tasks Manual.

Nota

Poky è nato come un progetto open-source inizialmente sviluppato da OpenedHand. OpenedHand ha sviluppato Poky a partire dal sistema di build OpenEmbedded esistente per creare un sistema di build commercialmente supportato per Linux embedded. Dopo l'acquisizione di OpenedHand da parte di Intel Corporation, il progetto Poky è diventato la base per il sistema di build di Yocto Project.

Ricetta

Un insieme di istruzioni per la creazione di pacchetti. Una ricetta [recipe] descrive da dove ottenere il codice sorgente, quali patch applicare, come configurare il codice sorgente, come compilarlo e così via. Le ricette descrivono anche le dipendenze per le librerie o per altre ricette. Le ricette rappresentano l'unità logica di esecuzione, ovvero il software da compilare e le immagini da creare, e utilizzano l'estensione di file .bb.

Reference Kit

Un esempio funzionante di un sistema, che include un BSP, un build host e altri componenti, compatibile con hardware specifico.

SBOM

Questo termine (Software Bill of Materials) indica la distinta base del software. Quando si distribuisce un software, la distinta base fornisce una descrizione di tutti i componenti utilizzati, le relative licenze, le dipendenze, le modifiche apportate e le vulnerabilità note corrette.

Questo documento può essere utilizzato dai destinatari del software per valutare la propria esposizione a problemi di conformità delle licenze e vulnerabilità di sicurezza.

Per maggiori dettagli, consultare l'articolo Software Supply Chain su Wikipedia.

Il sistema di build OpenEmbedded può generare tale documentazione per il progetto, in formato SPDX, basandosi su tutti i metadati utilizzati per creare le immagini software. Consultare la sezione "Creating a Software Bill of Materials" del Manuale di Sviluppo dei Task.

Source Directory

Questo termine [Directory Sorgente] si riferisce alla struttura di directory creata a seguito della configurazione dell'ambiente per la creazione di immagini con Yocto Project, operazione che può essere eseguita in due modi:

  • Utilizzando l'utilità da riga di comando bitbake-setup (Setting Up The Environment With bitbake-setup).

  • Oppure configurando manualmente i Layers (Setting Up the Poky Reference Distro Manually).

In entrambi i casi, il risultato sarà un insieme di Layers e una Build Directory: questa è la directory sorgente per la build. La documentazione di solito indica questa directory con il nome "bitbake-builds".

Una struttura tipica per la Source Directory sarebbe:

bitbake-builds/
├── build/
└── layers/

Dove la directory layers/ corrisponde alla directory contenente i layer del progetto, e la directory build/ corrisponde alla Build Directory.

Presentiamo la struttura della Source Directory e i suoi componenti in dettaglio nella sezione Struttura della Directory Sorgente del Manuale di Riferimento di Yocto Project.

Nota

Il sistema di build OpenEmbedded non supporta nomi di file o directory contenenti spazi. Assicurarsi che la directory sorgente utilizzata non contenga questo tipo di nomi.

La directory Source Directory contiene BitBake, OpenEmbedded-Core (OE-Core) e altri file che supportano Yocto Project.

Di conseguenza, è necessario che la Source Directory sia presente sul sistema di sviluppo per poter sviluppare applicazioni con Yocto Project.

SPDX

Questo termine sta per Software Package Data Exchange e viene utilizzato come standard aperto per fornire una Software Bill of Materials (SBOM) [distinta base software]. Questo standard è sviluppato nell'ambito del progetto Linux Foundation e viene utilizzato dal sistema di build OpenEmbedded per fornire una SBOM associata a ciascuna immagine software.

Per maggiori dettagli, consultare la pagina SPDX page di Wikipedia e la sezione "Creating a Software Bill of Materials" del Manuale di Sviluppo dei Task.

SPDX License Expression

Uno standard definito da SPDX per esprimere come una o più licenze si applicano a un'opera.

La sintassi per un'espressione di licenza SPDX è definita nella Specifica SPDX.

Sysroot

Durante la cross-compilazione, il file system target può avere una struttura e un contenuto diversi rispetto al sistema host. Il concetto di sysroot si riferisce a una directory che riproduce il file system target e può essere utilizzata per la cross-compilazione.

Nel contesto delle toolchain di cross-compilazione, una sysroot contiene tipicamente le librerie C e gli header del kernel, oltre ai binari compilati per la libreria C. Una toolchain multilib può contenere diverse varianti dei binari della libreria C, ciascuna compilata per un set di istruzioni target (come armv5, armv7 e armv8), ed eventualmente ottimizzata per uno specifico core della CPU.

Nel contesto più specifico del sistema di build OpenEmbedded e di Yocto Project, ogni ricetta ha due sysroot:

  • Un sysroot target contenente tutte le librerie e gli header target necessari per compilare la ricetta.

  • Un sysroot nativo contenente tutti i file e gli eseguibili host necessari per compilare la ricetta.

Vedere le variabili SYSROOT_* che controllano la creazione e la memorizzazione dei sysroot.

Task

Un'unità di esecuzione per ricetta per BitBake (ad esempio do_compile, do_fetch, do_patch e così via). Uno dei principali vantaggi del sistema di compilazione è che, poiché ogni ricetta in genere avvia l'esecuzione di numerosi task [attività], è del tutto possibile che molti task vengano eseguiti in parallelo, sia i task provenienti da ricette separate, quelli indipendenti all'interno della stessa ricetta, potenzialmente fino al livello di parallelismo del sistema di compilazione.

Toaster

Un'interfaccia web per OpenEmbedded Build System di Yocto Project. L'interfaccia consente di configurare ed eseguire le build. Le informazioni relative alle build vengono raccolte e memorizzate in un database. Per informazioni su Toaster, consultare il Manuale Utente di Toaster.

Upstream

Riferimento al codice sorgente o ai repository che non si trovano localmente sul sistema di sviluppo, ma in un'area remota controllata dal manutentore del codice sorgente. Ad esempio, affinché uno sviluppatore possa lavorare su una specifica porzione di codice, deve prima ottenerne una copia da una sorgente "upstream".
